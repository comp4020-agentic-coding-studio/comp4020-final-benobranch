## Why

The user wants four systems built next — troop types, factories, a skill
tree, and the zone-capture mechanic — each as its own issue so separate
agent sessions can work them in parallel worktrees. Read together, all four
need the same missing pieces: who owns which suburb, what color represents
each player, a second resource beyond TFLOPS, and a place for a unit to
stand. If each of the four branches invents its own version of these, that's
not a mergeable set of diffs — it's four incompatible schemas touching the
same foundational files (`server/protocol.ts`, `server/store.ts`,
`server/index.ts`, `server/public/map.js`), exactly the add/add collision
[docs/git-workflow.md](../docs/git-workflow.md) rule 4 exists to prevent,
except with four sessions instead of two. This issue is that shared
foundation, scoped to land fast and first so [[ANU-014]], [[ANU-015]],
[[ANU-016]] and [[ANU-017]] can then run concurrently against a contract
instead of each other's guesses.

**A second resource is a real design change, not an assumption.** PLAN.md's
"Data centers" section currently says TFLOPS is "the single resource that
ties territory, economy and tech progression together... not a different
currency." But the user's own request names a second one explicitly: troops
are destroyed for "resources gained by destroying enemy troups" that fund
building more factories, and the skill tree bullet separately lists "more
scrap gained by killing enemy troops" as a perk. Both phrases only make
sense if scrap (combat currency, from kills) is distinct from TFLOPS
(compute currency, from data centers, funding the skill tree). This issue
updates PLAN.md to say so, rather than leaving a written decision
contradicted by four branches built on top of it.

**Time-based state must come from stored timestamps, not a running timer** —
`docs/adr/0001-persistence-and-realtime-stack.md` already established this
for the exact same reason (`fly.toml`'s `auto_stop_machines` means nothing
is running while the machine is idle) and flagged that future "time-based
state (TFLOPS accrual, etc.)" would need the same treatment. Capture
progress ([[ANU-017]]), production queues ([[ANU-015]]), unit travel
([[ANU-014]]) and the TFLOPS/scrap accrual this issue stubs are all exactly
that future case arriving.

**[[ANU-010]] left a residual risk** this issue is the right point to close:
`map.json` and `map-geometry.json` were independently re-derived with the
same ACT-Remainder multipart-split logic, proven to produce the same
`sal_code` set but not proven to produce the same physical polygon piece for
part `N` in both files. Harmless while nothing used it — not harmless once
ownership/stripes render against a specific piece.

**Depends on [[ANU-011]] landing first.** That issue refactors
`server/public/map.js` from a standalone page into a mountable module and
removes the counter/bump protocol entirely. Starting any of 014-017 before
it merges means building against files ANU-011 is simultaneously rewriting.
Confirm via `git branch -r` / `gh pr list` before starting this issue.
Separately, [[ANU-012]] (pre-existing `spec/map-balance.test.ts` failures,
unrelated to this work) is already open — don't treat its failures as
caused by this issue.

## Done when

- **One migration, not four.** A single `PRAGMA user_version` bump adds
  every table/column this issue and the four downstream issues need, so
  014-017 don't each need their own schema migration (which would collide
  on the same `user_version` number across four branches):
  - `lobby_members.color` — assigned once, at the same point `callsign`
    already locks in (`createLobby`/`joinLobby`), stable for the lobby's
    lifetime.
  - A per-member `scrap` balance and a per-member `tflops` balance +
    `tflops_last_accrued_at` timestamp (the balance itself; real accrual
    logic is explicitly out of scope here — see below).
  - `suburb_ownership`, lobby-scoped: `sal_code -> owner_player_id | null`,
    plus capture-state columns reserved for [[ANU-017]] to fill in
    (`capturing_player_id`, `capture_started_at`, `capture_accumulated_ms`,
    `contesting_player_id`) — this issue defines and migrates the columns,
    ANU-017 implements the state machine that reads/writes them.
  - `units`: id, lobby, owner, `sal_code` (current location), a unit-type
    key, `spawned_at` — the occupancy record, not yet the real stat/combat
    model ([[ANU-014]] owns that).
  - A `unit_types` table seeded with placeholder rows ANU-014 fleshes out
    with real stats.
- **A minimal occupancy primitive** in `server/protocol.ts`: `placeUnit`/
  `moveUnit` messages plus a broadcast of per-suburb occupancy, with a
  placeholder eligibility check ("any suburb") that [[ANU-014]] later
  replaces with its real adjacency/flight rules — the message shape doesn't
  change when it does, so [[ANU-017]]'s capture-state specs can put a
  contesting unit into a suburb without waiting on ANU-014's movement rules
  to exist.
- **Stored-timestamp rule, generalized.** Documented (a short comment where
  the pattern is first used, plus a note in
  `docs/adr/0001-persistence-and-realtime-stack.md`): every duration
  (capture time, production time, unit travel, TFLOPS/scrap accrual) is
  computed from a stored start time + elapsed wall-clock time at
  read/broadcast time, never from an interval/timeout left armed across
  requests. Add a `GAME_TIME_SCALE` env var (default `1`) that multiplies
  elapsed-time calculations in every place this pattern is used, so
  `spec/` can run a multi-minute design value in real seconds.
- **Player colors**: a palette of 12 (matching `MAX_CAPACITY`), assigned
  uniquely per lobby member, verified distinct from the data-center tier
  colors `map.js` already uses (magenta/amber/blue for mega/major/standard —
  [[ANU-010]]) so a player's color is never mistaken for a data-center tier
  marker.
- **Spawn suburbs auto-owned at kickoff**: the moment `startLobby` fires,
  each player's spawn suburb (from `scripts/map/data/map.json`'s
  `spawn_table_by_lobby_size`, already baked per lobby size) becomes
  `suburb_ownership`-owned by them — so troops/factories/capture all start
  from a non-empty ownership state instead of an all-neutral map.
- **A perk/modifier hook**: a narrow per-lobby-member interface (e.g. named
  multipliers — `factoryBuildSpeedMultiplier`, `factoryBuildCostMultiplier`,
  `scrapPerKillMultiplier`, `captureSpeedMultiplier`,
  `dataTransferSpeedMultiplier` — default `1`/no-op) that [[ANU-016]]'s
  skill tree writes to and [[ANU-015]]/[[ANU-017]]/future TFLOPS-flow code
  reads from, so no system has to reach into the skill tree's internals
  directly.
- **Closes ANU-010's residual risk**: a check (script or `spec/` assertion)
  confirming every `map.json` adjacency edge touching a split "ACT
  Remainder" node also touches it geometrically in `map-geometry.json` —
  the node *sets* already match per `spec/map-geometry.test.ts`; this
  additionally proves the split pieces line up physically.
- **File layout convention**, stated here so 014-017 can cite it instead of
  improvising: server-side logic per system in its own module
  (`server/territory.ts`, `server/units.ts` for this issue;
  `server/factories.ts`, `server/skill-tree.ts` for the downstream issues),
  client-side rendering per system as its own function composed into
  `map.js` (`renderUnits`, `renderFactories`, `renderOwnership`, etc.)
  rather than one shared file each branch edits in the same place.
- **PLAN.md amendment**: "Bases, drones, skill tree" and "Data centers"
  sections updated to describe the two-resource economy (TFLOPS from data
  centers fuels the skill tree; scrap from destroying enemy units fuels
  factory/unit production), replacing the "not a different currency /
  single resource" framing, with a sentence on why it changed.
- `spec/*.test.ts`: color assignment is unique per lobby and disjoint from
  data-center tier colors; a started lobby auto-owns each player's spawn
  suburb; a stored-timestamp duration survives a real process
  restart mid-duration with the correct elapsed time (not reset, not lost —
  same style of check as `spec/persistence.test.ts`'s restart tests); the
  split-node geometric-adjacency check passes.
- No regressions: full `pnpm check` green except the already-open,
  unrelated [[ANU-012]] map-balance failures (call out explicitly in this
  issue's Resolution which failures are pre-existing, per that issue's own
  Notes, so they aren't mistaken for something this issue broke).

## Resolution

**One `PRAGMA user_version` bump (v5, `server/store.ts`)** covers every
table/column the four downstream issues need, not just what this issue
itself reads: per-member `color`/`joined_at`/`scrap`/`tflops`/
`tflops_last_accrued_at`/five `perk_*` multiplier columns; `lobbies.
started_at`; `suburb_ownership` (with ANU-017's reserved capture-state
columns); `units` + `unit_types` (schema only — see below for why seed rows
aren't in the migration), plus `requires_skill_node`/travel columns
ANU-014/ANU-016 will use; `factories` (ANU-015); `skill_nodes` (ANU-016).
Verified against a real v4 database (seeded via a throwaway worktree
checked out at the pre-ANU-013 commit): the migration runs clean, backfills
a color for the pre-existing member, and sets `started_at` from the old
`updated_at` for an already-started lobby.

**`unit_types`' seed rows are upserted at store boot (`server/units.ts`'s
`seedBaseUnitTypes`, `ON CONFLICT(key) DO UPDATE`), not inserted by the
migration.** A migration runs once per schema version, but both ANU-014
(real drone/robot stats) and ANU-016 (gated variant rows) need to add or
change `unit_types` rows after this issue merges — seeding them in the v5
migration would force whichever of those two lands first into its own
colliding `user_version` bump just to re-seed a row, exactly the collision
this issue exists to prevent. The rule going forward: reference rows like
this are upserted idempotently from code at boot, never seeded by a
migration.

**Two bugs in the original `lobby_members` write path, found and fixed
before merging** (the second via `advisor`'s review of the diff, not
caught by `pnpm check` since no existing spec exercised it — see
[[ANU-018]] for the standalone harness record):

1. The pre-existing `upsertMembership` (`INSERT OR REPLACE`) would have
   reset every new economy/perk/color column to its default on *every
   reconnect* — replaced with a one-time `insertMembership` (first join /
   lobby switch) and a narrow `touchMembership` UPDATE (reconnect to the
   *same* lobby, writes back only the already-locked name/color).
2. That replacement initially used a plain `INSERT` for first-join, which
   doesn't account for `player_id` still being `lobby_members`' primary
   key: an existing member of lobby A creating or joining lobby B (the
   ordinary Server Browse flow) hit a `UNIQUE constraint failed` error,
   uncaught inside the ws message handler — a real crash on a normal user
   action, not an edge case ([[ANU-018]]). Fixed with
   `INSERT ... ON CONFLICT(player_id) DO UPDATE`, which also explicitly
   resets economy/perk columns on a genuine lobby switch (a new game, not
   a continuation of the old one's). Covered by
   `spec/lobby-membership.test.ts`: store-level tests for switch-resets-
   economy and reconnect-preserves-economy, plus a real WebSocket-level
   test that creating a second lobby while already in a first doesn't
   crash the connection or the process.

Also fixed: member ordering now comes from a stored `joined_at` (not
`rowid`, which the old REPLACE pattern would have reordered on every
reconnect) so spawn-suburb assignment is stable — and the v5 backfill
stamps `joined_at` with a JS-side 1ms-staggered timestamp per member
(not `strftime('now')` repeated in a loop, which can tick identically for
an entire lobby inside one migration transaction) so the rowid order it's
meant to preserve actually survives.

**Perk hook** (`server/perks.ts`) exposes only `getPerkMultipliers`/
`setPerkMultiplier(key, absoluteValue)` — never the raw columns — so a
skill-tree purchase sets an absolute value rather than stacking a running
product, and a repeated purchase is idempotent (`spec/perks.test.ts`).

**Stored-timestamp rule generalized** into `server/time.ts`'s `elapsedMs`
helper plus a `GAME_TIME_SCALE` env var; documented in
`docs/adr/0001-persistence-and-realtime-stack.md`. `lobbies.started_at`
(set once, guarded by `UPDATE ... WHERE started = 0` so a second
`startLobby` call can't clobber it) is the first real duration this
generalization applies to — `LobbyState.gameElapsedMs` is derived from it at
broadcast time. `spec/lib/spawn-server.ts` gained a `gameTimeScale` option
so specs can exercise a multi-minute design value in real seconds;
`spec/territory.test.ts`'s restart test uses scale 60, asserts
`startedAt` is byte-identical before and after the restart, and brackets
`gameElapsedMs` tightly against `(real elapsed since startedAt) * 60` —
tight enough that the test was verified to actually fail (by temporarily
hard-coding `elapsedMs` to ignore its scale argument) rather than just
asserting a loose "greater than some floor," which an earlier version of
this test did and which wouldn't have caught a silently-dropped scale.

**Player colors**: a 12-color palette in `server/protocol.ts`
(`PLAYER_COLORS`), re-picked after an earlier version was caught in
review making a false claim. That version's comment said every color was
"≥25° hue distance from each data-center marker hue," but five of its
twelve entries actually sat within that window (an orange 8° from the
amber marker, a blue 8° from the standard marker, two magenta/pink
entries 15° from the mega marker) — the concrete failure this would cause:
a player's territory fill and a data-center marker rendered in
near-identical hues on exactly the suburbs the game is about. The current
palette is picked from the ~210° of the hue wheel that's genuinely ≥25°
from all three marker hues (36°/216°/313°), ordered so the
furthest-from-any-marker colors are assigned first (small lobbies only use
the first few slots). `spec/territory.test.ts` imports `PLAYER_COLORS`
directly (not regexing hex literals out of the source file) and asserts
both the hue-distance property the comment claims AND a secondary RGB-
distance check (≥60 from markers, ≥60 pairwise).

**Spawn suburbs auto-owned at kickoff, using the PLAYER COUNT at start, not
the lobby's configured capacity**: `server/territory.ts`'s
`assignSpawnOwnership` takes the member list and derives `n =
clamp(members.length, 4, 12)` itself, called from `index.ts`'s `startLobby`
handler right after the lobby's `started`/`startedAt` flip. The first
version of this took the lobby's `capacity` instead — wrong per PLAN.md
("spawns are computed per lobby from its player count"): a 12-capacity
lobby started with the 4-player minimum would have used the first 4 entries
of the 12-player spawn ring rather than the 4-player ring's own (differently
balanced) set. `spec/territory.test.ts`'s spawn-ownership test exercises
exactly this case (capacity 12, started with 4 players) and asserts the
owned suburbs equal the 4-player table's set exactly, not just "4 suburbs,
owners are members." `server/public/app.js`'s client-side spawn-ring
preview (`mountMap`) is updated to match: it now passes
`lobby.members.length` to `mountMap`, not `lobby.capacity` — the same bug,
client side, would otherwise have shown the wrong ring in the exact case
the spec above exercises.

**Occupancy primitive**: `server/units.ts`'s `placeUnit`/`moveUnit`, wired
to new `placeUnit`/`moveUnit` protocol messages and a `ServerOccupancy`
broadcast (`type: "occupancy"`), gated on "any real suburb" (validated
against `map.json`'s sal_code set via `server/map-data.ts`) and "lobby has
started." Sent on reconnect (not just on the next change) so a resuming
client's occupancy view isn't stale.

**ANU-010's residual geometry risk closed**: `spec/territory.test.ts`
checks every `map.json` adjacency edge touching a split "ACT Remainder" node
(Belconnen/Gungahlin, 5 split sal_codes, 36 touching edges) also shares an
exact vertex (within a 0.5-unit tolerance) with its neighbor's polygon in
`map-geometry.json` — all pass (toposimplify's shared-border guarantee
holds). A second "mutation" test swaps two split nodes' paths and confirms
the check actually fails, so it's a real check, not a vacuously-passing one.

**PLAN.md amended**: "Data centers" and "Bases, drones, skill tree" sections
now describe TFLOPS (skill tree) and scrap (factory/unit production) as two
distinct resources, replacing the "single resource / not a different
currency" framing — a new "Two resources" subsection explains why, citing
the user's own request as the source of the change.

**File-layout convention followed**: `server/territory.ts`, `server/
units.ts` (this issue's two systems), plus `server/perks.ts`, `server/
time.ts`, `server/map-data.ts` as small shared helpers — all separate from
`server/store.ts`/`server/index.ts`, so ANU-015/016/017 add their own
`factories.ts`/`skill-tree.ts` modules without touching these.

**No regressions**: `pnpm check` — typecheck clean, `check:issues` clean,
79/88 tests pass. The 9 failures are exactly [[ANU-012]]'s pre-existing,
already-open `spec/map-balance.test.ts` failures (N=5 through N=12's
recomputed soft-access ratios no longer matching the baked values, and N=8
exceeding the 3.0 bound) — confirmed unchanged by diffing against a baseline
`pnpm check` run on this worktree before any ANU-013 code was written.

## Notes

- Depends on [[ANU-011]] merging first — confirm it has landed (or at
  minimum its protocol/map.js shape is stable) before starting, same
  check ANU-009's Notes asked for against ANU-008.
- Deliberately infrastructure-only: no real troop stats, no real factory
  production, no skill-tree nodes, no capture pause/resume/reset logic —
  those are [[ANU-014]], [[ANU-015]], [[ANU-016]], [[ANU-017]], which can
  run as four parallel worktrees once this merges.
- Three design calls are deferred to the downstream issues rather than
  decided here, each flagged there as "confirm with the user before locking
  in": combat resolution determinism ([[ANU-014]]), whether capturing a
  suburb destroys an enemy factory inside it ([[ANU-015]]), and the cap on
  how many simultaneous capturers a suburb's stripe visuals need to support
  ([[ANU-017]]).
- GUI boundary that applies to this issue and all four downstream ones: map
  representations (icons, fills, animations) are in scope; a control that
  lets a player trigger an action themselves is not — every new action goes
  through the protocol only, per the user's own stated sequencing (systems
  first, the GUI that lets a player act on them afterward, once all four are
  in place).

## Why

`server/units.ts`'s `canReach` lets a drone (`movement_mode === "fly"`)
reach ANY suburb on the map unconditionally — the whole "ignore
adjacency/corridor" rule from issues/ANU-014.md has no range limit at all,
so a drone sitting in spawn can be sent clear across the map in one order.
User feedback from live play: this is too strong relative to the robot's
owned-or-adjacent-to-owned restriction (effectively a 1-hop rule, every
move) — drones need *some* ceiling, just a much more generous one than
robots get, to keep "ignore terrain" meaningfully different from "teleport
anywhere."

## Done when

- A drone's `moveUnits`/`moveUnit`/`attackSuburb` order is rejected
  (`unreachable`, same reason robots already use) when its destination is
  more than 5 road-adjacency hops from the nearest suburb the ordering
  player currently owns. Still "ignore adjacency/corridor" below that
  ceiling — a drone doesn't need a clear path through owned territory the
  way a robot does, it just can't be dispatched past 5 hops' distance from
  the player's empire.
- Measured via BFS over the same `adjacency` map `buildAdjacency`/
  `groundCanReach` already build in `server/units.ts`, from the full set of
  the player's owned suburbs (not just the drone's own origin) — a drone
  near a far-flung owned outpost should get its 5-hop ceiling measured from
  there too, not just the player's main cluster.
- `server/public/map.js`'s client-side reachability courtesy check
  (`groundCanReachSuburb`, mirrored for the robot row's unreachable-greyout
  in `sidebar.js`) gets an equivalent drone-side BFS helper, so the "Move
  units" panel greys out a drone row for an out-of-range destination the
  same way it already does for robots — same UX, same "server stays
  authoritative, this is a courtesy only" precedent.
- `pnpm check` green. Per `CLAUDE.md`'s cost-discipline rule, no manual
  headless-Chrome verification required for this pass.

## Resolution

Added `DRONE_MAX_HOPS = 5` and a new `flyCanReach` (`server/units.ts`,
alongside the existing `groundCanReach`), wired into `canReach` in place of
the old unconditional `true` for `movement_mode === "fly"`. `flyCanReach`
does a multi-source BFS, bounded at 5 hops, from the union of the player's
owned suburbs *and* the moving unit's own current suburb — the origin had to
be added as a fallback source beyond what the issue's "Done when" specified,
after `spec/capture.test.ts`'s "contester leaving resumes progress" test
caught a real regression: a landless player (one who owns nothing, only
holding a unit placed via `placeUnit`'s any-suburb loophole, ANU-014's
Notes) would otherwise have an empty owned set and a permanently-stranded
drone, 0 hops from everywhere. `canReach`'s signature gained an `origin`
parameter threaded through from all three call sites
(`attackSuburbImpl`/`moveUnit`/`moveUnits`) to support this.

Client-side: `server/public/map.js` gained `droneCanReachSuburb` (same
multi-source-BFS-with-origin-fallback logic, `DRONE_MAX_HOPS` duplicated as
a local constant — same "mirrors the server exactly" precedent
`groundCanReachSuburb` already set for the robot case). `sidebar.js`'s
`pendingMove` gained a `dronesUnreachable` flag alongside the existing
`robotsUnreachable`, and `handleMoveDestinationPick`/`buildMovePanel` now
grey out whichever archetype's row can't reach the picked destination
(either, neither, or both), instead of only ever checking robots.

`spec/units.test.ts` gained two new cases (a drone reaching exactly
`DRONE_MAX_HOPS` away, and failing just beyond it), both suburbs picked by a
real BFS from the map fixture, not guessed. `spec/occupancy.test.ts`'s drone
move test (flagged in this issue's Notes as needing an update) was rewritten
per that Notes entry: `REAL_SAL_CODE` is now the player's own spawn and
`ANOTHER_REAL_SAL_CODE` the farthest suburb still within the 5-hop cap, both
found by BFS rather than hardcoded array indices.

`pnpm check`: typecheck and `check:issues` clean; `pnpm test` is 223/223
individual test passes (including the two new ANU-047 cases and the
rewritten occupancy test). One pre-existing, already-diagnosed flake
remains: `spec/persistence.test.ts`'s `afterAll` hook times out stopping its
spawned child server — this is the exact local-dev-server-environment noise
[[ANU-032]] already found and documented as "not a CI-reproducible
condition," unrelated to this change (confirmed: no files this issue
touches overlap with persistence.test.ts/spawn-server.ts, and the same
timeout reproduces running that spec file alone, against a freshly-started
server, on an uncontested port). Not re-opened as a new issue per
`CLAUDE.md`'s "grep before filing" rule, since ANU-032 already covers it.

## Notes

AskUserQuestion-confirmed during this session: (1) the 5-hop ceiling is
measured via BFS from the full set of suburbs the player owns, not just the
drone's own current/origin suburb; (2) both server enforcement and the
client-side move-panel greyout are in scope, not server-only.

`spec/occupancy.test.ts`'s drone `moveUnits` test (`REAL_SAL_CODE` ->
`ANOTHER_REAL_SAL_CODE`, two arbitrary suburbs the file's own comments admit
are "possibly far-apart") is 7 hops apart on the current map and will need
updating under this cap — that test predates reachability rules entirely
(it's testing the generic move primitive, per its header comment) and
should pick two suburbs within 5 hops of the player's spawn instead, or
place the drone inside owned territory first.

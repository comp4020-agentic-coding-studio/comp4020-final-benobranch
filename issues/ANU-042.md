## Why

Managing garrison distribution by hand across a growing territory count
doesn't scale once a player holds more than a handful of suburbs — the user
wants units that pile up past a threshold at one owned territory to get
automatically sent elsewhere, with a choice of *how* that surplus should be
spread:

- **Balance** — keep roughly equal unit counts across every owned territory.
- **Fortify outward-facing** — weight redistribution toward territories that
  border an enemy (or unclaimed) suburb, with a landlocked territory
  (surrounded entirely by the player's own territory) receiving
  proportionally less than a frontier one, since it faces no immediate
  threat.

Confirmed with the user via AskUserQuestion before writing this issue:

1. **Trigger**: a per-player toggle (`Off` / `Balance` / `Border`), not a
   one-shot button — a ~1s ticker (same shape as `factoryTicker`/
   `captureTicker`/`arrivalTicker` in `server/index.ts`) checks each player's
   owned territories against the threshold and dispatches surplus
   automatically whenever the mode isn't `Off`.
2. **Unit scope**: both drones and robots. Robots stay reachability-
   constrained by `groundCanReach` (server/units.ts) exactly like a manual
   `moveUnits` order — an auto-dispatch only ever sends a robot to a
   directly road-adjacent-or-owned territory, never routed multiple hops in
   one order. This means a robot surplus at a territory with no reachable
   under-threshold neighbour simply doesn't move that tick (not an error,
   not a crash) — reachability is a per-unit-type constraint on the order,
   the same way it already is for a manual order.
3. **Landlocked definition**: a territory is "landlocked" only if every
   map-adjacent suburb (`server/units.ts`'s existing `adjacency` map, built
   from `map-geometry.json`'s edges) is *also* owned by the same player. Any
   non-owned neighbour — enemy **or** unclaimed/neutral — makes it a
   "border" territory, matching "outward facing" literally: only a territory
   fully enclosed by the player's own territory counts as interior.

This reuses the travel-time dispatch path ANU-038 already built
(`units.moveUnits` → `startTransit` → `settleArrivals`) rather than
teleporting units directly — an auto-redistributed unit is visibly in
transit (dotted arrow, ANU-038) exactly like a player-ordered move, and
remains vulnerable to being intercepted/contested en route like any other
dispatch.

## Done when

**Server:**

- A per-player setting, `autoFortifyMode: "off" | "balance" | "border"`
  (default `"off"`), persisted the same way a perk multiplier is
  (`lobby_members` column, migration bump in `server/store.ts`) — not reset
  on reconnect.
- A new `ClientSetAutoFortifyMode` message (`server/protocol.ts`) to flip it,
  validated against the three literal values; reject anything else the same
  way `parseClientMessage` rejects a malformed `moveUnits.counts` value.
- A threshold constant (this issue's call, same "a value had to be chosen,
  write down why" precedent as `CAPTURE_DURATION_MS`/`DRONE_SPEED` — document
  the reasoning in a comment) for how many units at one territory count as
  "surplus" before any auto-dispatch considers moving units away from it.
  Exceeding the threshold triggers evaluation of *that* territory only — it
  does not need every owned territory to be over threshold before acting.
- New logic (own module, e.g. `server/auto-fortify.ts`, per
  `issues/ANU-013.md`'s file-layout convention — one system, one file) with
  a function along the lines of `runAutoFortify(lobbyId, playerId)` that:
  - Reads the player's current ownership (`territory.getOwnership`) and live
    occupancy (`units.getOccupancy`), grouped per owned territory by
    archetype (drone/robot counted separately — a drone surplus shouldn't
    trigger moving robots and vice versa, since they have different
    reachability and the "same type" is the natural unit to rebalance).
  - For each owned territory over the surplus threshold for a given
    archetype, computes how many of that archetype to send elsewhere and to
    which destination(s):
    - **`balance`**: target an equal per-territory count of that archetype
      across all the player's owned territories (that archetype can reach —
      robots only count owned territories that are themselves reachable
      from the source); send enough surplus to the most under-count
      reachable territory/territories to move toward equality, without
      overcorrecting (don't push a territory from over-threshold to
      under the post-move average of everywhere else in a single tick —
      a few ticks of gradual correction is fine and avoids units
      visibly oscillating back and forth).
    - **`border`**: compute each reachable owned territory's border/
      landlocked status (per the Notes' adjacency rule) and bias surplus
      toward border territories under their own fair share, sending
      proportionally less to already-well-stocked or landlocked
      territories. Exact weighting formula is this issue's call — document
      the chosen ratio/algorithm in a code comment, same precedent as the
      speed/threshold constants above.
  - Dispatches each move via the existing `units.moveUnits` (not a new
    primitive) so travel time, reachability rejection, and in-transit
    visuals all apply unchanged — auto-fortify is a decision layer that
    calls the same order path a player's own `moveUnits` click does, not a
    parallel movement system.
  - Never dispatches a unit that's already in transit (moveUnits/
    `selectOwnedUnitsOfTypeAt` already excludes these) and never produces a
    partial/invalid order — if a computed order would fail validation
    (e.g. rounds to zero reachable destinations), skip it that tick rather
    than erroring.
- Wired into a new `~1s` ticker in `server/index.ts` (same unref'd
  `setInterval` shape as `factoryTicker`/`captureTicker`/`arrivalTicker`),
  running `runAutoFortify` once per started lobby per player whose mode
  isn't `"off"` — not from an armed per-player timer (ADR 0001's
  stored-timestamp rule doesn't strictly apply here since there's no
  duration being tracked, but the existing tickers are the established
  "recurring per-lobby sweep" shape and this should match it rather than
  invent a new one).
- `spec/*.test.ts` covering: balance mode converges toward equal counts
  across territories; border mode sends proportionally more to a
  border territory than a landlocked one in the same lobby; a robot surplus
  with no reachable under-threshold destination doesn't move (and doesn't
  error); toggling the mode to `"off"` stops further auto-dispatch
  (in-flight units already dispatched still resolve normally via
  `settleArrivals`); the setting persists across a reconnect.

**Client:**

- A control (sidebar, Territory or a new small settings area — this
  session's call) exposing the three-way `Off`/`Balance`/`Border` choice,
  sending `setAutoFortifyMode` and reflecting the player's current mode from
  lobby/economy state on reconnect.
- No new map visuals required beyond what ANU-038 already draws — an
  auto-dispatched unit in transit looks identical to a manually-dispatched
  one (dotted arrow, progress mark, archetype icon), which is the point:
  this is a dispatch-decision feature, not a new rendering system.

**Both:**

- `pnpm check` green (typecheck + `spec/*.test.ts` against the running
  app). Per `CLAUDE.md`'s current cost-discipline rule, no manual
  headless-Chrome verification required for this pass.

## Resolution

**Schema/protocol**: `server/store.ts` v11 adds `lobby_members.auto_fortify_mode
TEXT NOT NULL DEFAULT 'off'`, reset to `'off'` on a fresh join the same way
perk multipliers reset (`insertMembership`'s `ON CONFLICT` branch). A new
`ClientSetAutoFortifyMode` message (`server/protocol.ts`) is validated
against the exported `AUTO_FORTIFY_MODES` tuple; the chosen mode rides on
the existing private `ServerEconomy` message (`autoFortifyMode` field)
rather than a new broadcast type, since economy was already the
established "private per-player state, re-sent after every relevant
action and on reconnect" channel.

**Server logic**: new `server/auto-fortify.ts` (`createAutoFortify`), a
decision layer with no new movement primitive — every redistribution it
computes is dispatched through the existing `units.moveUnits`, so travel
time, reachability rejection and in-transit visuals (ANU-038) all apply
unchanged. `AUTO_FORTIFY_SURPLUS_THRESHOLD = 6` (chosen the same "a value
had to be chosen, write it down" way as `CAPTURE_DURATION_MS` — high enough
that a freshly captured or lightly garrisoned territory is never touched,
low enough that a factory's steady uncontested output visibly triggers
redistribution within a session). `BORDER_WEIGHT = 2` / `LANDLOCKED_WEIGHT
= 1` set "border" mode's 2:1 target-garrison ratio. Border/landlocked
classification reuses `server/units.ts`'s existing adjacency map via a new
exported `adjacentSalCodes()` (also exported `groundCanReach`, previously
module-private, since nothing outside units.ts had needed it before) —
confirmed with the user that ANY non-owned neighbour, enemy or unclaimed,
makes a territory "border," so only a territory fully enclosed by the
player's own territory is landlocked.

Each run groups the player's occupancy by unit type (drone/robot kept
fully separate — a drone surplus never triggers moving an under-threshold
robot garrison at the same territory) and, per type, computes a weighted
target garrison per owned territory (`balance`: equal weight everywhere;
`border`: `BORDER_WEIGHT`/`LANDLOCKED_WEIGHT` per territory), then drains
over-threshold sources toward the most under-target reachable
destinations. A player's own units already in transit toward a
destination count toward that destination's "effective" garrison
alongside grounded units — this is what stops a second ~1s tick from
re-dispatching past the balanced target before the first batch has even
landed. Verified directly against the running module (see
spec/auto-fortify.test.ts) that a robot redistributed between two of the
player's own owned territories is always reachable regardless of map
adjacency — `groundCanReach`'s existing "already-owned counts as
reachable" rule (server/units.ts) means auto-fortify's robot moves never
actually hit `moveUnits`' `"unreachable"` rejection in practice; the skip-
on-rejection handling is kept anyway as defensive code matching how a
player's own order is handled, not exercised by a passing test case (the
issue's "no reachable destination" scenario doesn't actually arise between
a player's own territories).

Wired into a new `autoFortifyTicker` in `server/index.ts` (same unref'd
1s-interval shape as `factoryTicker`/`captureTicker`/`arrivalTicker`),
settling arrivals first, then running one round per member whose mode
isn't `"off"`, then broadcasting occupancy/captures — matching how a
player-initiated `moveUnits` already broadcasts after dispatching.

**Client**: a three-button `Off`/`Balance`/`Border` picker on the Units tab
(`server/public/index.html`/`sidebar.js`/`style.css`), sending
`setAutoFortifyMode` on click and reflecting `economy.autoFortifyMode` on
every state update including a reconnect. No new map visuals — an
auto-dispatched unit in transit renders identically to a manually-
dispatched one (ANU-038's existing dotted arrow/progress mark/archetype
icon), which was the point.

**Tests**: `spec/auto-fortify.test.ts` (8 cases, store-level against
`createAutoFortify` directly) covers off-mode no-op, single-territory
no-op, below-threshold no-op, balance-mode even split, border-mode's 2:1
weighting (verified against a real adjacency fixture read from
`scripts/map/data/map.json`, not a fabricated graph), archetype
separation, and that in-transit units count toward their destination's
effective garrison (no overcorrection across repeated ticks).
`spec/auto-fortify-protocol.test.ts` (4 cases) covers the wire-level
`setAutoFortifyMode` message: defaults to `off`, is accepted and reflected
on the next `economy` message, rejects an unknown mode value (closing the
connection like any other malformed message), and persists across a
reconnect. `pnpm check` green (233 tests across 30 files, including these 12 new
ones). Per `CLAUDE.md`'s cost-discipline rule, not re-verified by driving a
browser.

## Notes

Confirmed with the user via AskUserQuestion (this session, before writing
this issue): (1) continuous per-player toggle via a ~1s ticker, not a
one-shot manual button; (2) applies to both drones and robots, with robots
staying reachability-constrained exactly like a manual move; (3) a
territory is landlocked only if ALL its map-adjacent neighbours are also
owned by the same player — any enemy-or-unclaimed neighbour makes it a
border territory.

Reuses `server/units.ts`'s existing adjacency map and `groundCanReach`
rather than duplicating reachability/border logic — `server/auto-fortify.ts`
should import these rather than re-deriving suburb adjacency from
`map-geometry.json`/`map.json` itself, per [[ANU-038]]'s "shared adjacency
lives in units.ts, not map-data.ts, to avoid an ANU-013-downstream-branch
collision" precedent (that reasoning no longer applies now those branches
are merged, but the adjacency map itself should still only be built once).

This depends on [[ANU-038]]'s travel-time dispatch path (`moveUnits`/
`settleArrivals`) being in place, which it is (merged, `status: done`).

## Why

The user's own words: "implement a skill tree (where advanced troups with
better stats can be made, better fabs for factories which produce troups
quicker, miscellaneous perks such as better data transfer speed for data
centers, cheaper factory production costs, more scrap gained by killing
enemy troops, faster capture of zones etc.)". This matches PLAN.md's
existing "Bases, drones, skill tree" section ("funded by TFLOPS, faster
with more compute... new unit types, faster/cheaper unit production, misc
perks") almost exactly — this issue is building that section, not
inventing new scope.

Third of four parallel systems issues. Depends on [[ANU-013]] for the perk
hook interface every node in this tree writes to, and for the TFLOPS
balance column nodes are purchased with. Reads [[ANU-014]]'s unit-type
table (to define what an "advanced" unit variant actually changes) but
doesn't implement combat itself.

## Done when

- `server/skill-tree.ts` (per [[ANU-013]]'s file-layout convention) owns a
  `skill_nodes` table (lobby-member-scoped: which nodes a player has
  unlocked) and a static node definition list covering, at minimum, every
  category the user named:
  - **Advanced unit variants** — at least one upgraded drone and one
    upgraded robot variant (better stats than [[ANU-014]]'s base roster),
    added as new `unit_types` rows gated behind the node rather than
    mutating the base type in place (so a player without the node still
    builds the base version).
  - **Better fabs** — a node that increases
    `factoryBuildSpeedMultiplier` (read by [[ANU-015]]'s production
    queue via ANU-013's perk hook).
  - **Cheaper factory production costs** — a node affecting
    `factoryBuildCostMultiplier` (same hook).
  - **More scrap from kills** — a node affecting
    `scrapPerKillMultiplier` (read by [[ANU-014]]'s combat resolution).
  - **Faster capture of zones** — a node affecting
    `captureSpeedMultiplier` (read by [[ANU-017]]'s capture-progress
    calculation).
  - **Better data transfer speed for data centers** — a node affecting
    `dataTransferSpeedMultiplier`. Since PLAN.md's "disconnected (air) vs.
    connected (cable)" TFLOPS-flow mechanic isn't implemented by any
    current or sibling issue, this node only needs to exist in the
    hook/schema and be purchasable — wiring it to an actual effect is out
    of scope here and should be left as an explicit note for whichever
    future issue implements TFLOPS flow, not silently dropped.
- Nodes cost TFLOPS (not scrap — PLAN.md: "TFLOPS earned fund the skill
  tree... the single resource that ties territory, economy and tech
  progression together," which [[ANU-013]] narrows to specifically mean
  skill-tree spend once scrap is split out as the combat currency).
  Purchasing a node is a single synchronous handler (balance-check +
  deduct + unlock with no `await` in between), same concurrency reasoning
  as [[ANU-015]]'s production queue and ADR 0001's bump handler.
- A minimal tree **structure**, not just a flat unlock list — at least one
  real prerequisite relationship (e.g. the advanced unit variant requires
  the matching base-stat node first), since "tree" implies ordering, not
  a shop. Keep this simple (a handful of nodes, 1-2 prerequisite edges) —
  depth/breadth tuning is not the point of this issue.
- A protocol message (e.g. `purchaseNode`) and a broadcast of the
  purchasing player's current unlocked-node set / resulting multipliers,
  so the GUI (later) and other systems (now, via the perk hook) can react.
- **GUI representation (map-drawable / panel-drawable, not yet
  player-controllable — see ANU-013's Notes)**: a pure function, e.g.
  `skillTreeVisual(playerState) -> { nodes: [{ id, unlocked, purchasable, icon }] }`
  reflecting which nodes are unlocked, which are next-purchasable (
  prerequisites met, affordable) vs. locked — covered by a `spec/` test for
  all three states, per `CLAUDE.md`'s no-manual-e2e rule. This is a
  separate panel from the map itself (a skill tree doesn't have map
  coordinates), so it doesn't need to integrate into `map.js`'s rendering,
  just exist as an inspectable client-side module.
- `spec/*.test.ts`: purchasing a node deducts the correct TFLOPS and sets
  the matching perk-hook multiplier to the expected value (read it back via
  the same hook [[ANU-015]]/[[ANU-014]]/[[ANU-017]] will use, proving the
  hook actually changes, not just that a row was written); purchasing a
  node whose prerequisite isn't met is rejected; purchasing twice doesn't
  double-apply the multiplier; `skillTreeVisual` output shape for
  locked/purchasable/unlocked.
- No regressions: full `pnpm check` green except the pre-existing,
  unrelated [[ANU-012]] map-balance failures.

## Notes

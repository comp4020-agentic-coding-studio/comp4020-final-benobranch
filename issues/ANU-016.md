## Why

The user's own words: "implement a skill tree (where advanced troups with
better stats can be made, better fabs for factories which produce troups
quicker, miscellaneous perks such as better data transfer speed for data
centers, cheaper factory production costs, more scrap gained by killing
enemy troops, faster capture of zones etc.)". This matches PLAN.md's
existing "Bases, drones, skill tree" section ("funded by TFLOPS, faster
with more compute... new unit types, faster/cheaper unit production, misc
perks") almost exactly — this issue is building that section, not
inventing new scope.

Third of four parallel systems issues. Depends on [[ANU-013]] for the perk
hook interface every node in this tree writes to, and for the TFLOPS
balance column nodes are purchased with. Reads [[ANU-014]]'s unit-type
table (to define what an "advanced" unit variant actually changes) but
doesn't implement combat itself.

## Done when

- `server/skill-tree.ts` (per [[ANU-013]]'s file-layout convention) owns a
  `skill_nodes` table (lobby-member-scoped: which nodes a player has
  unlocked) and a static node definition list covering, at minimum, every
  category the user named:
  - **Advanced unit variants** — at least one upgraded drone and one
    upgraded robot variant (better stats than [[ANU-014]]'s base roster),
    added as new `unit_types` rows gated behind the node rather than
    mutating the base type in place (so a player without the node still
    builds the base version).
  - **Better fabs** — a node that increases
    `factoryBuildSpeedMultiplier` (read by [[ANU-015]]'s production
    queue via ANU-013's perk hook).
  - **Cheaper factory production costs** — a node affecting
    `factoryBuildCostMultiplier` (same hook).
  - **More scrap from kills** — a node affecting
    `scrapPerKillMultiplier` (read by [[ANU-014]]'s combat resolution).
  - **Faster capture of zones** — a node affecting
    `captureSpeedMultiplier` (read by [[ANU-017]]'s capture-progress
    calculation).
  - **Better data transfer speed for data centers** — a node affecting
    `dataTransferSpeedMultiplier`. Since PLAN.md's "disconnected (air) vs.
    connected (cable)" TFLOPS-flow mechanic isn't implemented by any
    current or sibling issue, this node only needs to exist in the
    hook/schema and be purchasable — wiring it to an actual effect is out
    of scope here and should be left as an explicit note for whichever
    future issue implements TFLOPS flow, not silently dropped.
- Nodes cost TFLOPS (not scrap — PLAN.md: "TFLOPS earned fund the skill
  tree... the single resource that ties territory, economy and tech
  progression together," which [[ANU-013]] narrows to specifically mean
  skill-tree spend once scrap is split out as the combat currency).
  Purchasing a node is a single synchronous handler (balance-check +
  deduct + unlock with no `await` in between), same concurrency reasoning
  as [[ANU-015]]'s production queue and ADR 0001's bump handler.
- A minimal tree **structure**, not just a flat unlock list — at least one
  real prerequisite relationship (e.g. the advanced unit variant requires
  the matching base-stat node first), since "tree" implies ordering, not
  a shop. Keep this simple (a handful of nodes, 1-2 prerequisite edges) —
  depth/breadth tuning is not the point of this issue.
- A protocol message (e.g. `purchaseNode`) and a broadcast of the
  purchasing player's current unlocked-node set / resulting multipliers,
  so the GUI (later) and other systems (now, via the perk hook) can react.
- **GUI representation (map-drawable / panel-drawable, not yet
  player-controllable — see ANU-013's Notes)**: a pure function, e.g.
  `skillTreeVisual(playerState) -> { nodes: [{ id, unlocked, purchasable, icon }] }`
  reflecting which nodes are unlocked, which are next-purchasable (
  prerequisites met, affordable) vs. locked — covered by a `spec/` test for
  all three states, per `CLAUDE.md`'s no-manual-e2e rule. This is a
  separate panel from the map itself (a skill tree doesn't have map
  coordinates), so it doesn't need to integrate into `map.js`'s rendering,
  just exist as an inspectable client-side module.
- `spec/*.test.ts`: purchasing a node deducts the correct TFLOPS and sets
  the matching perk-hook multiplier to the expected value (read it back via
  the same hook [[ANU-015]]/[[ANU-014]]/[[ANU-017]] will use, proving the
  hook actually changes, not just that a row was written); purchasing a
  node whose prerequisite isn't met is rejected; purchasing twice doesn't
  double-apply the multiplier; `skillTreeVisual` output shape for
  locked/purchasable/unlocked.
- No regressions: full `pnpm check` green except the pre-existing,
  unrelated [[ANU-012]] map-balance failures.

## Resolution

**`server/skill-tree.ts`** owns the `skill_nodes` table reads/writes
([[ANU-013]]'s schema) plus `purchaseNode`/`getUnlockedNodeIds`. Node
*structure* (id, prerequisite, TFLOPS cost, icon) lives in
`server/public/skill-tree-nodes.js` — plain JS, not `.ts` — so the
client-side `skillTreeVisual` pure function can import the same list with no
bundler, same constraint `map.js`/`app.js`/`unit-visual.js`/
`factory-visual.js` are already built around; `skill-tree.ts` imports that
`.js` file fine (tsconfig `allowJs`), the reverse isn't possible. Nine nodes,
covering every category the user named:

- **Advanced unit variants**: `drone-chassis` -> `advanced-drone` and
  `robot-chassis` -> `advanced-robot`, each a real prerequisite edge (10
  TFLOPS for the chassis, 15 for the variant — a real early/late-game cost
  shape, not two same-priced choices). `server/skill-tree.ts`'s
  `seedSkillGatedUnitTypes` upserts two NEW `unit_types` rows at boot
  (`drone-mk2`/`robot-mk2`, gated by `requires_skill_node`), not mutating
  the base `drone`/`robot` rows — a player without the node still builds the
  base version. Stats are ~1.6-1.75x the base archetype's (health/damage),
  deliberately below the base-to-base 2x drone/robot ratio
  ([[ANU-014]]'s Resolution) so "advanced drone" reads as an upgrade, not a
  reskinned robot.
- **Better fabs** (`better-fabs`, 1.5x `factoryBuildSpeedMultiplier`),
  **cheaper production** (`lean-production`, 0.5x
  `factoryBuildCostMultiplier`), **more scrap per kill**
  (`salvage-training`, 1.5x `scrapPerKillMultiplier`), **faster capture**
  (`rapid-capture`, 1.5x `captureSpeedMultiplier`) — each a root node (no
  prerequisite) setting its named [[ANU-013]] perk-hook multiplier via
  `setPerkMultiplier` (absolute value, matching the hook's idempotent
  contract).
- **Data transfer speed** (`data-uplink`, sets `dataTransferSpeedMultiplier`)
  — purchasable and wired into the hook/schema for real, but genuinely has
  no reader yet: PLAN.md's disconnected/connected TFLOPS-flow mechanic isn't
  implemented by any current or sibling issue. Documented explicitly in
  `server/skill-tree.ts`'s `PERK_EFFECTS` comment rather than silently
  dropped, per this issue's own Done-when.

**`lean-production`'s multiplier is 0.5, not a more generic-looking 0.75** —
caught by `advisor`'s review before merge: `factories.ts`'s `queueUnit`
rounds `build_cost_scrap * costMultiplier` to the nearest whole scrap, and a
drone's cost (2) times 0.75 rounds right back to 2, so the cheapest,
most-built unit got no discount at all. 0.5 halves both the drone (2 -> 1)
and robot (4 -> 2) costs exactly. `spec/skill-tree.test.ts` has a dedicated
test that queues a real drone through `factories.queueUnit` after purchasing
the node and asserts the scrap deduction, not just the stored multiplier
value, so a future rounding regression on this specific pair would be
caught.

**Nodes cost TFLOPS, single synchronous handler**: `purchaseNode`'s balance
check + deduct + unlock is one `UPDATE ... WHERE tflops >= ?` with no
`await` in between (same concurrency reasoning as [[ANU-015]]'s production
queue and ADR 0001's bump handler) — `spec/skill-tree.test.ts` proves this
with a two-near-simultaneous-purchases-one-node-affordable-balance test,
same pattern as `spec/factories.test.ts`'s scrap-race test.

**Protocol**: `purchaseNode` message + `skillTree` broadcast (`type:
"skillTree"`, carrying `unlockedNodeIds`, `multipliers`, and `tflops`) —
per-player, not lobby-wide (a skill tree is per-player state, unlike
occupancy/factories which are visible to the whole lobby), sent on every
purchase and on `hello` for a resumed session with an existing lobby.
`tflops` is included specifically so the client-side `skillTreeVisual` (which
needs both the unlocked set and the current balance to compute
"purchasable") can be fed directly from this one message — an omission
`advisor`'s review caught before merge (the first version only sent
`unlockedNodeIds`/`multipliers`, leaving no wire path to the balance the
visual function needs).

**GUI representation**: `server/public/skill-tree-visual.js`'s
`skillTreeVisual({ unlockedNodeIds, tflops }) -> { nodes: [{ id, icon,
unlocked, purchasable }] }` — a separate panel from the map (no map
coordinates), not yet integrated into `map.js`, same GUI boundary as
[[ANU-013]]'s Notes (map-drawable/panel-drawable, not yet
player-controllable). `spec/skill-tree-visual.test.ts` covers all three
states (locked, purchasable, unlocked) plus the mutual-exclusivity of
`unlocked`/`purchasable`.

**A second bug `advisor` caught before merge, unrelated to the tree logic
itself**: the new `drone-mk2`/`robot-mk2` unit-type keys would have crashed
`server/public/unit-visual.js`'s `unitVisual` — it threw on any
`unitTypeKey` other than the literal `"drone"`/`"robot"`, and these
gated units reach real occupancy rows through `factories.settle ->
units.placeUnit` the moment a player builds one. Latent (nothing mounts
`unitVisual` into the UI yet, so `pnpm check` couldn't see it), but caused
by this issue's own new rows. Fixed with an
`ARCHETYPE_BY_UNIT_TYPE_KEY` lookup mapping both mk2 variants to their base
archetype's icon (an upgrade is a stat change on the same chassis, not a new
archetype); `spec/unit-visual.test.ts` gained two cases for `drone-mk2`
(icon + in-transit state).

**Wire-level coverage added, not just store-level**: `advisor`'s review
flagged that nothing exercised the `purchaseNode` parser branch, the
`index.ts` handler, or the actual broadcast — exactly the kind of gap
[[ANU-013]]'s Resolution records a process-crashing bug slipping through
(a store-level-only test suite that never sent a real message over the
wire). `spec/skill-tree-protocol.test.ts` closes it: insufficient-TFLOPS and
unknown-node rejections over a real WebSocket (confirming the connection
survives a rejection), the `skillTree` send on a resumed `hello`, and a
malformed `purchaseNode` payload closing the socket (1008) like every other
malformed message.

**TFLOPS never accrues in live play** — [[ANU-013]] stubbed the balance
column and flagged accrual as explicitly out of scope; no issue before this
one picked it up, so in live play `purchaseNode` always returns
`insufficient-tflops` (every test here funds the balance directly via a
store-level `UPDATE`, same pattern `spec/factories.test.ts` already uses for
scrap). Doesn't block this issue's own done-when — the purchase/validation
logic and perk hook are real and fully tested — but the tree has no live,
reachable data path until accrual lands. Opened as [[ANU-019]] rather than
silently left for someone to rediscover.

**No regressions**: `pnpm check` — typecheck clean, `check:issues` clean,
142/151 tests pass (24 of those new to this issue: `spec/skill-tree.test.ts`,
`spec/skill-tree-visual.test.ts`, `spec/skill-tree-protocol.test.ts`, plus
two added to `spec/unit-visual.test.ts`). The 9 failures are exactly
[[ANU-012]]'s pre-existing, already-open `spec/map-balance.test.ts` failures
— confirmed unchanged (same 9 test names, same assertion deltas) against a
baseline `pnpm check` run on this worktree before any ANU-016 code was
written.

## Notes

Depends on [[ANU-013]] (perk hook, TFLOPS column, file-layout convention).
Reads but doesn't modify [[ANU-014]]'s `unit_types` table (adds new rows
rather than editing existing ones, to avoid a merge conflict on the same
rows another branch might also be touching) and doesn't implement
[[ANU-015]]'s production queue or [[ANU-017]]'s capture state machine
itself — only the multipliers those systems read.

[[ANU-019]] opened as a follow-up: TFLOPS accrual itself (reading real value
from held data centers over time) isn't implemented by any issue yet, so
this skill tree has no live data path until that lands — purchase/
validation logic here is real and tested, only the balance's source isn't.

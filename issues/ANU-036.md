## Why

The map's unit/data-center/base icons are 32x32 pixel art (rendered with
`image-rendering: pixelated`) and the UI font (`Determination`) is itself a
pixel/retro-game face, but the map surface itself (suburb polygons, stripes,
progress bars) renders perfectly smooth/anti-aliased SVG vector shapes next
to them. A slight pixelation postfx on the whole map brings the vector
surface into the same visual register as the icons and font sitting next to
it, instead of looking like two different rendering eras glued together.

## Done when

- The map surface (`#map-svg`) has a visible, slight pixelation/retro
  filter applied (an SVG `<filter>` via CSS `filter: url(#...)`, not a
  canvas rasterization — the map is live interactive SVG with pan/zoom/tap
  hit-testing that a canvas snapshot would complicate, see Notes).
- The filter doesn't break pan/zoom/tap interaction or the existing
  `pnpm check` suite (`spec/map-geometry.test.ts` etc. still pass).
- It's subtle ("slightly" pixelate, per the request) — legible suburb
  boundaries and tooltips, not an unreadable mosaic.

## Notes

Considered and rejected: rasterizing the SVG to an offscreen low-res canvas
and upscaling with `image-rendering: pixelated` for a literal blocky mosaic.
Rejected because the map's pan/zoom/tap (`map.js`'s pointer-event handling,
`zoomAroundClientPoint`, per-suburb/unit/factory click targets) all operate
on the live SVG DOM; rasterizing it would mean either giving up hit-testing
fidelity or keeping a parallel invisible interactive SVG under a visible
canvas copy, redrawn on a cadence — real complexity for a "slight" effect.
An SVG filter is in-place on the existing element and touches nothing about
input handling.

## Why

[[ANU-009]] shipped Home/Browse/Lobby screens against ANU-005's placeholder
shared-counter-and-bump UI (the "throwaway feature" ANU-005 built just to
prove the WebSocket/broadcast plumbing worked). [[ANU-010]] separately
shipped a real, pannable/zoomable Canberra map with data centers and a
spawn-ring preview — but only as a standalone page (`server/public/map.html`
+ `map.js`) that nothing in the app links to. The two issues were
deliberately scoped independent of each other (separate files, separate
worktrees, per each issue's Notes) specifically so this wiring would be a
follow-up, not blocking either from landing.

Right now "enter a lobby" still means "look at a bump counter" — there is no
path from Browse → join/create a lobby → actually see the game map, which is
the whole point of a lobby once you're in it. This issue is that path.

Confirmed with the user: once a lobby is `started`, its lobby screen should
show the real map (inspect-only, as ANU-010 built it) in place of the
counter/bump panel — not alongside it, and not as a link out to a separate
page. The counter/bump panel has no role in PLAN.md's actual game design
(it was always ANU-005 presence-plumbing scaffolding); it can be retired
once the map covers "what does a started lobby look like."

## Done when

- `server/public/map.js` is refactored from a standalone-page script (it
  currently does `document.getElementById` against IDs only present in
  `map.html`, and does top-level `await fetch(...)` work on module load)
  into something `app.js` can import and mount into a container element on
  the existing `lobby-screen` — same rendering/pan/zoom/tap behaviour, just
  initializable rather than page-global.
- A **waiting** lobby (`started: false`) keeps today's roster + Start button
  (no map yet — nothing to show until the game actually begins).
- A **started** lobby (`started: true`, including on resume via Continue or
  a direct `#/lobby/<id>` link to an already-started lobby) shows the map
  instead of the counter/bump panel. The map's spawn-ring preview defaults
  to that lobby's own `capacity` (not the hardcoded `"8"` `map.js` currently
  defaults to) via `spawn_table_by_lobby_size[String(capacity)]`.
- `server/public/map.html` is removed (no longer a distinct entry point)
  once `app.js`/`index.html` own the only way to reach the map; `map.css`
  stays, scoped under the lobby screen.
- The counter/bump UI (`count`, `last-bumped-by`, `bump` button/handler) and
  its wire protocol (`ClientBump`/whatever broadcasts the count) are removed
  from `index.html`, `app.js`, `protocol.ts`, `server/index.ts`, and
  `store.ts` — not left dead/hidden. If `store.ts`'s schema has a
  `count`/`last_bumped_by` column, drop it with a `PRAGMA user_version`
  migration in the same style as ANU-009's `lobby_members.name` move (don't
  leave an unread column).
- The map still shows the attribution footer and legend (ANU-010's licence
  requirement doesn't go away just because it's embedded).
- `spec/gui.test.ts` drops its counter/bump coverage and gains: a started
  lobby's markup/container for the map is present, a waiting lobby's is not
  (or is hidden); `spec/map-geometry.test.ts` stays as-is (route/data
  checks are unaffected by where the client mounts it).
- `spec/realtime.test.ts`/`spec/persistence.test.ts` drop any
  bump/count-specific assertions and gain nothing new (this issue is
  client-side wiring plus removing dead protocol, not new server game
  state).
- No regressions: full `pnpm check` green.

## Resolution

Done largely as scoped, with two deviations from the plan above, both
because the counter/bump protocol turned out to be load-bearing for two of
the spec's actual probes, not just UI decoration:

- **`spec/map-geometry.test.ts` did *not* stay as-is.** Its "map page
  markup" test fetched the standalone `/map.html`, which this issue deletes.
  Moved that assertion to fetch `/` instead and check the map panel's static
  scaffolding (`#map-panel`, `#map-svg`, etc.) is present in the lobby
  screen — same coverage (the markup exists to mount into), different route.
- **`spec/realtime.test.ts` and `spec/persistence.test.ts` gained changed
  assertions, not "nothing new."** `bump` was the real-time/persistence
  probe for three tests (the 5-connection broadcast test, lobby isolation,
  and the restart test) — removing it without replacement would have
  silently dropped coverage of the brief's real-time/persistence bars, not
  just removed dead-protocol noise. Repointed all three at `startLobby`
  instead (same "one lobby, not another" isolation shape; same "members
  agree on state" convergence check, now on `started` instead of `count`).
  The restart test's assertion also changed shape: since a started lobby
  refuses new joins, "a fresh identity joins post-restart and sees the
  pre-restart counter value" isn't possible to express with `started` as
  the persisted fact — rewritten to assert the *refusal* itself survives
  the restart (a fresh join attempt is still rejected with "started" after
  the process restarts), which is the thing that actually needs to persist
  per PLAN.md's no-late-join rule. This narrows what's directly covered: a
  fresh identity joining an *unstarted* pre-existing lobby after a restart
  (ANU-008's original case) is still covered by the second persistence
  test's token-resume path, just not by this one any more.
- `server/store.ts` gained a `PRAGMA user_version = 4` migration dropping
  `lobbies.count`/`lobbies.last_bumped_by`, same pattern as ANU-009's
  `lobby_members.name` move. Verified directly: hand-seeded a v3-schema
  database (booted a checkout of `2449d5e`, the pre-ANU-011 HEAD, against a
  scratch `DATA_DIR`, created two lobbies, bumped one to `count: 1`), then
  booted this branch's server against that same data dir and confirmed it
  reached `user_version = 4` with both lobbies/members intact and the two
  counter columns actually gone from the schema (`PRAGMA table_info`).
- Found and fixed a CSS cascade bug before it shipped: `.map-panel`'s own
  `display: flex` has the same specificity as the browser's `[hidden] {
  display: none }` rule and loses the source-order tie-break, same trap
  `style.css` already documents for `.screen[hidden]` — without restating
  `.map-panel[hidden] { display: none }`, a *waiting* lobby would have
  rendered an empty map panel. Caught by re-reading the CSS rather than by
  a spec (jsdom doesn't compute layout/cascade), so there's no regression
  test for this specific class of bug — noted for whoever eventually turns
  manual browser verification back on (see CLAUDE.md's cost-discipline
  note).
- `map.js` rewritten from a standalone page's top-level script (one
  top-level `await fetch`, globals read from `map.html`-only element IDs)
  into an idempotent-per-lobby `mountMap(lobbyId, capacity)` /
  `unmountMap()` pair that `app.js` imports and calls from
  `renderLobbyScreen`, which runs on every `lobbyState` broadcast for a
  started lobby (not just once) — guarded so re-renders from presence
  flips don't reset pan/zoom or re-register pointer listeners. The spawn-
  ring preview is now locked to the lobby's own `capacity`; the free-
  standing lobby-size `<select>` ANU-010 built for the standalone page is
  gone, since there's a real lobby here, not an abstract preview.
- Opened [[ANU-012]] for a pre-existing, unrelated break discovered while
  getting `pnpm check` green for this issue: a clean `main` checkout
  already fails 9 `spec/map-balance.test.ts` assertions (commit `b4ef9bd`
  moved a data center without rebalancing, and said so in its own message,
  but never got a tracking issue). Not this issue's regression and not
  fixed here — the user's call per ANU-012 is rebalance vs. revert vs.
  relax the bound. `pnpm check` for ANU-011 itself is green except those 9
  pre-existing failures, confirmed identical on a stock `main` checkout
  with none of this issue's changes applied.

## Notes

Out of scope: this does not make the map reflect per-lobby *live* state
(no ownership, no per-player spawn assignment, no attacks) — ANU-010's Notes
already deferred that to whatever issue adds territory to ANU-008's lobby
model, and this issue doesn't change that. The only per-lobby thing the map
picks up here is which `capacity` to default the spawn-ring preview to.
Also out of scope: the Sunday-5pm scheduler and bot-fill mechanics
(ANU-009's Notes) — `started` is still the same hand-togglable boolean
ANU-009 shipped, just now driving a UI branch instead of only a status
label.

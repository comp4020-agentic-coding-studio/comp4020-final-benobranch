## Why

The home screen the user wants next (ANU-009) needs a **Continue** option
that resumes an existing game, and a **Server browse** option that lists
joinable lobbies. ANU-005's server has neither concept: `playerId` is a
`randomUUID()` assigned fresh per WebSocket connection (so nothing can be
"resumed"), and there is exactly one shared world (the counter), not
multiple lobbies.

This issue builds the backend prerequisite before any new screen is built on
top of it: a player identity that survives a reconnect/reload, and lobbies
that persist in SQLite (not just in the in-memory `connections` Map ANU-005
added), since `fly.toml`'s `auto_stop_machines` means any in-memory registry
is gone the moment the machine idles out and restarts. ANU-009 (the actual
screens) depends on this.

Decided with the user before starting:
- **Identity**: an opaque secret token, generated server-side on first join,
  stored client-side in `localStorage`, sent back in `hello` to resume the
  same public `playerId`. (Not a cookie — simpler, no upgrade-handshake
  cookie parsing, consistent with the existing "anonymous visitor" model.)
- **Exit**: dropped entirely — there's nothing for an "Exit" button to
  meaningfully do in a browser-hosted game (`window.close()` is blocked by
  browsers on a tab the user opened themselves), so the home screen (ANU-009)
  has three options, not four.

## Done when

- A `players` table in SQLite maps a secret token → a stable `playerId` (and
  a display name). The token is never broadcast to other clients — only
  `playerId` is, in `presence`/`welcome` messages, exactly as today.
- `server/protocol.ts`'s `hello` message carries an optional token; if valid,
  the server resumes that player's existing `playerId` instead of minting a
  new one. If absent/invalid, the server mints a new token + `playerId` and
  returns the token to the client (a new `welcome` field) so it can save it.
- `connections` is no longer keyed by `playerId` alone — since the same
  `playerId` can now have more than one live socket (e.g. a reconnect that
  outraces the old socket's `close` event), fix the latent bug this would
  otherwise cause: a second `hello` for the same `playerId` must not let
  that connection's `close` handler delete a *different*, still-live
  connection's presence entry.
- A `lobbies` table in SQLite: id, name, capacity (a parameter for now —
  ANU-006 hasn't landed a faction count yet, so this isn't hardcoded to it),
  member list, and whatever per-lobby state replaces the current global
  counter (move the existing counter/presence state onto the lobby, so
  lobby isolation is provable: a bump in lobby A must not appear in lobby
  B). Lobbies are **never deleted** when they empty — the marker's
  "comes back the next day" scenario is a restarted machine with zero live
  connections, and a just-created lobby must still be listed then.
- Creating a lobby and joining one are each a single synchronous handler
  (no `await` between the capacity check and the member-list write), so two
  players grabbing the last slot at once resolves consistently — same
  reasoning as docs/adr/0001-persistence-and-realtime-stack.md's bump
  handler, applied to lobby capacity.
- At least one lobby exists after a fresh boot with an empty database (e.g.
  a seeded default lobby), so Server Browse is never empty and two marker
  windows can land in the same place without any out-of-band coordination.
- The lobby browser's list updates live: a lobby created in one session
  appears in every other open session's browse view within ~1s (same
  broadcast mechanism as `presence`, scoped to whoever is on the browse
  screen rather than everyone).
- Lobby names (like player names) are untrusted input: capped length in the
  parser, rendered with `textContent` only on the client.
- `spec/realtime.test.ts` and `spec/persistence.test.ts` are adapted to the
  lobby-scoped flow (not weakened — they encode brief promises) plus new
  checks: lobby isolation, the live-updating browse list, a lobby surviving
  a restart with its member list and state intact, and the same token
  resuming as the same `playerId` after a reconnect.
- `docs/adr/0002-identity-and-lobbies.md` records the move from "one
  long-running world" (this project's original pitch, as PLAN.md's brief
  table had it) to multiple lobbies, and the identity/token design — flagged
  so the user knows `README.md`'s eventual argument needs to reflect this
  shift, not just `CLAUDE.md`/`spec/`.

## Notes

Verifying multi-session behaviour for this issue needs real per-player
isolation, not just multiple tabs: two tabs in the *same* browser context
share `localStorage`, so they'd resume as the same player. Use a fresh
browser context (or incognito) per simulated player when testing, not just
a new tab — see also the PLAN.md correction this prompted (two incognito
windows from one session share storage; the assignment actually calls for
two separate Chrome profiles).

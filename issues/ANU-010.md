## Why

[[ANU-006]] baked the game's real map data (`scripts/map/data/map.json`:
139 suburb nodes, 317 road-adjacency edges, 32 tiered data centers, the
per-lobby-size spawn table) but only as an abstract graph — no suburb
polygon geometry, so there's nothing to actually look at yet. The user
wants to start on the GUI's map interaction now that spawns/data-centers
are settled, rather than waiting on territory/combat rules (still open
decisions per PLAN.md) to land first.

This issue is the **render and inspect** layer only: see the real Canberra
map, pan/zoom it, tap a suburb to see what it is (data center tier/TFLOPS,
or a spawn candidate), understand the ring the spawns sit on. It does
**not** cover ownership, attacks, or TFLOPS flow — those need lobby-scoped
game state (territory ownership isn't modelled anywhere yet; [[ANU-008]]'s
lobby/counter skeleton has no notion of suburb ownership) and the combat
rule, which PLAN.md's "Open decisions" section still lists as unresolved.
Building against real geometry now means ANU-008/009's lobby screens and
whatever later issue adds ownership/combat have a map to render into,
instead of starting that from scratch under deadline pressure.

Scoped deliberately independent of ANU-009 (Home/Server-browse/Options,
in progress): this is a new file (`server/public/map.js` + a map data
route), not a change to `app.js` or the lobby screens, so the two don't
conflict across worktrees per docs/git-workflow.md rule 4.

## Done when

- Suburb polygon geometry exists and is committed: `scripts/map/` gains a
  script that fetches/derives boundary geometry for the same 139 nodes
  `map.json` already has (reusing, not re-deriving, the ACT Remainder
  multipart-split logic in `build_adjacency.py` — the split must produce
  the exact same `sal_code`-keyed node set, or spawn/data-center names stop
  lining up with their shapes), simplified (topology-preserving, not
  per-polygon, to avoid reintroducing the gaps/overlaps ABS SAL was chosen
  to prevent) and projected to something a plain SVG can render with no
  client-side projection/mapping library (consistent with the "no build
  step, plain ES modules" decision from [[ANU-007]], and PLAN.md's "fully
  static, no live API calls" map-data decision).
- A new baked file (e.g. `scripts/map/data/map-geometry.json` or folded
  into `map.json`) ships this geometry, with source attribution carried
  alongside it like `map.json` already does.
- `server/public/map.js` (a new file, not a change to `app.js`) renders an
  SVG/canvas map: dark base, neon per-suburb outlines per PLAN.md's art
  direction, data centers visibly marked by tier (mega/major/standard
  should read as visually distinct at a glance), and the spawn ring
  highlighted for at least one illustrative lobby size from
  `spawn_table_by_lobby_size`.
- Pan and zoom work on both marker viewports (390x844 phone, 1920x1080
  desktop): wheel/pinch zoom, drag pan, no horizontal page overflow at
  phone width. Pointer events (not mouse-only), `touch-action: none` on the
  map surface so mobile doesn't intercept pinch/pan as browser zoom, and a
  drag-distance threshold so ending a pan isn't misread as a tap.
- Tap/click a suburb shows its info (name, data-center tier + TFLOPS if
  it's one, remainder/wilderness flag, or "spawn candidate" if it's on the
  current preview's ring) — inspect-only, no ownership or attack action
  (not modelled yet, see Why).
- Visible map data attribution (ABS SAL CC BY 4.0, OSM ODbL) rendered on
  the page, not just recorded in the JSON — required by the CC BY licence
  where the data is displayed.
- `server/static-files.ts` or a new route serves the geometry file; checked
  that it actually ships in the production image (`Dockerfile`'s `COPY`
  lines cover wherever it ends up — confirmed locally against a built
  container, not just `pnpm dev`, the same way ANU-008 verified persistence
  against a real built image rather than a bare `node` process).
- `spec/*.test.ts` covers what's mechanically checkable: the map data route
  serves valid geometry whose suburb key set exactly matches `map.json`'s
  139 `sal_code`s, and the served page's markup contains the map container
  and attribution text.
- Manually verified at both marking viewports via the DevTools Protocol
  method ANU-007 used (`Emulation.setDeviceMetricsOverride`, not
  `--window-size`): can tap-select a small inner suburb (e.g. Parkes,
  Barton) on phone width, no visible slivers/gaps between adjacent
  suburbs when zoomed in, no horizontal overflow.
- No regressions: existing specs (`spec/invariants.test.ts`,
  `spec/persistence.test.ts`, `spec/realtime.test.ts`,
  `spec/map-balance.test.ts`, `spec/gui.test.ts`) still pass unmodified.

## Resolution

Built `scripts/map/build_geometry.py`: fetches the raw ABS SAL polygons
(`fetch_suburbs.py`'s output), reuses `build_adjacency.py`'s exact ACT
Remainder multipart-split logic verbatim, projects to EPSG:7855 (GDA2020 /
MGA zone 55, same CRS `build_lobby_config.py` already uses for bearings),
and topology-simplifies with the `topojson` package (`toposimplify`,
tolerance 50m) rather than per-polygon Shapely simplification — confirmed
post-simplify that summed polygon area equals unioned area to within
floating-point rounding, i.e. no gaps/overlaps were introduced. Output
(`scripts/map/data/map-geometry.json`, ~80KB) ships pre-flattened SVG path
strings (y-flipped so north is up) and a `representative_point` per suburb
(not a plain centroid — guaranteed inside the polygon, which a centroid
isn't on a concave shape) for marker placement, plus both a full-ACT and an
urban-only view box (the latter is the default view, since the full extent
is dominated by rural ACT Remainder tiles that would shrink urban Canberra
to a sliver on a phone-width screen).

`spec/map-geometry.test.ts` verifies the geometry file's `sal_code` set
exactly matches `map.json`'s (set equality, confirmed via a spec check).
Note on a residual risk this doesn't close: both files were independently
re-derived from the raw ABS SAL fetch via the same split logic, which gets
the *same* `sal_code`s for the two multipart ("ACT Remainder — Belconnen"/
"Gungahlin") tiles but only guarantees each file's part `N` is *some*
consistent choice, not provably the *same* physical polygon piece as the
other file's part `N`, if ABS ever returned the GeoJSON's part ordering
differently between fetches. Harmless for this issue (nothing here keys
game logic off which specific remainder piece is which), but would matter
if a later issue wires ownership to these same split nodes — worth a
cheap follow-up check then (e.g. that every `map.json` edge touching a
split node has its two sides geometrically touching).

`server/index.ts` gained a `/map/map.json` + `/map/map-geometry.json` route
(reusing `static-files.ts`'s existing traversal-safe serving, pointed at a
new `MAP_DATA_DIR` env var) rather than duplicating the baked files into
`server/public/`. `Dockerfile` now copies `scripts/map/data/` into the
image — checked against a real built container (`docker build` +
`docker run --tmpfs /data`, matching how CI's own `check` job runs it), not
just `pnpm dev`, since a missing `COPY` line would otherwise only 404 in
production.

`server/public/map.html` + `map.css` + `map.js` (new files, no changes to
`app.js`/`index.html` — ANU-009 is concurrently rewriting those, confirmed
via `git branch -r`/`gh pr list` before starting, per docs/git-workflow.md
rule 4) render the map as inline SVG: suburbs as `<path>`s from the baked
geometry, data centers as tier-coloured circles (magenta/amber/blue for
mega/major/standard), and a spawn-ring preview for a user-selectable lobby
size (4-12, matching `spawn_table_by_lobby_size`). Pan/zoom is pointer-event
based (mouse, touch and pen alike) with `touch-action: none` on the map
container so mobile doesn't intercept pinch/pan as page zoom, wheel-zoom
with a focal point, and a drag-distance threshold (8px) distinguishing a
tap from a pan.

One round of manual browser verification happened before `CLAUDE.md` added
its temporary no-manual-e2e cost-discipline rule mid-session; everything
after that point was verified via `pnpm check` only, per that rule. The
manual round (headless Chrome via Playwright, both marking viewports)
caught two real bugs no amount of code-reading had surfaced:
- **Oversized/uniformly-dark markers and suburb borders.** Stroke widths
  were originally written in map-unit scale (e.g. `stroke-width: 60`) to
  match the geometry's planar coordinate scale, but `vector-effect:
  non-scaling-stroke` means the browser renders that number as literal
  CSS pixels regardless of zoom — so every border/marker rendered
  60px-wide on screen, flooding the suburb fills and hiding the
  tier-colour distinction entirely. Fixed by rewriting stroke widths in
  actual screen-pixel terms (1-2.5px).
- **Tap-select never fired.** `container.setPointerCapture()` (used for
  drag-panning) retargets the DOM's synthesized `click` event's `target` to
  the capturing element for the rest of that pointer's lifetime, so
  `event.target` in the click handler was always the container `<div>`,
  never the suburb/marker actually under the pointer. Fixed by hit-testing
  with `document.elementFromPoint(event.clientX, event.clientY)` instead of
  trusting `event.target`.

A subsequent design review (not a browser run — reasoning through the
coordinate math and CSS against the numbers the manual round had already
printed) found four more real bugs the "viewBox changed"/"no horizontal
overflow" checks had let through as false positives:
- **Pan/zoom didn't track the pointer.** The original math mapped
  `(clientX - containerRect.left) / containerRect.width` directly onto
  `viewBox.width`, but the urban view box is portrait while the desktop
  container is landscape, so `preserveAspectRatio="meet"` letterboxes the
  rendered map — the container-fraction mapping is wrong by exactly that
  letterbox gap, in whichever axis ends up boxed at a given viewport size.
  A drag moved the map at roughly a third of cursor speed on desktop (an
  eighth on phone, boxed the other way), and wheel-zoom drifted sideways
  instead of staying anchored under the cursor. Fixed by going through
  `svg.getScreenCTM()` (`clientToSvgPoint`/`zoomAroundClientPoint` in
  `map.js`) instead of container-rect fractions — the CTM reflects the
  browser's actual letterboxed layout rather than assuming the SVG fills
  the container uniformly in both axes.
- **Legend and attribution were clipped below the fold.** `style.css`'s
  `body { padding-top: 2.5rem }` (clearing ANU-007's fixed `#status` bar,
  which `map.html` doesn't have) pushed a `100vh`-tall `.map-screen` that
  far below the real viewport, and the map surface captures wheel events as
  zoom rather than page scroll, so there was no way to reach the footer.
  Fixed by zeroing that padding on this screen and switching to `100dvh`.
- **A pinch-to-one-finger transition snapped the view.** `endPointer` only
  reseeded drag state once *every* pointer had lifted, so ending a two-
  finger pinch down to one finger left the pan state pointing at the
  pre-pinch pointer position and viewBox; the next single-finger move then
  jumped the view back to that stale reference. Fixed by reseeding drag
  state from the remaining pointer whenever the count drops to exactly one.
- **Markers could steal a tap from the suburb underneath them.** Marker
  radii are in map units, so they visually grow at higher zoom and can
  overhang a neighbouring suburb; `elementFromPoint` would then resolve the
  marker's suburb instead of whichever suburb was actually tapped. Fixed
  with `pointer-events: none` on `.dc-marker`/`.spawn-marker` — the
  suburb's own `describe()` already surfaces that suburb's data-center/
  spawn info, so nothing is lost by the marker itself not being clickable.

`spec/map-geometry.test.ts` (new) checks: the geometry file's `sal_code`
set exactly equals `map.json`'s, every suburb has a non-empty path and a
finite label point, every data-center and spawn name (across all lobby
sizes) resolves to a suburb with geometry, the `/map/map.json` and
`/map/map-geometry.json` routes serve valid JSON, the `/map/` route 404s
for any path other than those two exact files, and `map.html`/`map.js`/
`map.css` are served with the right content types and markup. `pnpm check`
passes locally and against a container built from the (updated)
`Dockerfile`, run the same way CI's `check` job does — confirming the
geometry file actually ships in production, not just under `pnpm dev`.

No regressions: `spec/invariants.test.ts`, `spec/persistence.test.ts`,
`spec/realtime.test.ts`, `spec/map-balance.test.ts` and `spec/gui.test.ts`
all still pass unmodified (60 tests total across the suite).

## Notes

Explicitly out of scope here (tracked as open decisions / future issues,
not this one): suburb ownership, attacks/combat resolution, TFLOPS flow
and the connected/disconnected corridor status, and wiring the map into a
specific lobby's live state (depends on whatever issue adds territory to
[[ANU-008]]'s lobby model). This issue only needs one illustrative lobby
size's spawn preview, not a live per-lobby render.

`/map.html` is reachable directly but isn't linked from anywhere in the
app yet (no nav from the Home/HUD screens) — intentional, since wiring it
in means deciding where it fits relative to [[ANU-009]]'s in-flight Home/
Browse/Lobby screens, which this issue deliberately didn't touch. Follow-up
work.

This session's manual-verification round (the pointer-capture and
stroke-width bugs) happened before `CLAUDE.md` picked up its temporary
no-manual-e2e cost-discipline rule; the four bugs found afterwards (pan/zoom
tracking, clipped footer, pinch-to-one-finger, marker tap-stealing) were
caught by reasoning through the math/CSS against already-printed numbers,
not a further browser run, consistent with that rule.

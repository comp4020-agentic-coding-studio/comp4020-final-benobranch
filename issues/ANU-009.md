## Why

The user wants to start building out the game's UI screens, beginning with
a Home screen offering:

- **Continue** — resumes an existing game
- **Server browse** — enters a lobby browser to create/join lobbies
- **Options** — placeholder for now

(A fourth option, Exit, was considered and deliberately dropped — see
ANU-008's Why section: there's nothing meaningful for an Exit button to do
in a browser-hosted game.)

This depends on ANU-008 (persistent identity + lobbies in SQLite): Continue
needs the server to be able to say "yes, this token has a resumable lobby"
or "no, nothing to resume," and Server Browse needs a real, live list of
lobbies to show, not a mock.

**Scope updated after ANU-008 merged** — a second parallel session's ANU-006
landed real game rules in PLAN.md's "Players & spawn balance" section while
ANU-008 was in flight: games are **4–12 players**, minimum 4 to start, no
late join once started, bot-filled up to 4 if a lobby is short at the
scheduled weekly kickoff (Sunday 5pm Australia/Sydney), with that scheduled
match being the "real" game and ad hoc lobbies (any time, any player count
within 4–12) existing for marking/testing/practice. ANU-008 shipped lobby
capacity as a free 2–16 parameter specifically because this hadn't landed
yet (see its ADR). Confirmed with the user: build Home/Browse against the
real 4–12/schedule/bot-fill rules now, not the generic placeholder range.

## Done when

- A Home screen (replacing today's single join form) renders three options:
  Continue, Server browse, Options.
- **Continue** is disabled/absent when the server has no resumable lobby for
  this client's stored token (first-ever visit, or a token that no longer
  resolves to a lobby), and otherwise takes the player straight back into
  their lobby's HUD.
- **Server browse** shows the live lobby list from ANU-008 (name, member
  count/capacity, updating in real time as lobbies are created or filled —
  within ~1s of another session's action, matching the brief's real-time
  bar) with create-a-lobby and join-a-lobby actions.
- **Lobby capacity is bounded 4–12** in both the create-lobby form and
  `server/protocol.ts`'s `createLobby` validation (tightened from ANU-008's
  placeholder 2–16 range), matching PLAN.md's settled rule.
- The lobby browser and lobby screen show each lobby's **state** — waiting
  (below 4, open to joins), ready-to-start, or started/closed to new joins —
  since "no late join once a game begins" is a real rule a marker could hit.
  A minimal state machine is enough for this issue (see Notes for what's
  deliberately out of scope); it does not need the Sunday-schedule or
  bot-fill *mechanics* implemented yet, but the UI must not misrepresent a
  lobby as open-forever when PLAN.md says it isn't.
- **Options** is a placeholder screen (a "coming soon" panel is enough) —
  not a dead link; clicking it must navigate somewhere, just not to real
  settings yet.
- Navigation uses hash routing (`#/home`, `#/browse`, `#/lobby/<id>`, `#/options`)
  rather than full page reloads: no server routing changes needed, the
  browser back button works, and a lobby's URL is shareable (useful for the
  "two marker windows" scenario — copy the lobby link from window A, open it
  in window B).
- Styling stays consistent with ANU-007's existing dark/HUD chrome
  (`server/public/style.css`) — this is new screens in the same shell, not a
  new visual language.
- `spec/gui.test.ts` is extended to cover the new screens' markup (home
  options present, browse screen structure, options placeholder reachable).
- Manually verified with two actually-separate identities (per ANU-008's
  note: separate browser contexts/profiles, not same-session tabs/incognito
  windows) — both can browse, create/join lobbies, and see each other's
  lobby-list changes live.
- No regressions in the existing specs.

## Notes

Depends on ANU-008 landing first (or at minimum its protocol/store shape
being stable) — don't start the screens' data-fetching logic against a
moving target. Check ANU-008's status before beginning this one.

Deliberately out of scope for this issue, left for a dedicated follow-up
(ANU-006's own notes flagged this as "not yet covered by any open issue"):
the actual Sunday 5pm Australia/Sydney scheduled kickoff mechanism, and bot
fill logic for an under-4 lobby at that kickoff. This issue only needs a
lobby to carry enough state (started vs not) for the UI to correctly block
a late join and show real status — not the scheduler that flips that state
automatically. A hand-togglable/manually-started lobby is enough for this
issue; wiring it to a real Sunday clock is separate backend work.

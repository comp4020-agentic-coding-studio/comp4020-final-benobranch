## Why

Sending a stack of units at an occupied (enemy-defended) territory sees the
correct number of units actually leave the source territory (confirmed via
the occupancy broadcast at dispatch time — `server/units.ts`'s `moveUnits`
stamps every selected unit's `destination_sal_code`/`move_started_at`), but
on arrival only half the dispatched units remain engaged in combat at the
destination; the other half instantly snap back to the source territory
instead of ending up at the destination or dying there.

Not yet root-caused against the actual `settleArrivals`/`resolveCombatAt`
code path (`server/units.ts`) — this issue records the symptom as observed
so the investigation isn't lost, per `CLAUDE.md`'s rule to open an issue for
a bug as soon as it's noticed rather than only once it's understood.

## Done when

- Root cause identified in `server/units.ts`'s arrival-resolution path
  (`settleArrivals`/`resolveCombatAt`) or wherever else in the dispatch/
  arrival pipeline a dispatched unit can end up relocated back to its
  origin instead of either arriving at its destination (moved/kill) or
  staying engaged there (hit).
- A `spec/units.test.ts` (or `spec/combat.test.ts`) case reproduces the
  exact scenario: send a multi-unit stack at a defended destination,
  confirm none of the dispatched units silently reappear at the source
  once `settleArrivals` resolves them.
- Fix lands with the reproduction test passing, and `pnpm check` green
  except the pre-existing, unrelated [[ANU-012]] map-balance failures.

## Resolution

**Root cause**: `resolveCombatAt` (`server/units.ts`) has always had three
outcomes — `"moved"` (undefended), `"hit"` (defender survives), `"kill"`
(defender dies) — and only `"moved"`/`"kill"` ever relocated the attacker to
`salCode` (via `arriveUnit`). A `"hit"` outcome ran `stayPut`, which cleared
the unit's transit stamps but deliberately left `sal_code` untouched at the
attacker's ORIGIN — a design choice from [[ANU-014]] ("the attacker stays
put") that was invisible back when `attackSuburb` resolved synchronously at
dispatch time: nothing had moved yet, so "staying put" and "never leaving"
looked identical. [[ANU-038]] then added real travel time and resolve-on-
arrival (`settleArrivals`) without revisiting that `"hit"` branch. The result:
a unit now visibly flies all the way to a defended destination (the client's
in-transit dotted-arrow animation, per ANU-038), and the instant
`settleArrivals` resolves a non-killing hit, `stayPut` snaps its `sal_code`
back to the origin it departed from minutes earlier — reading, to a player
watching the map, as exactly "half the dispatched stack teleports back to
source the instant it arrives." (The other "half" is whichever units in the
same stack land a `"kill"` or arrive against an already-cleared defender and
proceed normally — see issues/ANU-038.md's per-unit-in-order resolution
rule, confirmed again by the reproduction test below.) This also explains
why the user reported "half" specifically: `spec/units.test.ts`'s existing
rng-seeded fixtures already matched this exactly (a 2-attacker stack against
one tough defender: the first attacker's hit doesn't kill it, second
attacker still gets a turn against the same still-alive defender — so
historically neither advanced, but under ANU-038's travel animation that's
"both snap back," not "half").

**Reproduction**: `spec/units.test.ts`'s existing case ("settleArrivals
resolves combat against a defended destination on arrival") already set up
exactly this scenario (2 drones dispatched at 1 tough robot defender, rng
pinned so both land non-killing hits) but asserted the pre-fix (buggy)
behavior directly — `atDestination` empty, i.e. both attackers NOT at the
destination they just traveled to. That assertion was the bug encoded as a
passing test. Flipped it to assert the correct behavior instead (see below).

**Design decision — no `AskUserQuestion` tool was reachable in this
environment**, so this call was made directly rather than deferred, using
the same reasoning [[ANU-014]]/[[ANU-038]]'s own precedent points at: a unit
that survives a hit without dying or winning should remain AT the contested
destination, engaged, not retreat to its origin. This matches (a) the literal
semantics of "attacking" something you successfully reached and damaged
without being destroyed yourself, (b) [[ANU-038]]'s whole premise (units
travel for real, and "arriving" should mean something), and (c) the user's
own bug report, which explicitly frames staying engaged at the destination
as the correct behavior and snapping back as the defect. This is flagged
here for the coordinating session to confirm with the user post-hoc if
they'd rather the old retreat-on-hit semantics be restored as a deliberate
design choice instead.

**Fix** (`server/units.ts`'s `resolveCombatAt`): a `"hit"` outcome now runs
`arriveUnit.run(salCode, row.id)` — the same relocation statement `"moved"`/
`"kill"` already used — instead of the old `stayPut` (removed; it had no
remaining callers). The attacker's `OccupantUnit.sal_code` in the returned
outcome is now `salCode` (the destination), not the origin. A hit that
doesn't kill the defender now leaves both units occupying the same suburb,
contested — consistent with how a "moved" or "kill" arrival already places
the attacker there.

**Tests updated** (`spec/units.test.ts`): the rng-seeded "combat resolution
is deterministic" case now additionally asserts `result.attacker.sal_code`
equals the attack target, not the origin. The "settleArrivals resolves
combat against a defended destination on arrival" case (the direct
reproduction of this bug) now asserts both attackers end up AT
`ADJACENT_SAL_CODE` (not back at `SPAWN_SAL_CODE`) after a non-killing hit,
and are released from transit. Two WebSocket-level integration tests
(`spec/economy-broadcast.test.ts`'s `earnScrapByKilling`,
`spec/move-units-protocol.test.ts`'s kill-retry loop) previously re-dispatched
a surviving attacker from its original spawn suburb on every retry attempt,
relying on the old (buggy) "hit leaves the attacker at origin" behavior —
updated to track the attacker's actual current position (which, after a
survived hit, is now the target suburb) and dispatch each subsequent attempt
from there instead.

`pnpm check`: typecheck clean, 221/221 tests passing (28 test files). One
unrelated flake reproduces identically whether or not this fix is applied
(confirmed via `git stash`): `spec/persistence.test.ts`'s `afterAll` hook
intermittently exceeds its 10s timeout stopping spawned servers — this is
the same already-documented local-environment noise class [[ANU-032]]'s
Resolution describes ("a crashed, leftover `node server/index.ts` process...
not a CI-reproducible condition"), not a new regression; both of that file's
actual tests pass every time, only the cleanup hook times out. [[ANU-012]]'s
map-balance assertions no longer exist to fail (already resolved/deleted per
that issue's own Resolution), so the "9 pre-existing failures" baseline this
issue's Done-when section anticipated is itself stale — current `main` has
zero expected test failures other than this `persistence.test.ts` hook
flake.

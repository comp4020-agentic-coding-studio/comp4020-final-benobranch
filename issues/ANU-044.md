## Why

When two different players both have units standing in the same territory,
combat does not occur between their units at all. Instead, only one
player's units are ever treated as attackers/defenders against the
territory itself — once that player's "fight" resolves, that player begins
capturing the zone uncontested, completes the capture, and then the *other*
player's units start capturing it in turn, uncontested. This repeats
indefinitely: capture ownership just alternates between the two teams on a
loop, and no actual unit-vs-unit combat between the two enemy garrisons ever
happens.

Not yet root-caused. Two candidate areas, based on reading the code so far
without live reproduction:

- `server/units.ts`'s `resolveCombatAt` only ever resolves against "the
  single defender occupying the suburb longest" (`issues/ANU-014.md`'s
  documented design choice) — with 2+ distinct enemy owners garrisoned at
  once, it's unclear whether/how combat is supposed to pick between them,
  and this may be where N-way presence collapses into only ever fighting
  one side.
- `server/territory.ts`'s `settleSuburb` capture state machine filters
  "capturers" as anyone other than the suburb's registered owner
  (`occupantOwners.filter((o) => o.ownerPlayerId !== row.ownerPlayerId)`)
  and, in the 2+-capturers branch, treats it as **contested** (freezes
  progress) rather than resolving combat between the capturers themselves
  — but the observed behavior (one side completes a capture, then the other
  starts) suggests something is letting the capturer count collapse to 1
  at a time instead of staying at 2+ for as long as both garrisons are
  actually present, which would point back to units not actually being
  destroyed/engaged between the two non-owner players.

## Done when

- Root cause identified: why doesn't `resolveCombatAt`/the arrival or
  occupancy path ever pit two non-owning players' units against each other
  when both are garrisoned in the same territory at once?
- A `spec/units.test.ts`/`spec/combat.test.ts`/`spec/capture.test.ts` case
  reproduces the loop: two players' units both present in a
  neither-owns-it (or one-owns-it) territory at the same time results in
  actual combat between them, not a silent alternation of uncontested
  captures.
- Fix lands with the reproduction test passing, and `pnpm check` green
  except the pre-existing, unrelated [[ANU-012]] map-balance failures.

## Resolution

**Root cause: a missing feature, not a logic bug in either candidate area
named above.** Confirmed with two throwaway repro tests run directly
against `server/territory.ts`/`server/units.ts` (an in-memory SQLite
connection, same pattern as `spec/capture.test.ts`) before writing any fix:

1. `server/territory.ts`'s `settleSuburb` (ANU-017) is working exactly as
   designed: with 2 distinct non-owner occupants present, `capturers.length
   === 2` correctly takes the contested branch and freezes
   `capture_accumulated_ms` — verified it never advances across repeated
   `settleCaptures` calls while both garrisons stay present. ANU-017's
   contest-freeze was never the bug. `selectOccupancyGroups`'s lack of a
   `destination_sal_code IS NULL` filter (the thing the issue asked to
   double-check) also isn't the bug in practice — a unit mid-transit
   contributing a phantom "occupant" group at its *origin* suburb for one
   settle pass is a real, separate inconsistency (worth fixing some day, it
   means the origin suburb can read one group too many while a unit is
   departing) but it doesn't explain the alternating-capture symptom, since
   that phantom occupant disappears by the very next settle, not after an
   entire capture duration.
2. `server/units.ts`'s `resolveCombatAt` is also working as ANU-014
   documented: "single defender, by spawn order" is a deliberate design
   choice for the *arrival* combat case, not an N-way-presence bug.
3. **The actual gap: combat in this codebase only ever resolved at the
   INSTANT a unit's travel time elapsed** (`settleArrivals`, ANU-038) or
   via the dead single-unit `attackSuburb`/`moveUnit` primitives (confirmed
   still unreachable from the live WebSocket handler — `server/index.ts`
   has no `message.type === "moveUnit"`/`"attackSuburb"` branch; only
   `placeUnit` and the bulk `moveUnits` are wired up, matching ANU-027/
   ANU-038's docstrings). Once two enemy garrisons both finished arriving
   and were simply standing in the same suburb (`sal_code` equal,
   `destination_sal_code` null, nobody "arriving" anymore), **nothing in
   the entire codebase ever resolved combat between them again, for as
   long as they both stood there** — confirmed directly: placing two
   enemy drones in a neutral suburb and calling `settleCaptures` in a loop
   showed `contestingPlayerIds` staying frozen and non-empty forever, with
   zero units ever destroyed, while `settleArrivals` had nothing to settle
   (no in-transit units). The reported "alternates uncontested" shape is
   what this looks like in live play: the contest correctly freezes while
   both stand there, but since neither side's units were ever actually at
   risk, the practical experience was "my garrison + their garrison sit
   there forever, then eventually someone regroups/retreats, and whoever's
   left just finishes capturing uncontested" — repeatable by either side,
   reading as an alternating loop. This is the "missing feature, not a
   one-line bug" case the issue flagged as a real possibility.

**Design decision — flagged, not confirmed via `AskUserQuestion`**: this
project's convention (ANU-014/ANU-017/ANU-038 precedent) is to confirm a
non-obvious combat-rule decision like this with the user before building on
it, and this is exactly that kind of decision (a genuine new mechanic, not
a one-line bug fix, per the task brief's own flag). However, no
`AskUserQuestion`-equivalent tool was available in this session's toolset
(checked explicitly before implementing) — auto mode's guidance is to make
the reasonable call, note the assumption, and keep working rather than
block on a question with no way to actually ask it, so that's what this
Resolution does: the decision and reasoning below are a single agent's
judgment call, not a user-confirmed one, and the coordinating session
should treat this as the item most worth a real human sign-off before
merging, same spirit as flagging an unconfirmed balance call.

Added a new periodic combat-resolution pass — `server/units.ts`'s
`settleGarrisonCombat`, same settle-lazily-at-read/broadcast-time shape as
`settleArrivals`/`territory.ts`'s `settleCaptures` (ADR 0001: no armed
per-suburb timer) — rather than changing `settleSuburb`'s contested-freeze
semantics, which stay exactly as ANU-017 specified (frozen progress is
still correct while a contest is unresolved; it's just no longer a
permanent state once `settleGarrisonCombat` is also running). The
alternative considered and rejected: folding combat resolution into
`territory.ts`'s `settleSuburb` itself — rejected because combat is a
units.ts concern (stats, rng, scrap credit, the existing `resolveCombatAt`
primitive) and `territory.ts` has no rng/scrap dependencies today; mixing
them would make `settleSuburb` depend on `units.ts` and complicate the
clean two-file split the four parallel-worktree systems issues
(ANU-013/014/015/017) established.

**`settleGarrisonCombat(lobbyId)`** (`server/units.ts`): for every suburb
with 2+ distinct owners among its *stationary* (non-transit) occupants, runs
one round where each present owner, in deterministic longest-present-first
order, gets one attack via the existing single-defender `resolveCombatAt`
(same damage-variance rule, same `scrapPerKillMultiplier` hook, same
occupancy re-read before each owner's turn so a kill earlier in the same
round correctly ends the round early). One round per call, matching
`settleArrivals`'/`settleCaptures`'s existing per-call-does-one-pass
convention — a sustained stand-off plays out as a continuing trade of hits
across ticks, not an instant wipe. Deliberately reasons from **physical
presence** (any 2+ distinct owners with stationary units in the suburb),
not from `territory.ts`'s "capturers" definition (which excludes the
suburb's registered owner) — this is what makes a suburb's own defending
owner fight back against a lone invader too, not sit passively while a
capture ticks up against them (case 4 of ANU-017's visual spec: "a player
owns a zone and another player is invading" — the owner was never
mechanically at risk before this fix, even though the visual already showed
them as being invaded).

**Wiring** (`server/index.ts`): `settleGarrisonCombat` is called everywhere
`settleArrivals` already was — the local `settleArrivals(lobbyId)` wrapper
function (called from `placeUnit`/`moveUnits` handlers and the ~1s
`arrivalTicker`) now also calls `units.settleGarrisonCombat(lobbyId)` and
folds its outcomes into the same occupancy/economy/captures broadcast; the
`hello` handler's own direct `units.settleArrivals(lobbyId)` call (used so
a reconnecting client doesn't see a stale in-transit unit) now also calls
`units.settleGarrisonCombat(lobbyId)` directly, for the same reason — a
reconnecting client shouldn't see two garrisons frozen in a stand-off that
should already have traded hits while nobody was connected to trigger a
tick.

**Tests**: `spec/units.test.ts` gains four `settleGarrisonCombat` cases
exercised directly against `server/units.ts` (same pattern as the file's
existing rng-seeded combat tests) — two garrisons trade hits across
multiple rounds until one is wiped out (not resolved in one call, and
not left as an unresolved stand-off); a single owner present is a no-op
(uncontested accrual stays `territory.ts`'s job); a suburb's own owner
fights back against a lone invader; N=3 distinct owners resolves without
error. `spec/capture.test.ts` gains one end-to-end integration test
pairing `settleGarrisonCombat` with `territory.settleCaptures` the same
way `server/index.ts` now does, reproducing the exact reported scenario
(two non-owning players' garrisons in a neutral suburb) and proving the
contest now actually resolves — one garrison is destroyed, the survivor is
left as the suburb's sole occupant, and `territory.ts` correctly transitions
back to uncontested accrual for them — rather than freezing forever or
alternating.

**`pnpm check`**: `tsc --noEmit` clean, `check:issues` clean (43 issues all
valid), and the full `vitest run` passes all 226 test-level assertions
across 28 files (34 of them in `spec/units.test.ts`/`spec/capture.test.ts`,
the new/updated files from this fix). `spec/map-balance.test.ts` (ANU-012's
former failure) is fully green (21/21) — ANU-032 already resolved ANU-012 by
removing the two stale assertions, so there is no longer a standing
ANU-012 failure to compare against; this branch introduces none either.
The one file-level failure in a full `pnpm vitest run` here,
`spec/persistence.test.ts`'s `afterAll` hook timing out trying to kill its
spawned child server process, is an artifact of *this coding session's own
sandbox* (process-kill actions are denied by the harness's workload-
protection guard in this environment, confirmed by independently hitting
the same denial via a bare `pkill` in this session) — not a code
regression: verified identical on this same worktree with the fix
`git stash`-ed out, and both of `spec/persistence.test.ts`'s actual
assertions pass every time, only the cleanup hook hangs. Flagging this
explicitly per `CLAUDE.md`'s "note it in an issue" convention rather than
silently treating it as `pnpm check` green — a CI run or any non-sandboxed
session should hit no such restriction.

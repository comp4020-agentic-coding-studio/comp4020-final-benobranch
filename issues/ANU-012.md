## Why

Commit `b4ef9bd` ("map.json: move the mega data center from Kingston to
Monash") moved a data center per direct user request without re-running
[[ANU-006]]'s balance search, and said so explicitly in its own message:
it "raises the worst-case soft-access ratio above the previously agreed 3.0
bound (spec/map-balance.test.ts will fail) and makes lobby sizes 10-12
spawn-infeasible under the current ring/separation constraints," and flagged
"follow-up tracked for whoever picks the rebalance back up" — but no such
issue was actually opened at the time. This is that issue, opened on
discovering `pnpm check` can't go green on a clean `main` checkout
independent of any other work in flight.

Confirmed independently while working ANU-011 (lobby→map wiring, unrelated
to map balance): a stock `main` checkout with no other changes fails 9
`spec/map-balance.test.ts` assertions (lobby sizes 5-12's recomputed
soft-access ratio no longer matches the baked value in `map.json`, and N=8
exceeds the agreed 3.0 worst-case bound). This is not something ANU-011 (or
any other open issue) should silently route around — it needs its own
tracked resolution.

## Done when

One of:
- The balance search (ANU-006's spike) is re-run against the current
  `map.json` (post-Monash-move) and the baked `ratio`/`scores` values in
  `spawn_table_by_lobby_size` are updated to match, restoring
  `spec/map-balance.test.ts` to green with no bound relaxed; or
- The user confirms the Monash placement should be reverted instead (the
  commit was explicit that this was deliberate, so don't revert without
  asking); or
- The 3.0 worst-case bound itself is deliberately revised upward (with the
  user's sign-off — it was "the previously agreed" bound per the commit
  message, not an arbitrary number) and `spec/map-balance.test.ts` updated
  to the new bound, not loosened silently.

Whichever path: `pnpm check` goes green against a clean `main` with no test
skipped, deleted, or loosened without an explicit decision recorded here.

## Notes

Not blocking per se — the rest of the test suite is unaffected, and the app
still runs — but it does mean `pnpm check` cannot currently go fully green
on `main`, which matters for the pre-push hook (docs/git-workflow.md rule 5)

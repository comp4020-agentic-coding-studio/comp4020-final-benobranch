title: pre-push hook checked the wrong worktree's HEAD, not the commit being pushed
status: done
type: harness
opened: 2026-11-02

## Why

Adapting a RefWhistle-style "don't ship an unchecked build" guard into
`.githooks/pre-push`: the hook should refuse a push to `main` unless
`pnpm check` has passed recently against the exact commit being pushed.

## Done when

The hook reads the commit actually named in pre-push's stdin
(`<local-ref> <local-sha> <remote-ref> <remote-sha>`) for `refs/heads/main`,
not `git rev-parse HEAD` of whatever branch the current worktree happens to
have checked out.

## Resolution

The first version compared the `CHECK_OK` marker's recorded sha against
`git rev-parse HEAD`. That's wrong in exactly the setup this project depends
on — multiple worktrees, each possibly on a different branch: `HEAD` in the
worktree running the hook is not necessarily the commit being pushed to
`main`. A hook running from a feature-branch worktree while pushing an
already-checked `main` sha would have been blocked for the wrong reason, and
worse, the inverse (pushing an unchecked sha while `HEAD` happened to match
some old passing run) could have slipped through.

Caught by asking a second model (via the `advisor` tool) to review the hook
before building the issue tracker on top of it, rather than by hitting it in
practice. Fixed by parsing `local_sha`/`remote_ref` out of the real stdin
loop and comparing the marker against that `local_sha` for
`refs/heads/main`, instead of `HEAD`. Verified with an isolated test repo
(`/tmp/hook-test`, not committed) exercising four cases: checked out on a
feature branch while pushing main's already-checked sha (now passes, was
previously comparing against the wrong sha); pushing an unchecked sha to
main (blocked, with the correct sha quoted in the error); a non-main push
(always passes through untouched); and a clean, fresh, matching marker
(passes).

Landed in `.githooks/pre-push` and documented in
[`docs/git-workflow.md`](../docs/git-workflow.md) rule 5.

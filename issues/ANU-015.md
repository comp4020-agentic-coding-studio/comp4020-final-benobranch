## Why

The user's own words: "implement factories to build troups (every player
starts with one in their spawn and can build more by using resources gained
by destroying enemy troups)". This is the second of four parallel systems
issues ([[ANU-013]] is the shared foundation this depends on; [[ANU-014]]
defines the unit types/costs this issue queues production of; [[ANU-016]]'s
skill tree later makes factories faster/cheaper via the perk hook ANU-013
defines). Scoped to the production mechanic itself, not the GUI control
that would let a player click "build" — per ANU-013's Notes, that's later
work once all four systems exist.

## Done when

- `server/factories.ts` (per [[ANU-013]]'s file-layout convention) owns a
  new `factories` table (lobby-scoped: id, `sal_code`, `owner_player_id`,
  a production queue/state) migrated as part of [[ANU-013]]'s single
  schema bump if that issue hasn't merged this table yet when this issue
  starts — otherwise add it here behind its own migration, coordinating
  with whichever of 013/015 lands first so there's only one
  `PRAGMA user_version` bump between them, not two colliding ones.
- **Spawn factory on kickoff**: the moment a lobby starts (same `startLobby`
  trigger [[ANU-013]] uses to auto-own spawn suburbs), each player gets
  exactly one factory, placed in their spawn suburb.
- **Building more factories — confirm with the user before locking in**
  (not specified by the user's request beyond "can build more"): where can
  a second factory be built — any suburb the player owns, or restricted
  further (e.g. must be adjacent to an existing owned factory)? And **does
  capturing a suburb destroy an enemy factory standing in it**, or does
  ownership of the factory itself change hands? Both flagged in
  [[ANU-013]]'s Notes as decisions for this issue specifically — get the
  user's sign-off (`AskUserQuestion`, same pattern as [[ANU-006]]/
  [[ANU-014]]) and document the chosen rule here before building the
  queue logic around it.
- A production queue: building a unit costs scrap (per [[ANU-014]]'s
  `unit_types.build_cost` in scrap) and takes time — using ANU-013's
  stored-timestamp rule (start time + elapsed time at read/broadcast,
  scaled by `GAME_TIME_SCALE`), not an in-memory timer that would reset on
  a machine restart. Queueing is a single synchronous handler (scrap-check
  + queue-write with no `await` between them), same reasoning
  `docs/adr/0001-persistence-and-realtime-stack.md` already applies to the
  bump handler and [[ANU-008]] applies to lobby-capacity joins — two
  near-simultaneous build orders against the same scrap balance must
  resolve consistently, not double-spend.
- When a queued unit completes, it's placed via [[ANU-013]]'s occupancy
  primitive (`placeUnit`) in the factory's suburb, owned by the factory's
  owner.
- Reads [[ANU-013]]'s perk hook for `factoryBuildSpeedMultiplier` and
  `factoryBuildCostMultiplier` (both default 1 until [[ANU-016]] gives a
  skill-tree node a way to change them) rather than hardcoding either —
  so the skill tree issue doesn't need to touch this file to have an
  effect.
- A broadcast of factory state (location, owner, current queue/progress)
  so clients watching the map can show build progress live, matching the
  brief's real-time bar (same ~1s target `spec/realtime.test.ts` already
  holds other broadcasts to).
- **GUI representation (map-drawable only, not player-controllable yet —
  see ANU-013's Notes)**: a pure function, e.g.
  `factoryVisual(factory) -> { icon, ownerColor, queueProgressFraction | null }`
  — covered by a `spec/` test for queued/idle/mid-build states, per
  `CLAUDE.md`'s no-manual-e2e rule.
- `spec/*.test.ts`: each player has exactly one factory at their spawn
  suburb immediately after `startLobby`; queueing a unit deducts the
  correct scrap (including with a non-1 build-cost multiplier passed via
  the perk hook, to prove the hook is actually read, not just present);
  two near-simultaneous queue requests against an insufficient-for-both
  scrap balance resolve to exactly one succeeding, not both or neither
  incorrectly; a completed queue item places a real unit via ANU-013's
  occupancy primitive; a production duration survives a process restart
  mid-build with correct elapsed progress (same style as
  `spec/persistence.test.ts`'s restart tests); `factoryVisual` output
  shape for each state.
- No regressions: full `pnpm check` green except the pre-existing,
  unrelated [[ANU-012]] map-balance failures.

## Resolution

**Two design calls confirmed with the user via `AskUserQuestion` before the
queue logic was built:**

1. **Where a second (and later) factory can be built: any suburb the
   player currently owns**, no adjacency-to-an-existing-factory
   restriction. Simpler than the adjacency-restricted alternative, and
   nothing in the user's original request implied expansion had to be
   contiguous.
2. **Capturing a suburb with an enemy factory in it TRANSFERS the factory
   to the capturing player** (ownership changes hands) rather than
   destroying it — including any in-progress build, which completes for
   the new owner. PLAN.md's "Bases, drones, skill tree" section amended to
   state both.

**`server/factories.ts`** (per ANU-013's file-layout convention) owns the
production queue against the `factories` table ANU-013's v5 migration
already created — no new migration needed here, since that table (`id`,
`lobby_id`, `sal_code`, `owner_player_id`, `queued_unit_type_key`,
`queue_started_at`) already has everything this issue needs. One queue
slot per factory (the schema has no room for more than one in-flight
build), so `queueUnit` rejects a second request at an already-busy factory
with `"busy"`.

**Spawn factory on kickoff** (`spawnFactories`, called from `index.ts`'s
`startLobby` handler immediately after `territory.assignSpawnOwnership`):
reads each player's just-assigned spawn suburb back from
`suburb_ownership` directly, rather than recomputing the spawn table a
second way — recomputing it was exactly the capacity-vs-player-count bug
ANU-013's Resolution found and fixed in `territory.ts` (a 12-capacity
lobby started with only 4 players must use the 4-player spawn ring, not
the first 4 entries of the 12-player ring), and this module must not
reintroduce that bug by guessing spawns independently.

**Building an additional factory** (`buildFactory`): flat
`FACTORY_BUILD_COST_SCRAP` (20 — not specified by the user's request
beyond "can build more," chosen as a 5-10x multiple of a single base
unit's build cost so expanding production capacity is a meaningful
economic investment, not a trivial add-on) deducted synchronously, checked
against suburb ownership and "no factory already there." Deliberately NOT
scaled by `factoryBuildCostMultiplier` — that perk is read elsewhere for
the cost of the *units* a factory produces (what issues/ANU-015.md's
"production queue" bullet actually names), and no node in ANU-016's roster
makes a new factory itself cheaper.

**Production queue** (`queueUnit`): a single synchronous handler — unit
type lookup, `requires_skill_node` gate (checked against the `skill_nodes`
table ANU-016 owns, so a gated variant row isn't buildable by everyone
before that issue lands), and a scrap deduction guarded by
`UPDATE ... WHERE scrap >= ?` with a `changes === 1` check — all with no
`await` in between, same reasoning `docs/adr/0001-persistence-and-realtime-stack.md`
already applies to the bump handler and `server/store.ts`'s `startLobby`/
`joinLobby` guards. Cost is `round(unit_types.build_cost_scrap *
factoryBuildCostMultiplier)`.

**Completion is settle(), not a timer**: `settle()` scans every factory in
a lobby and, for any whose `elapsedMs(queue_started_at) >=
build_time_ms / factoryBuildSpeedMultiplier`, calls `units.placeUnit` at
the factory's suburb for the factory's **current** owner (not whoever
queued it) and clears the queue. Called before every read/broadcast
(`getFactories`) and from a ~1s `unref()`'d `setInterval` in `index.ts`
that only ticks lobbies with a live connection — the ticker is a wake-up,
not the source of truth: it holds no build state itself, so a machine
sleeping through it (per `fly.toml`'s `auto_stop_machines`) loses nothing —
the next `getFactories`/`hello` call still computes correct elapsed
progress from the stored `queue_started_at` timestamp (ADR 0001's
stored-timestamp rule). "Current owner" is what makes the capture-transfer
rule correct: `transferFactoryOwnership` (called by ANU-017's capture
state machine once a capture completes) only updates
`factories.owner_player_id`, leaving any in-progress queue untouched —
`settle()` then completes that build for the new owner, verified directly
in `spec/factories.test.ts`.

**Broadcast**: a new `factories` protocol message (`lobbyId`,
`FactoryState[]` — `id`, `sal_code`, `ownerPlayerId`, `queuedUnitTypeKey`,
`queueProgressFraction`), sent on `startLobby`, on `buildFactory`/
`queueUnit`, on the ~1s ticker, and on `hello` (so a reconnecting client's
view isn't stale, same reasoning ANU-013's occupancy broadcast already
follows).

**`factoryVisual`** (`server/public/factory-visual.js`): a pure function
`(factory, ownerColor) -> { icon: "factory", ownerColor,
queueProgressFraction }` — one icon for every factory (ownership is color,
per ANU-013's convention, not a second icon), `queueProgressFraction`
passed through unchanged (`null` idle, `0` just queued, fractional
mid-build) so the caller distinguishes "no progress yet" from "nothing
queued." Covered by `spec/factory-visual.test.ts` for idle/just-queued/
mid-build/ownerColor-passthrough.

**Tests** (`spec/factories.test.ts`, direct import against
`openStore(":memory:")`, same boundary reasoning `spec/units.test.ts`/
`spec/perks.test.ts` use — no message carries a lobby member's scrap
balance back, so there's nothing to assert over the WebSocket protocol for
the economy checks): one factory per player at spawn after `startLobby`;
queueing deducts the correct scrap, including under a non-1
`factoryBuildCostMultiplier` (0.5x on a robot, chosen so the scaled cost is
an exact integer and the assertion isn't laundering a rounding
coincidence) to prove the hook is actually read; `"busy"`/
`"insufficient-scrap"`/`"not-owner"`/`"already-exists"`/`"locked"`
rejections; two near-simultaneous `queueUnit` calls against two idle
factories but scrap for only one unit resolve to exactly one succeeding
and a final scrap balance of exactly 0 (two factories, not one, so the
second request fails on scrap specifically rather than being
indistinguishable from a `"busy"` rejection); a completed build (forced by
backdating `queue_started_at`) places a real unit via `units.getOccupancy`
and clears the queue; `queueProgressFraction` scales correctly under
`factoryBuildSpeedMultiplier`; `transferFactoryOwnership` moves ownership
and preserves an in-progress build, which then completes for the new
owner; a skill-node-gated unit type is rejected until the node is
unlocked. `spec/factories-restart.test.ts` (process-spawn, same pattern as
`spec/territory.test.ts`'s restart test): a queued build survives a real
process restart with `GAME_TIME_SCALE=0.1` (robot's 3000ms design duration
stretched to a 30-real-second build, so it provably can't complete during
the brief restart window) and correct small elapsed progress, not reset or
lost. `spec/factory-visual.test.ts` covers the pure visual function.

**No regressions**: `pnpm check` — typecheck clean, `check:issues` clean,
118/127 tests pass. The 9 failures are exactly [[ANU-012]]'s pre-existing,
already-open `spec/map-balance.test.ts` failures (same failures present on
`main` before this branch — unrelated to factories).

## Notes

Depends on [[ANU-013]] (occupancy primitive, scrap column, perk hook,
spawn-ownership-on-kickoff trigger, file-layout convention) and reads
[[ANU-014]]'s `unit_types` build costs, but doesn't implement combat or
movement itself — scoped to stay out of `server/units.ts` so the two can
run as parallel worktrees.

**For [[ANU-017]]**: when its capture state machine completes a capture of
a suburb, it must call `server/factories.ts`'s
`transferFactoryOwnership(lobbyId, salCode, newOwnerPlayerId)` if a
factory stands there — per this issue's confirmed rule, capture
*transfers* a factory rather than destroying it, including any in-progress
build (which then completes for the new owner). This issue does not call
that function itself anywhere (there's no capture logic to trigger it
yet) — it only exists and is tested directly
(`spec/factories.test.ts`) against the behavior ANU-017 needs to invoke.

**For [[ANU-016]]**: a unit type's `requires_skill_node` column (already
read by `queueUnit`, rejecting with `"locked"` if the player hasn't
unlocked it via the `skill_nodes` table) is the gate a gated variant row
needs — no change to this file required for that to work once ANU-016
adds such rows.

id: ANU-034
title: Unit markers fully overlap at a tile when mixed - fan out by archetype, show live counts, flash on loss
status: done
type: feature
opened: 2026-11-05

## Why

[[ANU-024]] gave drone/robot markers distinct icon artwork, but
`renderUnits` (`server/public/map.js`) still draws every occupant at a
suburb at the exact same `geo.label_point` coordinate (no index-based
offset). When a tile holds both a drone and a robot (or just several units
of mixed type), their `<g class="unit-marker...">` groups stack exactly on
top of each other — only the last-drawn one is visible, so the player can't
tell at a glance that both archetypes are present.

The user likes the icon art itself but wants:
- Drone and robot icons to sit beside each other (not overlapping, not
  touching) when both are present at a tile.
- The count of each unit type at that tile shown as white text underneath
  its icon (e.g. "x15", "x12", "x3") — `suburb-detail-view.js`'s
  `countByType` grouping already exists for the sidebar's move panel, but
  nothing surfaces counts directly on the map.
- A losing side's count to flash red and jitter briefly when a unit of that
  type is destroyed at that tile, so combat outcomes are readable on the
  map itself without having to open the sidebar.

## Done when

- `renderUnits` groups occupants per `(sal_code, archetype)` instead of
  drawing one marker per individual unit, and lays out up to two
  archetype groups (drone/robot) side by side around `label_point` with a
  visible gap — never overlapping, never touching.
- Each archetype group shows its count as white text beneath the icon.
- When a group's count at a tile drops between one `occupancy` broadcast
  and the next (a unit of that type/tile was lost), the count label
  gets a transient CSS class (new `@keyframes`, following
  `map.css`'s existing `capture-stripe-pulse` convention: a modifier class
  toggled from JS, animation defined in `map.css`) that flashes red and
  jitters briefly, then returns to normal white. Detected by diffing the
  previous per-(sal_code, archetype) count against the new one client-side
  in `app.js`'s `occupancy` handler — no server/protocol change, since
  individual kill events aren't broadcast (see Notes).
- Clicking either icon in a fanned-out pair still resolves to a sensible
  unit selection for the sidebar (doesn't need to be a specific individual
  unit id the way single-unit selection worked before, since the user-facing
  concept is now "this archetype's group at this tile" — confirm against
  `sidebar.js`'s `selectFromMap`/`currentSelection` handling).
- `pnpm check` green (typecheck + `spec/*.test.ts`) — per `CLAUDE.md`'s
  current cost-discipline rule, no manual browser verification required for
  this pass.

## Resolution

Added `server/public/unit-marker-layout.js`'s `layoutUnitMarkers()` — a pure
function (no DOM, same testable-without-jsdom convention as
`capture-visual.js`/`unit-visual.js`) that groups `OccupantUnit`s by
`(sal_code, ownerPlayerId, archetype)`, assigns each group a stable
`offsetIndex`/`groupCountAtSalCode` for fan-out layout, and compares each
group's count against a caller-supplied map of the previous render's counts
to flag `lostAUnit`.

`renderUnits` (`map.js`) now calls this instead of drawing one marker per
individual unit: it keeps the previous call's per-group counts in module
state (`unitGroupCounts`, reset in `unmountMap` so switching lobbies can't
misfire a flash against stale counts), and positions each group's icon by
centering the whole row of a suburb's groups on `label_point` and offsetting
by `index * (UNIT_MARKER_SIZE + UNIT_GROUP_GAP)` — a single group still
lands exactly on `label_point`, matching the old layout exactly when there's
nothing to fan out. Each group gets an SVG `<text>` count label
(`.unit-marker__count`, white, sized in the same map/SVG user-unit space as
`UNIT_MARKER_SIZE`) beneath its icon; `lostAUnit` toggles the
`.unit-marker__count--lost` modifier class, which plays a new one-shot
`unit-count-lost` `@keyframes` (map.css) — a red/white fill flash plus a
horizontal jitter — following the existing `.capture-stripe--pulsing`
convention of a JS-toggled class driving a CSS-defined animation. The click
handler's dataset (`unitId`/`salCode`) is unchanged in shape; a group's
`sampleUnitId` (one representative unit) stands in for what used to be a
single unit's own id, so `sidebar.js`'s existing `selectFromMap`/
`currentSelection` handling needed no change.

No protocol change: loss detection is entirely a client-side diff of
successive `occupancy` broadcasts against `unitGroupCounts`, never a
server-sent kill event (see the original Notes below — `AttackOutcome`'s
`"kill"` outcome stays server-internal).

13 new tests in `spec/unit-marker-layout.test.ts` cover grouping,
stable ordering, per-suburb isolation, `inTransit` propagation, and the
loss-detection edge cases (never-seen group, unchanged/grown count, and a
group that disappeared entirely not being misread as a loss on reappearance).
`pnpm check` green (203 tests across 27 files) against a locally running
instance; per `CLAUDE.md`'s cost-discipline rule, not re-verified by driving
a browser.

## Notes

Individual unit death is only observable client-side by diffing successive
`occupancy` broadcasts (`OccupantUnit[]` snapshots) — `server/units.ts`'s
`AttackOutcome` (`"kill"` outcome, `destroyedUnitId`) is computed
server-side but never sent to clients today, only used internally to decide
whether to also push an economy update. Count-diffing needs no protocol
change; exposing kill events directly would.

## Why

The user wants a rare, high-impact weapon: an EMP that disables an enemy (or
any) territory's economy for a while, rather than fighting for it directly.
Confirmed with the user via AskUserQuestion before writing this issue:

1. **Delivery**: the EMP is a real `unit_types` row, auto-produced by
   factories once its skill-tree node is researched, and dispatched exactly
   like a drone/robot via the existing "Move units" panel (`moveUnits` ->
   `startTransit` -> `settleArrivals`, [[ANU-038]]) — no new launch message,
   no new movement primitive. Arriving at its destination is what triggers
   the blackout instead of combat.
2. **Arrival always detonates.** An EMP's arrival bypasses `resolveCombatAt`
   entirely — it never fights a defender, never dies on arrival, always
   applies the blackout to the destination regardless of who or what is
   garrisoned there, then the EMP unit itself is deleted (consumed). This is
   a deliberate asymmetry from every other unit type's arrival.
3. **Fragile only while idle, not in transit.** The user was explicit: *"It
   shouldn't be able to be destroyed when sent to a territory. However, if a
   player attacks a territory that has EMPs sitting idle in it (just came
   out of the factory), they should be very fragile."* So:
   - An EMP that is **in transit** (dispatched, `destinationSalCode` set)
     can't be intercepted or destroyed before it arrives — matching point 2,
     arrival is guaranteed to detonate.
   - An EMP **sitting at its home suburb** (just produced, not yet
     dispatched) is a normal occupant and defends like any other unit if
     that suburb is attacked before it ships out — just with a very low
     health stat (see Done When) so it dies to almost any hit.
4. **Effect scope**: only that territory's factory production and data
   center TFLOPS contribution are disabled for the duration. Capture
   progress, combat, and unit movement at that territory are **not**
   affected by an active EMP — this is an economic blackout, not a shield or
   a freeze on the fight for the zone.
5. **Re-strike**: a second EMP landing on an already-EMP'd territory
   refreshes the duration to the full 20 minutes from that moment, rather
   than stacking additively or being wasted.
6. **Research gate**: a new standalone root node in the skill tree (no
   prerequisite, alongside the existing six roots), gating a new `emp`
   `unit_types` row — same `requires_skill_node` mechanism
   `seedSkillGatedUnitTypes`/`advanced-drone`/`advanced-robot` already use,
   not a new gating mechanism.
7. **Tuning** (a value had to be chosen, same "write down why" precedent as
   every other duration in this codebase — `CAPTURE_DURATION_MS`,
   `DRONE_SPEED`/`ROBOT_SPEED`, the skill node base research times):
   - **Research**: 5 minutes (300,000ms) base research time at 1x TFLOPS
     speed — by far the longest node in the tree (current longest is
     `advanced-drone`/`advanced-robot` at 45s), matching "very hard to come
     by." Same `speedMultiplier(tflops)` curve speeds it up as every other
     node.
   - **Factory build time**: 5 minutes (300,000ms) per unit, once unlocked —
     by far the longest build in the tree (current longest is robot at 2
     minutes), so even a teched-up player can only produce one every few
     minutes per factory.
   - **Blackout duration**: 20 minutes (1,200,000ms) per the user's
     instruction, as a named constant with the same "a value had to be
     chosen" comment convention, not a magic number inline.
   - **EMP combat stats** (only relevant while idle, pre-dispatch, per point
     3): health 1 (dies to any hit, including a 20%-under-rolled drone hit),
     damage 0 (it's a payload, not a combatant — it never meaningfully
     fights back if attacked while idle). `scrap_value`: a small amount
     (this issue's call during implementation, consistent with the existing
     scrap-economy convention) credited to whoever kills an idle one.
     `movement_mode`: "fly" (same unrestricted-reachability rule as drones —
     an EMP should be launchable at any territory, matching "launchable to
     any territory" in the user's request, not road-adjacency-gated like a
     robot — note [[ANU-047]] is in flight capping drone fly-range to 5 hops
     for balance; if that lands first, decide during implementation whether
     the EMP shares that cap or stays unrestricted given how rare/slow it
     already is). `speed`: this issue's call — reusing `DRONE_SPEED` is a
     reasonable default since there's no stated reason for an EMP to fly
     slower or faster than a drone.

## Done when

**Server:**

- `server/store.ts` migration v11 adds nothing new to `units`/`unit_types`
  schema beyond what already exists (`destination_sal_code`/`move_started_at`
  on `units`, `speed`/`requires_skill_node` on `unit_types` already cover an
  EMP's transit needs) — only a new `suburb_ownership` blackout state is
  schema-new: two columns, `emp_active_until` (TEXT, nullable) or the
  stored-timestamp-pair equivalent (`emp_started_at` + fixed duration,
  whichever shape settles more naturally against ADR 0001's "stored
  timestamp, not a running timer" rule — this issue's call, document the
  choice in the migration's comment same as every prior migration does).
  Plain `ALTER TABLE ... ADD COLUMN`, not the rebuild-via-new-table dance
  ([[ANU-023]]'s DROP COLUMN quirk doesn't apply to an addition).
- A new `unit_types` row, `"emp"`, seeded idempotently alongside
  `seedBaseUnitTypes`/`seedSkillGatedUnitTypes`'s existing `ON CONFLICT ...
  DO UPDATE` pattern (own small seed function, e.g. in `server/units.ts` or
  co-located with the new EMP module below — this issue's call), gated by
  `requires_skill_node: "emp-research"` (or equivalent id, matching the new
  skill node below). Stats per the Why section's Tuning: health 1, damage 0,
  speed = `DRONE_SPEED` (reused, not duplicated), movement_mode "fly",
  build_time_ms 300_000, a documented `scrap_value`.
- A new node in `server/public/skill-tree-nodes.js`'s `SKILL_NODES` array:
  `prerequisiteId: null`, `baseResearchTimeMs: 300_000`, `effectKind:
  "structural"` (same kind as `advanced-drone`/`advanced-robot` — it gates a
  unit type, not a perk multiplier), a real icon (reuse an existing
  `icons/skills/*.png` rather than sourcing a new asset — this issue's call
  which one reads as "EMP"-appropriate, e.g. a reused chassis/fab icon;
  sourcing a brand-new pixel-art asset is out of scope), `name`/`description`
  describing the unlock, `effectLive: true` (the gate has a real, live
  effect the moment this issue ships — the new unit type).
- `server/units.ts`'s `settleArrivals`/`resolveCombatAt` path: an arriving
  unit whose `unitTypeKey` is `"emp"` takes a **new branch**, checked before
  the existing defended/undefended combat logic — it never calls into
  `resolveCombatAt`'s combat resolution. On arrival it:
  - Deletes the EMP unit itself (consumed).
  - Writes the blackout state (`emp_active_until`/equivalent) onto
    `suburb_ownership` for the destination `sal_code` in this lobby, set to
    `now + EMP_BLACKOUT_DURATION_MS` (or the started-at equivalent) —
    **overwriting** any existing still-active blackout there (point 5's
    confirmed refresh-not-stack rule), regardless of current ownership
    (an EMP can land on a neutral or even unowned suburb, matching "any
    territory").
  - Returns a new `AttackOutcome` variant (e.g. `{ outcome: "emp-detonated";
    sal_code }`) distinct from `moved`/`hit`/`kill`, so
    `index.ts`'s relay logic and `spec/*.test.ts` can assert on it
    specifically rather than overloading `"moved"`.
  - This also applies to the **non-arrival** instant primitives
    (`attackSuburbImpl`/`moveUnit`) only if they're ever reachable for an
    `"emp"` unit type — per [[ANU-038]]'s note these are dead code from the
    live protocol (unreachable since [[ANU-027]]), so no change is needed
    there beyond not breaking their existing tests; don't add EMP-specific
    branches to code nothing can reach.
- `server/factories.ts`'s `settleFactory`/`toFactoryState`: a factory
  standing on a suburb with an active (unexpired) EMP blackout does not
  advance or complete any production cycle — `settleFactory` checks the
  suburb's blackout state (reading the same `suburb_ownership` columns,
  likely via a small new accessor on `server/territory.ts`, e.g.
  `isEmpActive(lobbyId, salCode)`, rather than a second ownership query
  inline) before its existing per-type elapsed-time check, and simply skips
  settling that factory's cycles while blacked out. A cycle's progress is
  **frozen, not reset** — matching the capture pause/resume precedent
  (`backdatedStart`): the stored `cycle_started_at` timestamp needs the same
  elapsed-time-excluding-blackout treatment capture's pause does, so a
  factory doesn't instantly complete every frozen cycle's worth of elapsed
  wall-clock time the moment the blackout lifts. Exact mechanism (stop/
  resume via `backdatedStart`-style bookkeeping vs. a stored "blackout
  started" offset) is this issue's call — document the chosen approach in a
  comment, same "a design choice was made, here's why" precedent as the
  Tuning section above.
- `server/tflops.ts`'s `getTflops`: a data-center suburb with an active EMP
  blackout contributes 0 TFLOPS to its owner's sum for the duration (checked
  the same way `settleFactory` above checks blackout state) — no persisted
  TFLOPS to unfreeze here since TFLOPS is already a live-computed sum, not
  an accrued balance ([[ANU-019]]), so this is just a filter on the existing
  per-suburb loop, not a settle/resume mechanism.
- Capture (`server/territory.ts`) and combat at a blacked-out suburb are
  **unaffected** — per point 4, no change needed to `settleSuburb`/
  `settleCaptures`/`resolveCombatAt` for a non-EMP unit's ordinary arrival
  there. Explicitly confirm (via a `spec/territory.test.ts` case) that a
  capture in progress at a blacked-out suburb keeps accruing normally.
- `server/protocol.ts`: `LobbyState.ownership`-adjacent broadcast needs the
  blackout state visible to clients — simplest fit is a new sparse field on
  `LobbyState` (e.g. `empActiveUntil: Record<string, string>`, sal_code ->
  ISO expiry timestamp, absent/sparse for suburbs with no active blackout,
  same sparse-map convention `ownership` itself uses) rather than a new
  message type, since this is suburb-scoped state that belongs alongside
  ownership on every broadcast a client already receives. Document why this
  rides on `LobbyState` rather than becoming a fourth per-suburb broadcast
  type (`captures`/`occupancy`/`factories` precedent) — this issue's call,
  but the existing `captures` message (sparse, suburb-keyed) is the closer
  precedent than inventing a new message shape.
- `server/index.ts`: `settleArrivals`'s relay logic broadcasts `lobbyState`
  (not just `occupancy`) when an `"emp-detonated"` outcome is present, since
  that's what carries the new blackout field — same "relay the side effects
  a synchronous outcome always has" pattern the existing kill-credits-scrap/
  captures-settle branches follow.

## Notes

Confirmed with the user via AskUserQuestion (this session, before writing
this issue):

1. Delivery reuses the existing `moveUnits` dispatch/travel-time/in-transit-
   arrow system ([[ANU-038]]) rather than a new launch primitive — an EMP is
   just another `unit_types` row from the dispatch system's point of view,
   with special-cased arrival behaviour.
2. An EMP always detonates on arrival, bypassing combat resolution entirely
   — it's a guaranteed-delivery payload, not a combatant that could lose a
   fight at the destination.
3. An EMP cannot be destroyed while in transit (matching point 2 — arrival
   always succeeds), but is very fragile (health 1) while sitting idle,
   not-yet-dispatched, at its home suburb — the user's own distinction
   between "sent to a territory" (safe) and "sitting idle in it, just came
   out of the factory" (very fragile).
4. The blackout only disables that territory's factory production and data
   center TFLOPS contribution — capture progress and combat there continue
   normally, this is not a broader "zone goes offline" shield.
5. A second EMP landing on an already-blacked-out territory refreshes the
   duration to the full 20 minutes rather than stacking or being wasted.

Research node placement (new standalone root, no prerequisite) and the
5-minute research/build tuning tier were also confirmed via
AskUserQuestion. The EMP's own `speed`/`scrap_value`/exact skill-node icon
and id, and the exact mechanism for pausing/resuming a frozen factory
production cycle across a blackout window, are left as implementation-time
calls per the Done When section above — document whichever choice is made
the same way every other tuning constant in this codebase already is.

This depends on [[ANU-038]]'s travel-time dispatch path (`moveUnits`/
`settleArrivals`) and [[ANU-016]]/[[ANU-019]]'s skill-tree research
machinery, both merged (`status: done`). [[ANU-047]] (drone range cap) is a
separate, independent in-flight issue noted above only because it touches
the same "fly" movement_mode reachability rule an EMP reuses.

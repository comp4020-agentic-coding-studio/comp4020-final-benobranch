## Why

Running `pnpm check` against the actual fresh-container environment CI uses
(the repo has been private, so CI's `check`/`deploy` jobs have never actually
run — `gh run list` shows every run so far as `skipped`) surfaced real,
reproducible failures, not the local dev-server flakiness it first looked
like. Both turned out to be already-diagnosed, still-open issues that this
session hadn't read first: [[ANU-012]] (map-balance) and [[ANU-026]]
(robot health) had independently traced the exact same two root causes
earlier, in sibling worktrees, and left them open pending a decision. This
issue is the decision-and-close pass on both, not a new discovery:

- [[ANU-026]]: `spec/economy-broadcast.test.ts`'s "hello yields a
  unitCatalog with the real seeded drone/robot stats, not placeholders"
  asserted `robot: health 6`, but `server/units.ts`'s `seedBaseUnitTypes`
  seeds `10`. Traced to commit `9a2b164` ("updated robot health") — a bare,
  undocumented direct commit to `main`, no issue or ADR behind it, which
  also leaves [[ANU-014]]'s documented "flat 2x ratio robot-over-drone"
  design invariant stale against the current seed values.
- [[ANU-012]]: `spec/map-balance.test.ts`'s two per-lobby-size assertions
  (`recomputed soft-access ratio matches the baked value`, `no spawn's
  power access exceeds the agreed worst-case bound`) failed for every lobby
  size. Traced to commit `b4ef9bd` ("move the mega data center from
  Kingston to Monash"), an explicit, documented user decision: "direct user
  request, no rebalancing -- raises the worst-case soft-access ratio above
  the previously agreed 3.0 bound... deliberately left as-is."

## Done when

`pnpm check` passes clean against a freshly built Docker image (`docker build
-t app .` + `docker run` with a throwaway `/data`, same as `checks.yml`), not
just against a long-running local dev server.

## Resolution

Removed the single failing assertion from `economy-broadcast.test.ts` (the
file's other two tests still pass and were left alone), and removed the two
failing per-lobby-size `it`s from `map-balance.test.ts` (the file's
existence/separation/remainder checks still pass and were left alone).

Explicit instruction from the user was to delete both without first fixing
the underlying drift, to unblock getting a live server deployed for testing.
That leaves two follow-ups genuinely open, for whoever picks unit/map
balance back up:

- decide whether `robot: health 10` is the real intended value (and update
  [[ANU-014]]'s "flat 2x ratio" invariant to match, since 10 vs. drone's 3 is
  no longer 2x), or revert to 6
- re-run the spawn-balance search against the Monash data center placement
  b4ef9bd introduced, since N=10-12 were noted as spawn-infeasible under the
  map's current ring/separation constraints at that placement

Also found and fixed in the same pass, as local-environment noise rather
than real bugs (neither needed a test change): a long-running local dev
server on port 8080 had accumulated enough stale WebSocket/DB state to cause
`spec/skill-tree-protocol.test.ts` timeouts that don't reproduce against a
fresh server or in CI's throwaway container; and a crashed, leftover
`node server/index.ts` process was squatting on `spec/persistence.test.ts`'s
hard-coded port, which is also not a CI-reproducible condition.

## Notes

This is the "corrections belong in the harness" case the brief asks
`PROCESS.md` to show: the fix is these two deletions plus this issue
recording why, not a silent edit or a retry loop.

Also worth recording against itself: this issue initially re-investigated
both root causes from scratch instead of first checking whether `ls issues/`
already had them — [[ANU-012]] and [[ANU-026]] turned out to already
document exactly this, opened 2026-11-02 and 2026-11-04 respectively. Fixed
by closing both with resolutions pointing here, rather than leaving three
overlapping issues on open/done with no cross-links. The actual lesson for
`CLAUDE.md`'s cost-discipline section: "only read the specific issue(s) the
session is working on" is right for avoiding a full-backlog survey, but a
session hitting a `pnpm check` failure should still grep `issues/*.md` for
the failing test's name before assuming it's new.

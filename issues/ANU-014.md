## Why

The user's own words: "implement different troups (drones that can fly
across enemy zones to attack zones the player is not connected to, robots
that can only attack neighouring zones but do more damage/have more
health, etc)". This is the first of the four parallel systems issues
(see [[ANU-013]], which this depends on for the occupancy primitive,
player colors, and scrap balance this issue spends/earns against) — the
unit types and their rules, not yet the UI to order one built (that's
[[ANU-015]]'s factories) or the skill tree that unlocks better versions
(that's [[ANU-016]]).

Two unit archetypes at minimum, matching the user's description exactly:
- **Drones**: fly — can attack a suburb the attacking player has no
  road-adjacent corridor to (ANU-013's occupancy model doesn't require
  adjacency to place a unit; this issue is what actually uses that to mean
  "ignores corridor/adjacency for drones specifically"). Lower
  health/damage than robots as the tradeoff for that reach.
- **Robots**: ground — can only attack a suburb road-adjacent (PLAN.md's
  existing adjacency definition: shares a *road* connection, not just a
  touching border) to one the player currently owns. Higher health/damage
  than drones as the tradeoff for the range restriction.

## Done when

- `server/units.ts` (per [[ANU-013]]'s file-layout convention) owns unit
  stats and combat resolution, reading/writing the `units` and
  `unit_types` tables ANU-013 migrated and seeded as placeholders.
- `unit_types` has real rows for at least drone and robot (health, damage,
  build cost in scrap, build time), replacing ANU-013's placeholders —
  stats don't need to be perfectly tuned, but must be genuinely distinct
  (drone: lower health/damage, any-suburb targeting; robot: higher
  health/damage, adjacency-restricted targeting) so the tradeoff is real,
  not cosmetic.
- **Combat resolution rule — confirm with the user before locking in**
  (flagged, not decided, in [[ANU-013]]'s Notes): deterministic
  (attacker stats vs. defender stats, no randomness) or with a random
  element. Pick one, document the choice and reasoning here in the
  Resolution, and get the user's sign-off the same way [[ANU-006]] did for
  its balance-bound call (`AskUserQuestion`) before building the GUI on top
  of an unconfirmed rule.
- Attacking a suburb with units present resolves combat between the
  attacking unit(s) and whatever's defending (other units, and/or the
  suburb's defensive value if the owner has no units there — define
  explicitly what "undefended" means) using the chosen resolution rule;
  losing units reduce health/are destroyed and the destroying player's
  `scrap` balance (ANU-013's column) increases by an amount scaled by
  `scrapPerKillMultiplier` (ANU-013's perk hook, default 1 until
  [[ANU-016]] gives it a way to be anything else).
- Attack/move messages extend ANU-013's `placeUnit`/`moveUnit` protocol
  shapes rather than inventing parallel ones — add an `attackSuburb`
  message if move-into-occupied-suburb isn't already enough to express
  "attack," but keep the occupancy broadcast shape ANU-013 defined.
- Drone movement validation ignores corridor/ownership entirely (per the
  "fly across enemy zones" requirement); robot movement validation checks
  road-adjacency to an owned suburb using the existing `map.json` adjacency
  graph (same data [[ANU-010]]'s map rendering already loads).
- A unit's current position/health is visible in the map's occupancy
  broadcast (ANU-013's primitive) so [[ANU-017]]'s capture-contest logic
  and the eventual GUI can both read "who/what is standing in this suburb
  right now" from one source.
- **GUI representation (map-drawable, not yet player-controllable — see
  ANU-013's Notes on the GUI boundary)**: a pure function, e.g.
  `unitVisual(unit) -> { icon, facing/orientation if relevant, healthFraction }`
  distinguishing drone vs. robot at a glance (different icon/shape, not
  just a color — color is reserved for ownership per [[ANU-013]]), plus a
  simple state representation for "destroyed" (fade/remove) and "in
  transit" (drones specifically, since they can be mid-flight over
  territory they don't own) — covered by a `spec/` test asserting the
  function's output shape for each case listed, not a rendered screenshot
  (per `CLAUDE.md`'s current no-manual-e2e rule).
- `spec/*.test.ts`: drone attack succeeds against a non-adjacent,
  unowned-corridor suburb; robot attack against the same target is
  rejected; a robot attack against an adjacent owned-corridor suburb
  succeeds; combat resolution matches the confirmed rule exactly (if
  deterministic: same inputs always produce the same outcome, asserted
  directly); a kill credits scrap to the attacker scaled by the perk
  multiplier; `unitVisual` output for drone/robot/destroyed/in-transit.
- No regressions: full `pnpm check` green except the pre-existing,
  unrelated [[ANU-012]] map-balance failures.

## Resolution

**Combat resolution rule (confirmed with the user via AskUserQuestion):
random element**, not deterministic. Implementation: attacker damage =
`round(baseDamage * (0.8 + rng() * 0.4))`, floored at 1 so a hit is never a
complete whiff — a uniform +/-20% variance band around the attacker's base
damage. `rng` is injected into `createUnits(db, rng)` (defaulting to
`Math.random`) specifically so `spec/units.test.ts` can assert exact
outcomes under a seeded sequence and confirm the rng genuinely varies
results (not secretly deterministic regardless of what's injected).

Drone/robot stats (`seedBaseUnitTypes`, server/units.ts): drone
health 3 / damage 2 / build cost 2 scrap / build time 1500ms, robot
health 6 / damage 4 / build cost 4 scrap / build time 3000ms — a flat 2x
ratio robot-over-drone on both health and damage, wide enough that the
+/-20% variance band can't blur a drone hit into a robot hit's range,
in exchange for robot's adjacency-restricted movement.

**"Undefended" (`attackSuburb`'s target has no enemy unit)**: true
whenever no unit owned by anyone other than the attacker currently
occupies the target suburb — regardless of who *owns* that suburb
(neutral, the attacker's own, or even enemy-owned with no garrison).
Attacking an undefended suburb just relocates the attacking unit there
(`outcome: "moved"`); capturing *ownership* of it is [[ANU-017]]'s job, not
this issue's. Combat only ever resolves against the single defender
occupying the suburb longest (`spawned_at`-then-`id` order) — not a
multi-defender melee, since nothing in the brief asked for simultaneous
multi-unit combat and a single deterministic-order defender keeps the rng
tests reproducible.

Movement-mode reachability (shared by `moveUnit` and the new
`attackSuburb` message — same rule, not two): a drone (`movement_mode:
"fly"`) can reach any suburb; a robot (`"ground"`) can reach only a suburb
it already owns, or one road-adjacent (per PLAN.md's share-a-road
definition, via `scripts/map/data/map.json`'s baked edge list) to one it
owns. `placeUnit` deliberately stays unrestricted by either rule — see
Notes below, this was a late correction after the advisor flagged it.

A kill deletes the defender's `units` row, credits
`defenderType.build_cost_scrap * scrapPerKillMultiplier` (rounded) scrap
to the attacker via `lobby_members.scrap` (ANU-013's column, ANU-016's
perk hook), and the attacking unit advances into the suburb it just
cleared.

**In-transit GUI state**: `OccupantUnit` gained optional
`destinationSalCode`/`moveStartedAt` fields (the `units` table already had
the columns, unused until now). Nothing in this issue's scope sets them —
every move/attack completes instantly, there's no travel-time system yet
— so `unitVisual`'s `"in-transit"` branch exists but is currently
unreachable in practice; a future issue adding travel time is what
populates those fields for real. `unitVisual` (server/public/unit-visual.js)
is a pure function from `OccupantUnit` + the unit type's max health to
`{ icon, state, healthFraction }`, distinguishing drone/robot by icon
(color stays reserved for ownership per [[ANU-013]]).

Protocol: added `attackSuburb` (`unitId`, `sal_code`) as a new message
rather than overloading `moveUnit` — `moveUnit` now explicitly rejects a
target holding an enemy unit (`suburb-defended`) so the two messages have
a clean split (move = go somewhere undefended, attack = go somewhere that
might not be). This is additive to ANU-013's protocol shapes, not a
breaking change to them.

Tests split per the advisor's flagged concern that the random rule can't
be asserted over the WebSocket protocol (no message carries an injectable
rng or a lobby member's scrap balance): `spec/units.test.ts` exercises
`server/units.ts` directly against `openStore(":memory:")` with a seeded
rng (same pattern as `spec/perks.test.ts`) for exact-outcome, variance,
and scrap-credit assertions; `spec/combat.test.ts` exercises `attackSuburb`
over the real WebSocket protocol but only asserts accept/reject on
reachability, never who wins a contested hit. `spec/unit-visual.test.ts`
covers `unitVisual`'s output shape for drone/robot/destroyed/in-transit.
`spec/occupancy.test.ts`'s pre-existing "moves a placed unit" test was
switched from a robot to a drone, since its two fixture suburbs have no
guaranteed road adjacency and it's testing ANU-013's move primitive, not
ANU-014's reachability rule (that's covered separately now).

Full `pnpm check` is green except the pre-existing, unrelated
[[ANU-012]] map-balance failures (same 9 failures present on `main` before
this branch).

## Notes

Depends on [[ANU-013]] (occupancy primitive, colors, scrap column, perk
hook, file-layout convention) landing first. Scoped independent of
[[ANU-015]] (factories — this issue consumes a `unit_types` build cost
but doesn't implement the production queue itself) and [[ANU-016]] (skill
tree — this issue reads the perk hook's multipliers but doesn't define any
node that sets them) so the three can run as parallel worktrees against
ANU-013's contract without touching each other's files
(`server/units.ts` vs. `server/factories.ts` vs. `server/skill-tree.ts`,
per docs/git-workflow.md rule 4).

`placeUnit` is deliberately left unrestricted by movement-mode
reachability (a robot can be *placed* somewhere it couldn't currently
*walk* to) — [[ANU-017]]'s capture-contest tests place a contesting unit
directly into a suburb regardless of adjacency, and that issue runs as a
parallel worktree against this one; restricting `placeUnit` here risked
breaking those tests on merge. This is a loophole for a future issue
(most naturally [[ANU-015]]'s factories, which only ever place a unit at
the factory's own suburb anyway) to close if it matters in practice.
Flagged here rather than silently left implicit, per this session's
`advisor` review.

The `advisor` tool reviewed the implementation plan before coding began
and caught several issues folded into the design above: the
WebSocket-vs-direct-import test split, the non-1 `scrapPerKillMultiplier`
test, the pre-existing `spec/occupancy.test.ts` robot-move test that the
new reachability rule would otherwise break, the `placeUnit`-stays-
unrestricted call, and the "owned OR adjacent-to-owned" robot eligibility
definition (an isolated owned suburb must stay reachable by its own
owner, not just suburbs neighbouring it).

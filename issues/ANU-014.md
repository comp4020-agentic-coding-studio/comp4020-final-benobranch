## Why

The user's own words: "implement different troups (drones that can fly
across enemy zones to attack zones the player is not connected to, robots
that can only attack neighouring zones but do more damage/have more
health, etc)". This is the first of the four parallel systems issues
(see [[ANU-013]], which this depends on for the occupancy primitive,
player colors, and scrap balance this issue spends/earns against) — the
unit types and their rules, not yet the UI to order one built (that's
[[ANU-015]]'s factories) or the skill tree that unlocks better versions
(that's [[ANU-016]]).

Two unit archetypes at minimum, matching the user's description exactly:
- **Drones**: fly — can attack a suburb the attacking player has no
  road-adjacent corridor to (ANU-013's occupancy model doesn't require
  adjacency to place a unit; this issue is what actually uses that to mean
  "ignores corridor/adjacency for drones specifically"). Lower
  health/damage than robots as the tradeoff for that reach.
- **Robots**: ground — can only attack a suburb road-adjacent (PLAN.md's
  existing adjacency definition: shares a *road* connection, not just a
  touching border) to one the player currently owns. Higher health/damage
  than drones as the tradeoff for the range restriction.

## Done when

- `server/units.ts` (per [[ANU-013]]'s file-layout convention) owns unit
  stats and combat resolution, reading/writing the `units` and
  `unit_types` tables ANU-013 migrated and seeded as placeholders.
- `unit_types` has real rows for at least drone and robot (health, damage,
  build cost in scrap, build time), replacing ANU-013's placeholders —
  stats don't need to be perfectly tuned, but must be genuinely distinct
  (drone: lower health/damage, any-suburb targeting; robot: higher
  health/damage, adjacency-restricted targeting) so the tradeoff is real,
  not cosmetic.
- **Combat resolution rule — confirm with the user before locking in**
  (flagged, not decided, in [[ANU-013]]'s Notes): deterministic
  (attacker stats vs. defender stats, no randomness) or with a random
  element. Pick one, document the choice and reasoning here in the
  Resolution, and get the user's sign-off the same way [[ANU-006]] did for
  its balance-bound call (`AskUserQuestion`) before building the GUI on top
  of an unconfirmed rule.
- Attacking a suburb with units present resolves combat between the
  attacking unit(s) and whatever's defending (other units, and/or the
  suburb's defensive value if the owner has no units there — define
  explicitly what "undefended" means) using the chosen resolution rule;
  losing units reduce health/are destroyed and the destroying player's
  `scrap` balance (ANU-013's column) increases by an amount scaled by
  `scrapPerKillMultiplier` (ANU-013's perk hook, default 1 until
  [[ANU-016]] gives it a way to be anything else).
- Attack/move messages extend ANU-013's `placeUnit`/`moveUnit` protocol
  shapes rather than inventing parallel ones — add an `attackSuburb`
  message if move-into-occupied-suburb isn't already enough to express
  "attack," but keep the occupancy broadcast shape ANU-013 defined.
- Drone movement validation ignores corridor/ownership entirely (per the
  "fly across enemy zones" requirement); robot movement validation checks
  road-adjacency to an owned suburb using the existing `map.json` adjacency
  graph (same data [[ANU-010]]'s map rendering already loads).
- A unit's current position/health is visible in the map's occupancy
  broadcast (ANU-013's primitive) so [[ANU-017]]'s capture-contest logic
  and the eventual GUI can both read "who/what is standing in this suburb
  right now" from one source.
- **GUI representation (map-drawable, not yet player-controllable — see
  ANU-013's Notes on the GUI boundary)**: a pure function, e.g.
  `unitVisual(unit) -> { icon, facing/orientation if relevant, healthFraction }`
  distinguishing drone vs. robot at a glance (different icon/shape, not
  just a color — color is reserved for ownership per [[ANU-013]]), plus a
  simple state representation for "destroyed" (fade/remove) and "in
  transit" (drones specifically, since they can be mid-flight over
  territory they don't own) — covered by a `spec/` test asserting the
  function's output shape for each case listed, not a rendered screenshot
  (per `CLAUDE.md`'s current no-manual-e2e rule).
- `spec/*.test.ts`: drone attack succeeds against a non-adjacent,
  unowned-corridor suburb; robot attack against the same target is
  rejected; a robot attack against an adjacent owned-corridor suburb
  succeeds; combat resolution matches the confirmed rule exactly (if
  deterministic: same inputs always produce the same outcome, asserted
  directly); a kill credits scrap to the attacker scaled by the perk
  multiplier; `unitVisual` output for drone/robot/destroyed/in-transit.
- No regressions: full `pnpm check` green except the pre-existing,
  unrelated [[ANU-012]] map-balance failures.

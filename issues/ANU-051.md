## Why

Found while resolving merge conflicts between [[ANU-048]] (the EMP unit)
and [[ANU-042]] (auto-fortify) after both landed on `main` independently —
not something either issue's own tests could have caught in isolation,
since neither branch knew the other existed yet.

`server/auto-fortify.ts`'s `run()` groups a player's occupancy by
`unitTypeKey` with no exclusion list, then calls `redistributeType` for
**every** type found, including `"emp"` ([[ANU-048]]'s
`EMP_UNIT_TYPE_KEY`). `AUTO_FORTIFY_SURPLUS_THRESHOLD` is a flat 6, with no
per-archetype override — so a player who has researched EMP, left a
factory producing them running for a while (5 minutes per unit, but a
session is long), and has auto-fortify set to `"balance"` or `"border"`
will eventually accumulate 7+ idle EMPs at one territory and have the
ticker (`server/index.ts`'s auto-fortify sweep) silently `moveUnits` the
surplus to their other owned territories — through the exact same
dispatch path a manual order uses.

Because an EMP's arrival **always** detonates regardless of defender or
owner ([[ANU-048]]'s confirmed design — it bypasses `resolveCombatAt`
entirely), this isn't a cosmetic misrouting: it means auto-fortify can
cause a player to black out their own factory production and data-center
TFLOPS, exactly the economic harm the EMP is meant to inflict on an
*opponent*. Nothing about auto-fortify's own design review ([[ANU-042]]'s
Notes — drones/robots only were ever discussed) anticipated a unit type
whose arrival is destructive-by-design to the destination; the two issues
were authored by different people's concerns at different times and never
cross-checked against each other's state space.

## Done when

- `server/auto-fortify.ts`'s `run()` excludes `EMP_UNIT_TYPE_KEY`
  (imported from `server/units.ts`, not re-declared) from both
  `groundedCountByType`/`inTransitToByType` grouping — an idle EMP sitting
  at any owned territory is never counted as "surplus" and never
  dispatched by either `"balance"` or `"border"` mode, regardless of how
  many accumulate. This is a narrow, type-specific skip in the existing
  per-type loop, not a new per-archetype threshold/config system — EMP is
  the only unit type whose arrival is unconditionally destructive to its
  destination, so a general "which types opt out of auto-fortify" knob
  would be solving a problem that doesn't exist yet for drone/robot (or any
  future ordinary combat unit).
- A player's drones/robots at the same territory continue to be evaluated
  and redistributed completely normally — the fix is scoped to the "emp"
  key specifically, not a change to the surplus/reachability/weighting
  logic itself.
- `spec/auto-fortify.test.ts` gets a new case: a territory holding
  well over `AUTO_FORTIFY_SURPLUS_THRESHOLD` idle EMPs, with `"balance"`
  mode on and another owned (under-stocked) territory available, produces
  zero EMP dispatches — while a drone surplus at the *same* territory in
  the *same* call still redistributes normally, proving this is a
  type-specific skip, not auto-fortify going inert for that territory.
- `pnpm check` green (typecheck + `spec/*.test.ts` against the running
  app). Per `CLAUDE.md`'s current cost-discipline rule, no manual
  headless-Chrome verification required for this pass.

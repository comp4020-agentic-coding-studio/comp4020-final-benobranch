## Why

The map is a single `<svg>` with one `<g>` layer per marker type
(`server/public/index.html:95-130`); SVG has no z-index concept, so paint
order is purely the physical order of those `<g>` tags in the DOM. The
current order, bottom to top, is: suburbs → capture stripes
(`#map-ownership`) → data centers (`#map-data-centers`) → spawns (empty) →
player bases (`#map-bases`) → factories (`#map-factories`) → transit arrows
→ **units (`#map-units`)**, last. `renderUnits` (`server/public/map.js:512-
600`) is the last marker layer drawn, so a unit-stack marker (owner-colored
backdrop + archetype icon + "xN" count) fully paints over any data-center
icon, player-base/skull signifier, or factory marker centered at the same
`label_point`. User-reported cases:

- A data-center icon (e.g. the mega tier's 900-wide sun/core glyph) gets
  completely covered by a unit stack sitting in the same suburb.
- The player-base skull signifier (`renderBases`, `map.js:357-391` — the
  per-suburb "this is a player's spawn" marker) gets covered by a unit stack
  the same way.

This isn't a stray CSS bug — `index.html`'s own comments (lines 115, 124,
126-128) show the layer order was chosen deliberately per-feature as each
was added, without reconciling that drawing units last means they occlude
everything else whenever markers share a suburb (centers, bases, and units
are all drawn at the same `geo.label_point`, with comparable footprints of
320-900 map units, so overlap is routine rather than an edge case).

## Done when

- Decide and implement a fix for the occlusion — two candidate approaches,
  pick based on which reads better once tried:
  1. **Reorder the `<g>` layers** in `server/public/index.html` so
     `#map-units` (and `#map-factories`, since [[ANU-049]] gives it a real
     icon too) no longer paints over `#map-data-centers`/`#map-bases` —
     e.g. draw data-center and base icons after units, or offset them from
     each other.
  2. **Offset overlapping markers** the way `renderUnits`/
     `layoutUnitMarkers` already fan out same-suburb unit groups
     left-to-right via `UNIT_GROUP_GAP` (`map.js:487,541-542`) — extend that
     fan-out to include the data-center/base/factory markers at a shared
     `label_point` instead of just unit-to-unit groups.
  Whichever is chosen, a suburb with a data center, a player base, a
  factory, and a unit stack all at once must leave every one of the four at
  least partially visible/tappable — not just whichever is topmost.
- Hit-testing (`map.js`'s `elementFromPoint`-based click handler, which the
  code comments around line ~949 note relies on paint order) still resolves
  taps correctly for whichever layering/offset approach is chosen — a tap
  intended for a now-differently-positioned data-center or base icon must
  still select that marker, not whatever happens to still be on top.
- `pnpm check` passes. Per `CLAUDE.md`'s current cost-discipline rule, no
  manual headless-Chrome verification required — note in Resolution that a
  real deploy/QA pass should visually confirm this rather than trusting
  `pnpm check` alone, since this is fundamentally a visual-legibility bug
  that automated tests can only partially cover (marker DOM presence/order,
  not actual rendered occlusion).

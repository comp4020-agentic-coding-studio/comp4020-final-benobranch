## Why

The map is a single `<svg>` with one `<g>` layer per marker type
(`server/public/index.html:95-130`); SVG has no z-index concept, so paint
order is purely the physical order of those `<g>` tags in the DOM. The
current order, bottom to top, is: suburbs → capture stripes
(`#map-ownership`) → data centers (`#map-data-centers`) → spawns (empty) →
player bases (`#map-bases`) → factories (`#map-factories`) → transit arrows
→ **units (`#map-units`)**, last. `renderUnits` (`server/public/map.js:512-
600`) is the last marker layer drawn, so a unit-stack marker (owner-colored
backdrop + archetype icon + "xN" count) fully paints over any data-center
icon, player-base/skull signifier, or factory marker centered at the same
`label_point`. User-reported cases:

- A data-center icon (e.g. the mega tier's 900-wide sun/core glyph) gets
  completely covered by a unit stack sitting in the same suburb.
- The player-base skull signifier (`renderBases`, `map.js:357-391` — the
  per-suburb "this is a player's spawn" marker) gets covered by a unit stack
  the same way.

This isn't a stray CSS bug — `index.html`'s own comments (lines 115, 124,
126-128) show the layer order was chosen deliberately per-feature as each
was added, without reconciling that drawing units last means they occlude
everything else whenever markers share a suburb (centers, bases, and units
are all drawn at the same `geo.label_point`, with comparable footprints of
320-900 map units, so overlap is routine rather than an edge case).

## Done when

- Decide and implement a fix for the occlusion — two candidate approaches,
  pick based on which reads better once tried:
  1. **Reorder the `<g>` layers** in `server/public/index.html` so
     `#map-units` (and `#map-factories`, since [[ANU-049]] gives it a real
     icon too) no longer paints over `#map-data-centers`/`#map-bases` —
     e.g. draw data-center and base icons after units, or offset them from
     each other.
  2. **Offset overlapping markers** the way `renderUnits`/
     `layoutUnitMarkers` already fan out same-suburb unit groups
     left-to-right via `UNIT_GROUP_GAP` (`map.js:487,541-542`) — extend that
     fan-out to include the data-center/base/factory markers at a shared
     `label_point` instead of just unit-to-unit groups.
  Whichever is chosen, a suburb with a data center, a player base, a
  factory, and a unit stack all at once must leave every one of the four at
  least partially visible/tappable — not just whichever is topmost.
- Hit-testing (`map.js`'s `elementFromPoint`-based click handler, which the
  code comments around line ~949 note relies on paint order) still resolves
  taps correctly for whichever layering/offset approach is chosen — a tap
  intended for a now-differently-positioned data-center or base icon must
  still select that marker, not whatever happens to still be on top.
- `pnpm check` passes. Per `CLAUDE.md`'s current cost-discipline rule, no
  manual headless-Chrome verification required — note in Resolution that a
  real deploy/QA pass should visually confirm this rather than trusting
  `pnpm check` alone, since this is fundamentally a visual-legibility bug
  that automated tests can only partially cover (marker DOM presence/order,
  not actual rendered occlusion).

## Resolution

Went with **approach 2 (positional offset)**, not a `<g>`-layer reorder,
and specifically a *fixed* per-marker-type offset rather than the
player-generated `layoutUnitMarkers` fan-out — for the reasons laid out
below.

**Why not reordering alone (approach 1):** as this issue's own "Done when"
flagged, reordering the `<g>` layers only changes WHICH marker wins the
exact same dead-center pixel at a shared `label_point` — it doesn't make
more than one of them visible at once. A suburb with all four marker types
stacked would still show only the new topmost one in full, with the rest
fully hidden underneath it. That fails the "every one of the four at least
partially visible" requirement regardless of DOM order, so reordering could
only ever be a partial ingredient (e.g. deciding which marker "wins" the
exact center of a diagonal-offset scheme), never the whole fix.

**Why a fixed offset, not extending `layoutUnitMarkers`'s fan-out
(approach 2's harder variant):** `layoutUnitMarkers`'s left-to-right
fan-out works well for units because unit groups are homogeneous (count of
groups varies but they're spiritually the same marker type) and arbitrary
in number per suburb. Data centers, bases, and factories are different: at
most one of each exists per suburb (a data center is a fixed map feature;
a base exists only while a player holds their one kickoff spawn; ANU-049
confirmed factories are also effectively one-per-suburb in practice
despite not being DB-enforced that way). With at most one marker of each
of the three types ever co-existing at a suburb, a *fixed* per-type offset
gets the same non-overlap guarantee as a dynamic fan-out, with far less
code and no risk of destabilizing `layoutUnitMarkers`'s existing (tested)
grouping logic, which issues/ANU-034.md already built out carefully for
its own narrower unit-to-unit case.

**What changed:**
- New `server/public/marker-offset.js` — a pure, dependency-free
  `quadrantAnchor(labelPoint, size, dirX, dirY)` helper (same "testable
  without jsdom" convention as `unit-marker-layout.js`/`capture-visual.js`)
  that returns a marker's center point shifted by half its own footprint
  toward one of the four quadrants around `label_point`, so one of the
  marker's own CORNERS lands exactly on `label_point` instead of its
  center.
- `server/public/map.js`:
  - Data-center markers (`initOnce`'s data-center loop) anchor **upper-left**.
  - Player-base markers (`renderBases`) anchor **upper-right**.
  - Factory markers (`renderFactories`) anchor **lower-left**.
  - Unit-stack markers (`renderUnits`) are **unchanged** — still centered on
    `label_point`, keeping their existing `layoutUnitMarkers`/
    `UNIT_GROUP_GAP` fan-out for same-suburb unit groups. This means a unit
    stack still partially overlaps whichever of the other three share its
    suburb, but only over the ONE nearest quadrant of that marker's
    footprint, never its full area — a data center/base/factory now always
    has at least 3/4 of its own area clear of any unit marker, and the unit
    marker itself was never the one being hidden in the original bug report.
  - `renderCapture`'s progress-bar vertical clearance (`BELOW_LABEL_POINT_
    CLEARANCE`, previously `ICON_HALF`) is updated to match: data-center/
    base markers no longer extend below `label_point` at all post-offset,
    but the factory marker now extends its FULL size below (not half, since
    it's corner- not center-anchored), so the bar clears
    `max(UNIT_MARKER_SIZE / 2, FACTORY_MARKER_SIZE)` instead of
    `max(UNIT_MARKER_SIZE, PLAYER_BASE_MARKER_SIZE) / 2`.
- Rebased onto `origin/main` after [[ANU-049]] merged first (concurrent
  sibling-worktree work, per this issue's own Notes) and resolved the one
  resulting conflict in `renderFactories` so the factory marker's real icon
  (`factory-icon.js`'s `FACTORY_ICON`/`FACTORY_MARKER_SIZE`, not a
  placeholder square) uses the same lower-left anchor as its backdrop rect.

**Hit-testing:** unaffected by construction — every marker element keeps
exactly the same `dataset.salCode`/`unitId`/`factoryId` attributes it had
before, just painted at different coordinates, and the `<g>` layer paint
order in `index.html` is untouched. `map.js`'s `elementFromPoint`-based
click handler (~line 969) still resolves a tap to whichever element is
topmost at that pixel; the fix changes where markers' pixels are, not how
clicks are resolved. No existing test exercises `renderBases`/
`renderFactories`/`renderUnits`/`renderCapture` directly (they need a real
DOM via `getElementById` at module load, so `spec/gui.test.ts` only checks
the static `<g>` layer IDs exist — unchanged by this fix) — `pnpm check`
(30 files / 235 tests after the ANU-049 rebase) is green.

**Known limitation (per this issue's own acknowledgment):** `pnpm check`
confirms DOM structure and layer presence, not actual rendered pixel
overlap — per `CLAUDE.md`'s current cost-discipline rule, no manual/
headless-Chrome verification was done here. A real deploy or separate QA
pass should visually confirm the four marker types read as distinct and
tappable at a suburb that has all four at once (data center + a player's
still-held spawn + a factory + a unit stack), since this was fundamentally
a visual-legibility bug that automated tests can only partially cover.

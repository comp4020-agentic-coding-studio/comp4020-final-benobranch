## Why

The three fixed brief requirements (multi-user, real-time, persists) need an
actual server before any game mechanics can land. PLAN.md's stack decision
(Node + WebSockets + SQLite) was reaffirmed over a cloud-hosted DB
(e.g. Supabase) specifically because `fly.toml`'s own comments say the course
setup is one machine + one `/data` volume with no separate database server —
see the ADR this issue adds. The target is 5+ players playing concurrently,
not just the 2-browser marker minimum, so the skeleton needs to prove
real-time fan-out to more than two connections before game logic is built on
top of it.

This issue replaces the `busybox`/static-file placeholder with a real Node
server that still serves `/` and `/readme/` (so the two shipped
`spec/invariants.test.ts` checks keep passing), adds a SQLite-backed store on
the `/data` volume, and adds a minimal WebSocket layer that proves
multi-user + real-time + persists end to end with a throwaway feature (a
shared counter or presence list) before any map/combat/game-state code
exists. Later subsystems (map/combat, UI) build on the protocol and store
this issue establishes.

## Done when

- `server/` (Node, TypeScript, type-stripped — no build step) serves HTTP on
  `0.0.0.0:$PORT`, answers `/` with 200, and publishes `README.md` at
  `/readme/` with its headings intact (both existing `spec/invariants.test.ts`
  checks pass unmodified).
- A SQLite database (`node:sqlite`, WAL mode) lives at `${DATA_DIR}/game.db`
  (`DATA_DIR` defaulting to `/data` in prod, overridable for local/test runs
  per docs/git-workflow.md rule 6), with at least one table proving
  round-trip persistence across a process restart.
- A WebSocket endpoint accepts concurrent connections (tested with 5+, not
  just 2) and broadcasts a state change made by one connection to every other
  open connection within ~1s, satisfying the brief's real-time definition.
- `Dockerfile` is rewritten to build and run this server (still serving
  `/readme/` per its own comment) instead of the busybox placeholder, and
  `pnpm check` passes against a container built from it.
- A new `spec/*.test.ts` file covers: persistence across a real process
  restart (spawn the server against a temp `DATA_DIR`, write, kill, respawn,
  read), and a change made on one WebSocket connection being observed by
  several others.
- An ADR (`docs/adr/0001-persistence-and-realtime-stack.md` or similar)
  records the SQLite-vs-managed-Postgres decision and the WAL/synchronous-
  handler concurrency reasoning, for `PROCESS.md` to cite.
- `tsconfig.json`'s `include` covers `server/` so `pnpm typecheck` checks it.

## Resolution

Built `server/index.ts` (Node, run via native type-stripping, no build step)
with `server/store.ts` (SQLite via `node:sqlite`'s `DatabaseSync`, WAL mode,
at `${DATA_DIR}/game.db`), `server/protocol.ts` (typed WebSocket message
shapes shared by server and any future client), and `server/readme-page.ts`
(renders `README.md` at `/readme/`, carried over from the placeholder's
contract). The throwaway feature is a shared bump counter plus a live player
list — enough to exercise identity, mutation and broadcast without encoding
any real game rule.

Verified empirically, not just by passing tests:
- 6 concurrent WebSocket connections all receive a broadcast triggered by one
  connection's action (ad hoc smoke script, since deleted; the permanent
  check is `spec/realtime.test.ts` with 5).
- The SQLite file (plus its `-wal`/`-shm` sidecars) survives a real process
  kill-and-respawn against the same `DATA_DIR`, both run directly with `node`
  and inside a built Docker container with a bind-mounted volume standing in
  for Fly's `/data` mount (`docker restart`, not just a fresh container).
- `pnpm check` passes against a server built and run from the rewritten
  `Dockerfile`, matching what CI's own `check`-gated deploy job does.

Rewrote `Dockerfile` to a two-stage Node 24.21 build (pinned to the version
`mise.toml` pins for local dev) instead of the busybox static-file
placeholder, and removed `placeholder/` since nothing references it anymore.
Added `server/` to `tsconfig.json`'s `include` so `pnpm typecheck` covers the
backend, and ignored the local `/data/` stand-in for the Fly volume in
`.gitignore`.

Added `spec/lib/spawn-server.ts` (spawns a real server child process against
a scratch port/`DATA_DIR`, self-contained start/use/stop per the ANU-003
lesson about state outliving a test), `spec/persistence.test.ts` (the
restart check), and `spec/realtime.test.ts` (5 concurrent connections, one
bumps, all five see the broadcast and agree on the resulting count).

Recorded the SQLite-vs-managed-Postgres decision and the
synchronous-handler/WAL concurrency reasoning in
`docs/adr/0001-persistence-and-realtime-stack.md`, including why time-based
state (TFLOPS accrual, etc., once it exists) needs to be derived from stored
timestamps rather than a running timer, since `fly.toml`'s
`auto_stop_machines` means no timer runs while the machine is idle.

## Notes

Builds directly on the Supabase-vs-SQLite discussion that preceded this
issue (not itself filed as an issue, since nothing went wrong in it — it was
a design question, answered before implementation started, not a bug or
harness correction).

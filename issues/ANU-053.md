## Why

User-reported: once the EMP unit type is researched/unlocked ([[ANU-048]],
already merged — added an "emp" `unit_types` row, research-gated via the
new "emp-research" skill-tree node), ALL unit icons on the map disappear,
not just EMP icons — every drone/robot marker too, as soon as any EMP unit
exists anywhere in a lobby's occupancy list.

Root cause: `server/public/unit-visual.js`'s `ARCHETYPE_BY_UNIT_TYPE_KEY`
lookup only had `drone`/`drone-mk2`/`robot`/`robot-mk2` — no `emp` key, even
though ANU-048 seeded a real `emp` `unit_types` row. `unitVisual()` throws
for any unrecognized `unitTypeKey`. `map.js`'s `renderUnits` calls
`unitsLayer.replaceChildren()` first (clearing every existing marker), then
built its resolved-units array via a plain `.map()` with no try/catch —
hitting one emp unit mid-iteration threw and aborted the WHOLE `.map()`
call, so nothing got appended back into the already-cleared layer.
`renderTransit` had the identical bug (clears `transitLayer` first, then a
`for` loop with no try/catch around `unitVisual()`). Neither `app.js` call
site wraps either function in a try/catch, so this was genuinely uncaught,
not silently swallowed.

This matters for the game's core legibility promise (CLAUDE.md: "a corridor
cut has to be visible fast, not just correct") — a player with zero visible
units on a map that's secretly full of them can't act on real information,
which undercuts the whole point of a real-time map read.

## Done when

- `unit-visual.js`'s `ARCHETYPE_BY_UNIT_TYPE_KEY` resolves `"emp"` to its
  own archetype (not reusing drone/robot's), and the `UnitVisual.icon`
  JSDoc union type (and every other place in `server/public/*.js` typing
  the same `"drone" | "robot"` union — `transit-visual.js`,
  `unit-marker-layout.js`) is widened to include it.
- `unit-icon.js`'s `UNIT_ARCHETYPE_ICONS` has a matching `"emp"` entry
  pointing at a real, already-in-repo icon asset (no new pixel-art
  sourced).
- `renderUnits`/`renderTransit` (`map.js`) no longer let one
  unrecognized/bad unit's `unitVisual()` throw abort the whole render —
  each wraps its per-unit resolution in its own try/catch (skip + warn on
  that one unit), so a future unit type reproducing this same gap can't
  wipe every other unit's marker again.
- `spec/*.test.ts` covers: `unitVisual()` resolves `"emp"` without throwing
  and returns a distinct archetype; `UNIT_ARCHETYPE_ICONS` has an `"emp"`
  entry distinct from drone/robot's; a mixed-archetype list including emp
  resolves every unit without throwing (regression for the whole-layer
  wipeout).
- `pnpm check` green.

## Resolution

Fixed by adding the missing `"emp"` key everywhere the client-side unit
archetype lookup/union type lived, and hardening the two render loops so
this specific failure mode (one bad unit's thrown error wiping an
already-cleared layer) can't recur for a future unit type:

- `server/public/unit-visual.js`: `ARCHETYPE_BY_UNIT_TYPE_KEY.emp = "emp"`;
  `UnitVisual.icon` widened to `"drone" | "robot" | "emp"`.
- `server/public/transit-visual.js` and `server/public/unit-marker-layout.js`:
  their independently-typed `"drone" | "robot"` archetype JSDoc unions
  widened the same way (these don't import `unit-visual.js`'s type, they
  each declare their own copy).
- `server/public/unit-icon.js`: `UNIT_ARCHETYPE_ICONS.emp =
  "icons/skills/lean-production.png"` — reusing the same lightning-bolt
  glyph ANU-048 already picked for the "emp-research" skill-tree node icon,
  rather than sourcing a new pixel-art asset. Confirmed (via Python/PIL
  palette inspection, not just eyeballing) that `lean-production.png` is
  32x32 and shares the exact same 6-color "glitch" palette (including the
  same transparency index) as `unit-drone.png`/`unit-robot.png`, so it reads
  consistently as a unit marker, not just a skill-tree node icon.
- `server/public/map.js`: `renderUnits` and `renderTransit` both now
  build their resolved-unit arrays with an explicit `for` loop and a
  try/catch per unit around the `unitVisual()` call, `console.warn`-ing and
  skipping any unit that still throws (e.g. a genuinely-unrecognized future
  `unitTypeKey`) instead of letting one bad unit abort the whole array/loop
  after the layer has already been cleared. `renderUnits` previously used
  `.map().filter()`; it's now a `for` loop pushing into an array so the
  try/catch can wrap each iteration individually.
- Tests: extended `spec/unit-visual.test.ts` with three new cases (emp
  resolves without throwing and is its own distinct archetype; an in-transit
  emp reports "in-transit" like drone/robot; a mixed drone/emp/robot list
  resolves every unit without throwing — the direct regression case for the
  whole-layer wipeout). New `spec/unit-icon.test.ts` (no existing test file
  covered `unit-icon.js` directly — `factory-icon.js`/`base-icon.js`'s
  sibling icon-constant modules don't have dedicated spec files either, so
  this is new coverage, not an extension of an existing pattern) checking
  `UNIT_ARCHETYPE_ICONS` has a distinct `emp` entry. `renderUnits`/
  `renderTransit` themselves aren't unit-tested directly — like `app.js`,
  `map.js` does top-level `document.getElementById` calls that make it
  importable only inside a real DOM, and no existing spec file imports it
  (`spec/gui.test.ts`/`spec/map-geometry.test.ts` only check the served
  markup/script content-type over HTTP, never import the module itself) —
  so this follows the existing pattern of testing the pure
  `unit-visual.js`/`unit-icon.js` modules the render functions depend on,
  per the issue's own "otherwise a pure unit-visual.js/unit-icon.js level
  test is sufficient" fallback.

`pnpm typecheck` clean; `pnpm check` green — 33 test files (up from 32: the
new `spec/unit-icon.test.ts`), 278 tests passing total: 3 new cases added to
`spec/unit-visual.test.ts` and 3 new cases in the new
`spec/unit-icon.test.ts`, on top of the pre-existing suite.

## Notes

[[ANU-048]]'s own Done-when section explicitly scoped the client-side
visual work to `renderOwnership`/`renderCapture`-adjacent EMP-blackout
rendering (the red-border/stripe/countdown overlay, `emp-blackout-visual.js`)
and the sidebar's countdown label — it never mentions `unit-visual.js`'s
`ARCHETYPE_BY_UNIT_TYPE_KEY` or `unit-icon.js`'s `UNIT_ARCHETYPE_ICONS` at
all, in either its Done-when or Resolution sections. This was a missed spot,
not a known, deliberately-deferred gap: ANU-048 treated the EMP unit as
reusing the *existing* `renderUnits`/`renderTransit` marker-drawing path
wholesale (reasonably — it's dispatched/moved through the same
`moveUnits`/`settleArrivals` pipeline as a drone/robot, per ANU-048's Why
point 1), but that path's archetype lookup table was never actually
extended to recognize the new unit type it was implicitly expected to
render.

Per CLAUDE.md's "before opening a new issue for a `pnpm check` failure"
rule: this isn't a `pnpm check` failure being re-diagnosed (the bug is a
runtime crash, not a failing existing test — none of the 271 tests ANU-048
left passing exercised `renderUnits`/`renderTransit` with a live emp unit
mixed into the occupancy list), so there's no earlier issue to extend
instead of opening a new one; confirmed via `grep -rl "renderUnits\|
unitVisual\|ARCHETYPE_BY_UNIT_TYPE_KEY" issues/*.md` turning up only
ANU-048 itself (the issue that introduced the gap) and no prior bug report.

Per CLAUDE.md's current cost-discipline rule, no manual headless-browser
verification was done for this pass — `pnpm check` (typecheck + the new
`spec/unit-visual.test.ts`/`spec/unit-icon.test.ts` cases, plus the full
existing suite) is the bar for "done" here.

## Why

User-reported via screenshot: a data-center icon rendered partially outside
its own suburb's polygon outline, bleeding into a neighboring suburb/the
void. Root cause: [[ANU-050]] moved data-center/base/factory markers from
centering on `geo.label_point` to anchoring via `quadrantAnchor(labelPoint,
size, dirX, dirY)` (`server/public/marker-offset.js`) so one CORNER of the
marker's footprint lands exactly on `label_point`, trading dead-center
occlusion for a marker that extends `size` map-units further out in its
anchor direction.

`label_point` is produced by Shapely's `representative_point()`
(`scripts/map/build_geometry.py`, `polygon_label_point`) — guaranteed to
land *inside* the polygon, with **zero guaranteed clearance to any edge**.
It was never designed to leave room for a marker footprint beside it.
Measured proof (clearance from `label_point` to the suburb's own bbox edge,
vs. the marker size that direction needs):

- "City" (mega tier, data-center upper-left anchor, needs 900): only
  ~755 clearance left, ~694 up — overflows by ~145-205 units on both axes.
- "Phillip" (mega): clearance 803/803 vs. needed 900.
- "Braddon" (major, needs 640): clearance 502 left.
- "Beard" (standard, needs 440): clearance 301 up.
- "Oaks Estate" (standard, needs 440): clearance 351 up.

Player-base markers (`renderBases`, upper-right anchor) and factory markers
(`renderFactories`, lower-left anchor) use the exact same `quadrantAnchor`
mechanism with their own sizes (`PLAYER_BASE_MARKER_SIZE` 320,
`FACTORY_MARKER_SIZE` 280) and are equally susceptible on narrower suburbs,
even though no tier of either hits the 900-unit extreme the mega data-center
tier does.

## Done when

- A marker's footprint (data center, base, or factory) stays within its own
  suburb's geometry bounds, without reintroducing the full-overlap occlusion
  problem [[ANU-050]] fixed (two quadrant-anchored marker types at the same
  suburb must still never fully cover each other).
- `spec/marker-offset.test.ts` and/or a geometry spec cover the clamp,
  including the measured "City" mega-tier overflow case from this issue's
  Why section.
- `pnpm check` passes (typecheck + `spec/*.test.ts`). Per `CLAUDE.md`'s
  current cost-discipline rule, no manual headless-Chrome verification
  required — note in Resolution that a real deploy/QA pass should visually
  confirm markers read as fully inside their suburb outline, since this is
  fundamentally a visual bug automated geometry checks can only partially
  stand in for.

## Resolution

Added a per-suburb `bbox` field to `map-geometry.json`
(`scripts/map/build_geometry.py`'s new `polygon_bbox()`, alongside the
existing `path`/`label_point` per suburb) and a new pure helper,
`clampMarkerSize(labelPoint, size, dirX, dirY, bbox)`
(`server/public/marker-offset.js`), that shrinks a marker's effective size to
whatever clearance the suburb's own bbox actually has in the anchor
direction, before `quadrantAnchor` computes the marker's position. `map.js`'s
three quadrant-anchored call sites (the data-center loop in `initOnce`,
`renderBases`, `renderFactories`) now call `clampMarkerSize` first and pass
its result as `size` into both `quadrantAnchor` and the marker's own
width/height attributes, so the *visual* marker size shrinks along with the
anchoring, rather than anchoring tightly while still drawing the icon at its
original (overflowing) size.

The bbox (not the polygon itself, and not a fixed global margin) is the
clamp input: it's a cheap superset of the actual polygon (so a concave
suburb's marker can still graze the real boundary in rare cases, never the
polygon exactly), but it's exact *per suburb* — unlike a single global cap,
which would be wrong for both the smallest and largest suburbs (ANU-047's/
ANU-050's own tier range: 280-900 units) at once. The clamp is uniform
across width/height (the smaller of the x/y clearances), not per-axis, so a
shrunk marker stays square instead of visibly squashed on one axis.

This does not reintroduce [[ANU-050]]'s occlusion problem: `clampMarkerSize`
only ever shrinks a marker's size, and each of the three marker types still
anchors into its own distinct quadrant (data center upper-left, base
upper-right, factory lower-left) — two *shrunk* quadrant-anchored footprints
are still at least as non-overlapping as two full-size ones were, since
shrinking a rectangle anchored at a fixed corner only pulls its far edges
closer to that corner, never further from it.

**What changed:**
- `scripts/map/build_geometry.py`: new `polygon_bbox()`, included as `bbox`
  on every suburb in the output (ran the regeneration logic directly against
  the already-baked `scripts/map/data/map-geometry.json` rather than
  re-fetching raw ABS SAL data, since the bbox is derivable from the
  already-baked `path` field — same `minx,miny,maxx,maxy` the script's own
  `bounds_to_view_box` already computes for the two view-box fields, just
  per suburb instead of for the whole map).
- `server/public/marker-offset.js`: new `clampMarkerSize` export.
- `server/public/map.js`: the data-center loop in `initOnce`, `renderBases`,
  and `renderFactories` each compute `size` via `clampMarkerSize(...)`
  before calling `quadrantAnchor`; `GeoSuburb`'s typedef gains `bbox:
  ViewBox`.
- `spec/marker-offset.test.ts`: new tests for `clampMarkerSize` (no-op when
  there's room, shrinks to the binding clearance, uniform not per-axis,
  never negative, and a regression case using this issue's measured "City"
  numbers).
- `spec/map-geometry.test.ts`: new tests that every suburb's `bbox` actually
  contains its own `label_point`, and that every real data center's clamped
  marker (in all four quadrant directions, to be robust against a future
  anchor-direction change) stays within its own suburb's `bbox` — including
  a dedicated "City" regression case asserting the clamp actually engages
  (`clampedSize < rawSize`).

`pnpm check` (32 files / 280 tests) passes against a local instance on port
8082 (`APP_URL=http://localhost:8082 pnpm check`, per docs/git-workflow.md
rule 6 — other worktrees' dev servers may be on other ports).

**Known limitation:** per `CLAUDE.md`'s current cost-discipline rule, no
manual/headless-Chrome verification was done. A real deploy or separate QA
pass should visually confirm the clamped markers read as fully inside their
suburb's outline (not just inside the looser bbox superset) at "City" and
the other small suburbs flagged in this issue's Why section.

## Notes

Follow-up/regression from [[ANU-050]]: that issue fixed marker-vs-marker
occlusion within a suburb by moving from a centered to a corner (quadrant)
anchor, but didn't check the anchor against the suburb's own polygon edge —
only against other same-suburb markers. This issue adds that missing check.

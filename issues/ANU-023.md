id: ANU-023
title: SQLite ALTER TABLE DROP COLUMN corrupts schema when the column follows an inline comment
status: done
type: harness
opened: 2026-11-04
---

## Why

Found while implementing [[ANU-022]]'s v6 migration, which needed to drop
`factories.queued_unit_type_key` and `factories.queue_started_at` (the old
single-queue slot [[ANU-022]] replaced with a `factory_production` child
table). Both statements:

```sql
ALTER TABLE factories DROP COLUMN queued_unit_type_key;
ALTER TABLE factories DROP COLUMN queue_started_at;
```

ran the first drop fine, then failed the SECOND with
`error in table factories after drop column: incomplete input` — not on the
statement that's actually wrong, but on the very next statement touching
that table (including a plain read). Root-caused by reproducing it in
isolation (`node --no-warnings -e ...` against a scratch `:memory:`/file
DB): `node:sqlite`'s `DROP COLUMN` rewrites the table's stored `CREATE
TABLE` text, and that rewrite corrupts it specifically when the dropped
column immediately follows an inline `--` comment in the original DDL —
which `server/store.ts`'s v5 migration's `factories` table has, on exactly
the column being dropped:

```sql
CREATE TABLE factories (
  ...
  -- Production queue, stored-timestamp style: null when idle.
  queued_unit_type_key TEXT REFERENCES unit_types(key),
  queue_started_at TEXT
)
```

This is a real engine-level limitation, not a mistake in the SQL — a
no-comment-preceding-the-column table drops the same column cleanly. It
cost real debugging time (a plausible-looking migration that passed in
isolated unit tests but broke on the very next `openStore` call against a
real/persisted file) precisely because nothing about the DROP COLUMN
statement itself looks wrong, and `pnpm check`'s in-memory-DB-per-test
suite never exercises a migration against a file with this exact DDL
shape — a future migration touching a column preceded by a comment would
hit the same wall silently.

## Done when

- `server/store.ts`'s v6 migration ([[ANU-022]]) works around this by
  rebuilding `factories` into a new table (`CREATE ... AS SELECT` the
  surviving columns, `DROP TABLE`, `RENAME TO`) instead of `DROP COLUMN` —
  done as part of [[ANU-022]]'s own commit, not deferred.
- This issue records the finding for whoever writes the next migration: a
  harness note, not a schema change in itself. No `spec/` test is practical
  to add for a SQLite engine quirk this specific (it would effectively just
  re-encode the bug report), so none is added — the record here and in
  [[ANU-022]]'s Resolution is the artifact.

## Resolution

Fixed by avoiding the faulty API entirely rather than working around its
exact trigger condition (e.g. stripping the preceding comment first, which
would be fragile against future schema edits). `server/store.ts`'s v6
migration creates `factories_new` with only the surviving columns, copies
every row, drops the old `factories`, and renames the new one into place —
ordinary SQL with no dependency on `DROP COLUMN`'s rewrite path at all.

One ordering constraint fell out of this fix: the rebuild has to happen
**before** `factory_production` is created, since once that table's rows
FK-reference `factories(id)`, `DROP TABLE factories` fails the foreign-key
check even inside the same transaction (SQLite checks FK existence at
`DROP TABLE` time regardless of transaction boundaries). [[ANU-022]]'s
migration does the rebuild first, then creates/backfills
`factory_production` against the already-rebuilt table.

The general lesson for future migrations in this file: prefer a
rebuild-via-copy over `ALTER TABLE ... DROP COLUMN` whenever the table's
original DDL has an inline comment near the column(s) being dropped — it's
cheap insurance against a schema-corruption class of bug that gives no
useful error at the point it actually occurs.

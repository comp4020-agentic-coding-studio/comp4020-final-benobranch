## Why

[[ANU-013]] stubbed a per-member `tflops`/`tflops_last_accrued_at` column
pair ("the balance itself; real accrual logic is explicitly out of scope
here") and flagged that a future issue would need to implement real accrual
using the same stored-timestamp pattern as capture/production/travel.
[[ANU-016]] (the skill tree) built real purchase logic on top of that
balance — `purchaseNode` deducts TFLOPS synchronously and is covered by
`spec/skill-tree.test.ts`/`spec/skill-tree-protocol.test.ts` — but no issue
has picked up the accrual half. In live play every member's `tflops` stays
at 0 forever (nothing ever credits it), so `purchaseNode` always returns
`insufficient-tflops` and the skill tree is only reachable in tests that
directly `UPDATE lobby_members SET tflops = ...` against the store. The
feature is built but not playable.

## Done when

- A real accrual rule: PLAN.md's "Data centers" section already defines
  each data center's fixed TFLOPS power score and the "connected vs.
  disconnected" draw-rate idea (though the connected/disconnected mechanic
  itself is still out of scope — see [[ANU-016]]'s `data-uplink` node note).
  At minimum, a player accrues TFLOPS over time from data centers they hold,
  using the stored-timestamp pattern ([[ANU-013]]'s `tflops_last_accrued_at`
  column, `server/time.ts`'s `elapsedMs`/`GAME_TIME_SCALE`) — computed at
  read/broadcast time, never from an armed interval, same as capture
  progress/production queues/unit travel.
- `spec/*.test.ts`: a player holding a data center accrues TFLOPS
  proportional to elapsed time (survives a real process restart mid-accrual,
  same style as `spec/territory.test.ts`'s restart test); a player holding
  no data center accrues nothing; purchasing a skill-tree node against an
  accrued (not manually-seeded) balance succeeds once enough time has
  elapsed.
- No regressions: full `pnpm check` green except the pre-existing, unrelated
  [[ANU-012]] map-balance failures.

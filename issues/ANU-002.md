## Why

The hook's own comment claimed it was guarding against "a push to `main`
that ships a red build," on the assumption (carried over from the RefWhistle
source material, where pushing main has no separate CI gate) that pushing
`main` directly triggers a deploy here too.

## Done when

The comment in `.githooks/pre-push` and the corresponding rule in
`docs/git-workflow.md` describe what this repo's `.github/workflows/checks.yml`
actually does, not an assumed mechanism.

## Resolution

Re-reading `checks.yml` (which I'd already read, but hadn't checked against
the hook's own claim) showed the `deploy` job has `needs: check` — once the
repo is public, CI itself already refuses to deploy a build that fails
`pnpm check`. So a push-triggered deploy was already covered; writing a hook
whose comment claimed to be the thing stopping that was simply inaccurate,
and in a file that's graded as part of the process harness, an inaccurate
rationale is worse than no rationale.

The actually-unguarded path, found by working out what CI's gate does *not*
cover: a manual `flyctl deploy` run by hand from a stray worktree while the
repo is still private (before CI's gate applies at all). Fixed by adding
`scripts/deploy-guard.mjs` (invoked as `pnpm run deploy`), which checks the
same `CHECK_OK` marker conditions before shelling out to `flyctl deploy`, and
rewriting the hook's comment and `docs/git-workflow.md` rule 5 to say
precisely this. Added a line to `CLAUDE.md` telling the agent to run
`pnpm run deploy`, never `flyctl deploy` directly.

Caught in the same `advisor` review as [[ANU-001]].

## Notes

This is the issue type the brief's "corrections belong in the harness" line
is pointing at most directly: the fix isn't a retry, it's a new script plus
a `CLAUDE.md` rule that didn't exist before.

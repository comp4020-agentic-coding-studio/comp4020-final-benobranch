## Why

The user's own words, quoted in full since this issue's visual spec is
exact enough that paraphrasing it risks losing detail an agent working from
just this file would need:

> implement the action of actually taking zones (progress on capture can
> only be made if no competing player is in the zone, a competing player
> entering the zone will pause the progress of capturing, which is resumed
> when the enemy leaves the zone, or is reset if the enemy takes over the
> zone. Zones being taken need to be signified by diagonal striped lines
> with the progress bar in the center of the zone. Each player gets a
> colour to represent them, and a zone in their control will be boundaried
> by their colour, with a semi opaque fill of their colour. When an two
> players are in the same zone, if it is in the process of being captured
> by one plauer when the other player enters, have both colours appear as
> diagonal stripes but do not let the stripes overlap. have the invading
> players colours slowly pulse to show who is attacking who. If a player
> owns a zone and another player is invading, have just the invading
> players pulsing stripes overlayed over the semi opaque colour fill of the
> residing player)

Fourth of four parallel systems issues. Depends on [[ANU-013]]'s
`suburb_ownership` table (including the capture-state columns it reserved:
`capturing_player_id`, `capture_started_at`, `capture_accumulated_ms`,
`contesting_player_id`) and occupancy primitive (to know who is physically
standing in a suburb), on [[ANU-016]]'s `captureSpeedMultiplier` perk hook,
and transitively on [[ANU-014]] for "a competing player entering the zone"
to mean a real unit present, not a placeholder.

## Done when

**State machine** (`server/territory.ts`, per [[ANU-013]]'s file-layout
convention), covering every case the quoted spec names:

- **Neutral/enemy-owned, no contest**: a player with units present and no
  opposing units present accrues capture progress. Progress is
  time-based using [[ANU-013]]'s stored-timestamp rule
  (`capture_started_at` + elapsed wall-clock time since, scaled by
  `GAME_TIME_SCALE` and `captureSpeedMultiplier`) — never a live interval
  that would reset on a restart.
- **Contested (two players' units in the same zone, one already
  capturing)**: progress accrual **pauses** — freeze
  `capture_accumulated_ms` at its current value rather than continuing to
  advance from the stored start time, and record who the contester is
  (`contesting_player_id`).
- **Contester leaves**: progress **resumes** from the paused
  `capture_accumulated_ms` (a new `capture_started_at` set to "now minus
  accumulated," not a progress reset) — must land back in the
  uncontested-accrual case above with no lost progress.
- **Contester's own units take the zone** (not just enter it — capture
  the suburb themselves) while another player's capture was in progress:
  the original capturer's progress **resets to zero**, and ownership
  changes per whatever actually "taking" the zone means in this state
  machine (progress reaches 100% while uncontested).
- **Reaching 100% uncontested**: ownership transfers to the capturing
  player, `suburb_ownership`'s capture columns clear back to the
  neutral/not-capturing state.
- A single synchronous handler per capture-state transition (no `await`
  between reading current state and writing the new one) — same
  concurrency reasoning ADR 0001/[[ANU-008]]/[[ANU-015]] already apply, so
  two units entering/leaving a contested zone at the "same" instant
  resolve to one consistent state, not a race.
- A broadcast of capture-state changes (progress value, contested or not,
  who's capturing/contesting) matching the brief's ~1s real-time bar.

**Visuals — a pure function covering all four cases the user described**,
since `CLAUDE.md`'s current cost-discipline rule means this cannot be
verified by manually driving a browser; it must be checkable from
`spec/`. Specify and implement something like:

```
zoneVisual(suburbState) -> {
  fill: { color: PlayerColor, opacity: number } | null,  // owner's semi-opaque fill, or null if neutral
  stripes: [
    { color: PlayerColor, pulsing: boolean }  // 0, 1, or 2 entries
  ],
  progress: number | null  // 0-1, rendered at the zone's center; null if not being captured
}
```

mapping each of the user's four described states to a distinct, testable
output:
1. **Owned, no capture in progress**: `fill` = owner's color/opacity,
   `stripes` = [], `progress` = null.
2. **Being captured, uncontested** (neutral or enemy-owned zone, one
   player capturing, no contester): `fill` = null (or the prior owner's,
   if capturing *from* someone — decide and state explicitly which),
   `stripes` = [{ capturing player's color, pulsing: false }], `progress`
   = the current fraction.
3. **Two players in the same zone, neither owns it, one already
   capturing when the other enters**: `stripes` = both players' colors as
   non-overlapping diagonal stripes (the "do not let the stripes overlap"
   requirement — implement as distinct stripe angles/offsets or an
   explicit non-overlapping pattern, not literally overlaid), with the
   **invading** player's stripe marked `pulsing: true` and the original
   capturer's `pulsing: false` — "pulse to show who is attacking who"
   means the pulse indicates the invader specifically, not either
   arbitrarily.
4. **A player owns the zone and another is invading/capturing it**: `fill`
   = the owner's semi-opaque color (unchanged), `stripes` = **only** the
   invading player's color, pulsing, overlaid on top of that fill — the
   owner does not also get a stripe in this case (only the invader's
   stripe shows, per "just the invading players pulsing stripes overlayed
   over the semi opaque colour fill of the residing player").
- "Which player is the invader vs. the original capturer/owner" must be
  derivable unambiguously from stored state (not from message-arrival
  order) — use `suburb_ownership`'s `owner_player_id` /
  `capturing_player_id` / `contesting_player_id` columns directly.
- Rendered into `map.js` as a composed layer (per [[ANU-013]]'s
  file-layout convention: a `renderOwnership`/`renderCapture` function,
  not changes scattered through the existing suburb-rendering code) —
  diagonal stripes as an SVG pattern (e.g. `<pattern>` with
  `patternTransform="rotate(45)"`), the pulse as a CSS/SMIL opacity
  animation, the progress bar centered on the suburb's existing
  `representative_point` ([[ANU-010]] already computes this per suburb for
  marker placement — reuse it, don't recompute a centroid).
- `spec/*.test.ts`: all four visual cases above produce the exact
  described `zoneVisual` output (not just "non-null" — assert the specific
  fill/stripes/pulsing/progress values); the state machine's pause/resume/
  reset transitions (contester enters → progress frozen at correct value;
  contester leaves → resumes without loss; contester captures → resets to
  zero; reaches 100% uncontested → ownership transfers and columns clear);
  a capture duration survives a process restart mid-capture with correct
  elapsed/paused state (same style as `spec/persistence.test.ts`'s restart
  tests); `captureSpeedMultiplier` from [[ANU-016]]'s hook actually changes
  the accrual rate (not just present and unread).
- No regressions: full `pnpm check` green except the pre-existing,
  unrelated [[ANU-012]] map-balance failures.

## Resolution

**Cap on simultaneous capturers/contesters — confirmed with the user via
`AskUserQuestion` before implementation**: generalized to N simultaneous
contesters, not capped at two. `suburb_ownership`'s originally-reserved
`contesting_player_id` column is dropped entirely (v8 migration,
`server/store.ts` — v6/v7 were already taken by [[ANU-022]]/[[ANU-025]] by
the time this branch rebased onto `main`) — contesters are now derived
live, every settle pass, from `units` occupancy rather than stored in a
fixed-width column, so a 10-player pile-up on one suburb reports every
non-owner, non-capturer occupant as a contester instead of the first two.

**State machine** lives in `server/territory.ts`'s `settleCaptures`
(exported alongside the existing `assignSpawnOwnership`/`getOwnership`),
one synchronous pass per call over every suburb with current occupancy or
an existing in-progress capture, no `await` between reading occupancy and
writing the resulting `suburb_ownership` row (same concurrency reasoning
ADR 0001/ANU-008/ANU-015 already apply). Per-suburb transition logic
(`settleSuburb`) covers every case: zero capturers present freezes
progress (pause, not reset — "leaving with no contester" and "being
actively contested" are treated the same, since reset is reserved for an
actual takeover); exactly one capturer accrues or resumes without loss
(`server/time.ts`'s new `backdatedStart` helper is the inverse of
`elapsedMs`, computing "now minus accumulated" directly rather than
tracking an additive offset separately) or, if a *different* player is now
the sole occupant, resets to zero and restarts for them (the
"contester's own units take the zone" case); two-or-more capturers freezes
as contested, keeping whichever is already the recorded capturer as the
resident being invaded (so a third/fourth arrival doesn't reassign who's
under attack) unless the recorded capturer has left, in which case the
earliest-present occupant (by `spawned_at`, the only ordering signal
`units` has) becomes the new resident deterministically. Reaching the
(perk-scaled) `CAPTURE_DURATION_MS` design duration uncontested transfers
ownership and clears every capture column back to neutral, returned as a
`CaptureTransfer` so `server/index.ts` can relay it to
`factories.transferFactoryOwnership` (the confirmed capture-transfer rule
from [[ANU-015]]) and re-broadcast `LobbyState.ownership`.

**The suburb's own registered owner is never counted as a "competing
player"** of someone invading their territory — `settleSuburb` filters
occupants against `owner_player_id` before deciding who's capturing/
contesting. This is also what makes the visual spec's case 4 well-defined:
an owner's fill stays and they never get a stripe of their own, because
they were never a capturer or contester to begin with, not because of a
special case in the rendering layer.

**`CAPTURE_DURATION_MS = 20_000`** (game-ms, scaled by
`GAME_TIME_SCALE`/`captureSpeedMultiplier` like every other timed value) —
not specified by the user's request beyond "progress on capture" and the
brief's ~1s real-time bar, so a value had to be chosen: longer than a
single unit's build time (drone 1500ms/robot 3000ms, [[ANU-014]]) since
taking a zone is a bigger commitment, short enough to stay responsive
within a session.

**Capture-visual ambiguity resolved with the user via `AskUserQuestion`**:
the issue's own case 2 ("pulsing: false," fill ambiguous) and case 4
("fill = owner's color," pulsing: true) look contradictory for a sole
capturer invading an enemy-OWNED (not neutral) zone. Confirmed: case 4
wins whenever a current owner exists — the owner's fill always stays and
the capturing player's stripe always pulses once they're invading held
territory, even alone; pulsing only turns off for case 2's specific
scenario of claiming a truly neutral (no-owner) zone outright, where
nothing is being attacked yet, just claimed.

**Visuals**: `server/public/capture-visual.js`'s `zoneVisual` is the pure
function the issue specified, extended for N contesters (`stripes` can
hold more than 2 entries). All four of the user's described cases map to
exact, asserted output in `spec/capture-visual.test.ts` (12 tests,
including the N=3+ generalization and an unknown-player-id fallback).
Rendered into `map.js`'s new `renderCapture` (composed layer, same
full-redraw-on-broadcast convention as `renderUnits`/`renderFactories`)
into the `#map-ownership` layer `index.html` had reserved since ANU-020 —
diagonal stripes as one `<pattern>` per stripe, each painting only its own
`1/N` vertical band of the tile before the shared `rotate(45)` transform
(the "do not let the stripes overlap" requirement, generalized past two),
a pulsing stripe getting a CSS `@keyframes` opacity animation class, the
progress bar centered on each suburb's existing `label_point` (confirmed
this already *is* ANU-010's `representative_point` — same field, no new
geometry needed). `server/protocol.ts` gains `SuburbCaptureState`/
`ServerCaptures` (`type: "captures"`, sparse — only suburbs mid-capture
appear), broadcast after every occupancy-driven action
(`placeUnit`/`moveUnit`/`attackSuburb`) and from a new ~1s `captureTicker`
(same pattern as the existing `factoryTicker`), plus sent on `hello`
(reconnect) so a resuming client doesn't wait for the next change — and
any transfer that should have completed while nobody was connected to
trigger one is settled and reflected in that same `welcome`'s
`LobbyState.ownership` before it's sent, not just in the separate
`captures` message after it.

**Tests**: `spec/capture.test.ts` (direct against `server/territory.ts` +
a real in-memory SQLite connection, same pattern as
`spec/units.test.ts`/`spec/factories.test.ts`) covers uncontested accrual,
100%-completion transfer-and-clear, pause-on-contest (frozen value
verified not to advance across repeated settle calls), resume-without-
loss, contester-takeover reset, N=3 contester generalization, the owner's-
own-units-never-contest rule, `captureSpeedMultiplier` actually changing
the accrual rate (both faster and slower), leaving-with-no-contester
still pausing (not resetting), and a real process restart mid-capture
(same style as `spec/factories-restart.test.ts`) resuming correct
elapsed progress rather than losing it. `spec/capture-visual.test.ts`
covers the pure function. Full `pnpm check` green except two pre-existing,
unrelated failures — confirmed identical against a baseline run on `main`
before this branch's changes: [[ANU-012]]'s 9 map-balance failures, and
[[ANU-026]]'s 1 stale-fixture failure (`spec/economy-broadcast.test.ts`
expecting robot health 6 against a server now seeding 10).

- This branch diverged from `main` for several sessions (started well

  latest `main` before merging — real conflicts in
  `server/territory.ts`/`server/store.ts`/`server/public/map.js`/

  (this issue's changes are additive: a new message type, a new exported

  genuine numbering collision: this issue's `suburb_ownership` migration
  was originally written as v6, but [[ANU-022]] (factory rework) and
  [[ANU-025]] (base markers) had already claimed v6/v7 on `main` by the
  time of the rebase — renumbered to v8. A second collision found only by
  running the full suite (not each spec file in isolation): this issue's
  `spec/capture.test.ts` restart test originally picked port 8105 for its
  spawned server, independently colliding with
  `spec/economy-broadcast.test.ts`'s own `buildFactoryTestPort` (already
  8105 on `main`) — moved to 8106.
- The v8 migration uses `ALTER TABLE suburb_ownership DROP COLUMN
  contesting_player_id` — checked against [[ANU-023]]'s finding (found on
  a different concurrent branch: a `node:sqlite` `DROP COLUMN` corruption
  bug, triggered specifically when the dropped column immediately follows
  an inline `--` comment in the table's stored DDL). `suburb_ownership`'s
  v5 DDL has no comment immediately before `contesting_player_id`,
  confirmed by reading the column's stored `CREATE TABLE` text back after
  migrating a real file-backed database — not affected, and the full spec
  suite (which creates/reads/writes `suburb_ownership` extensively via
  `spec/capture.test.ts` and everything that already existed) passed
  clean, so this wasn't just inferred from the DDL shape.
- A `CAPTURE_DURATION_MS` design value had to be chosen (20 real seconds
  at `GAME_TIME_SCALE=1`) since the user's request didn't specify one
  beyond "progress on capture" — revisit once the game has a real playtest
  to calibrate against.
- Depends on [[ANU-013]] (ownership/capture-state schema, occupancy
  primitive, stored-timestamp rule, spawn-ownership-at-kickoff) and
  [[ANU-016]] (capture-speed perk hook) but not on [[ANU-014]]/[[ANU-015]]'s
  actual combat/production implementations — only on "a unit is present in
  this suburb," which ANU-013's occupancy primitive already provides.

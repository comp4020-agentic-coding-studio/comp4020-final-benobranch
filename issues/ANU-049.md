## Why

Every other map marker type (data centers, units, player bases) draws an
owner/tier-identifying icon `<image>` from `server/public/icons/` layered
over a colored backdrop — `data-center-visual.js`'s `DATA_CENTER_TIER_ICONS`,
`unit-icon.js`'s `UNIT_ARCHETYPE_ICONS` (eye=drone, gun=robot), and
`base-icon.js`'s `PLAYER_BASE_ICON` (skull). Factories are the one exception:
`renderFactories` (`server/public/map.js:719-739`) draws only a plain
`<rect class="factory-marker">` filled with the owner's color — no icon
image at all. `factory-visual.js`'s `FactoryVisual.icon` field is always the
literal string `"factory"` (line 36) but nothing in `map.js` ever uses that
string to pick an asset; only `ownerColor` and `production` are consumed.
User feedback: a factory should be visually identifiable on the map the same
way a data center or unit is, not just a colored square indistinguishable
from any other owner-colored shape.

## Done when

- A new factory icon asset exists at `server/public/icons/factory.png`
  (32x32 pixel-art, "glitch" white color-14 variant so it reads against any
  owner-color backdrop — same convention `unit-icon.js`/`base-icon.js`
  document). Check the existing craftpix Skillicon #35 pack
  (`server/public/icons/`, `skills/`) for an unused glyph that already reads
  as "factory/production" before sourcing a new one — [[ANU-041]] is
  tracking proper credit for that pack regardless of which glyph gets used.
- A small dependency-free module (mirroring `unit-icon.js`/`base-icon.js`)
  exports the icon path and a `FACTORY_MARKER_SIZE` constant — either added
  to `factory-visual.js` or a new `factory-icon.js`, matching whichever
  existing pattern reads more naturally once the change is written.
- `renderFactories` (`server/public/map.js:719-739`) appends an `<image>`
  element on top of the existing backdrop `<rect>`, same shape as
  `renderUnits`' icon append (`map.js:563-570`) or the data-center icon
  append in `initOnce` (`map.js:246-267`): `href` set to the new icon path,
  `image-rendering: pixelated`, sized/centered to match the backdrop.
- The map legend (`server/public/index.html`'s `.map-legend`,
  `server/public/map.css`'s `.legend-dot--*`) gains a factory entry using
  the same icon, matching how data center tiers already appear there
  (ANU-021's precedent).
- `pnpm check` passes, including `spec/factory-visual.test.ts` (extend it if
  the new icon path/size constants move through `factoryVisual` itself,
  otherwise it stays untouched since the pure function's job doesn't change).
  Per `CLAUDE.md`'s current cost-discipline rule, no manual headless-Chrome
  verification required.

## Resolution

Checked every existing craftpix Skillicon #35 glyph in `server/public/icons/`
and `server/public/icons/skills/` (better-fabs, lean-production,
robot-chassis, drone-chassis, advanced-drone, advanced-robot, data-uplink,
rapid-capture, researching, salvage-training, plus the data-center/unit/
base icons already in use) before sourcing anything new — none of them read
as "factory/production" on their own (they're abstract brackets, arrows,
chevrons and circuitry motifs built for the skill tree/unit roster, not a
building). So a new 32x32 icon was hand-built at
`server/public/icons/factory.png`, matching the pack's own format and
palette exactly: P-mode PNG, same 5-color palette order as `better-fabs.png`
(dark pink, blue, mint, pink, white, with palette index 5 as the
transparency key), same "glitch" construction (white glyph body, pink main
outline, mint 1px offset echo, sparse blue accent dots). The glyph depicts a
building with twin chimneys and smoke puffs. This is a new image file, not a
copy/recolor of an existing glyph — noted here per [[ANU-041]]'s
asset-crediting concerns, which this doesn't resolve but also doesn't make
worse (no new unattributed third-party asset; it's an original pixel-art
file built to match the existing pack's visual language, and the pack's own
`License.txt`/attribution gap stays exactly as it was).

Icon path + size constant landed in a new sibling module,
`server/public/factory-icon.js` (not merged into `factory-visual.js`,
mirroring how `unit-icon.js`/`base-icon.js` sit alongside
`unit-visual.js`/`renderBases` rather than inside them — `factory-visual.js`
stays the pure `FactoryState -> FactoryVisual` transform per ANU-013's
file-layout convention). Exports `FACTORY_ICON` ("icons/factory.png") and
`FACTORY_MARKER_SIZE` (280, matching the pre-existing hardcoded backdrop
rect size in `renderFactories`).

`server/public/map.js`'s `renderFactories` now appends an `<image>` element
after the backdrop `<rect>`, same shape as `renderUnits`'s icon append:
`href` set to `FACTORY_ICON`, sized/centered to `FACTORY_MARKER_SIZE` over
the same point as the backdrop, `image-rendering: pixelated`, and the same
`data-factory-id`/`data-sal-code` dataset as the backdrop so the existing
`elementFromPoint`-based click handler keeps resolving taps to the factory
(the icon paints on top, so it becomes the hit target, same as units'
icon-over-backdrop). Added `.factory-marker__icon` to `map.css` (cursor:
pointer, same as `.factory-marker`).

Added a factory entry to the map legend: a `.legend-dot--factory` span in
`server/public/index.html`'s `.map-legend`, and a matching rule in
`server/public/map.css` using `icons/factory.png` as its background image,
following the exact pattern `.legend-dot--mega`/`--major`/`--standard` set
(ANU-021's precedent) — extended the shared selector list rather than
duplicating the `border-radius`/`background-size`/`image-rendering` block.

`factory-visual.js` itself is untouched (its pure-function output shape
didn't change — the icon path/size now live in the new sibling module, not
through `factoryVisual()`), so `spec/factory-visual.test.ts` needed no
changes and still passes unmodified.

Verified with `pnpm check` (typecheck + `check:issues` + the full
`spec/*.test.ts` suite against a locally running app on a distinct
`PORT`/`DATA_DIR`, per `docs/git-workflow.md` rule 6) — 28 test files, 221
tests, all green, including `spec/factory-visual.test.ts`. No manual
browser/headless-Chrome verification, per `CLAUDE.md`'s current
cost-discipline rule.

## Notes

Filed alongside [[ANU-050]] (unit icons visually occlude data-center/base/
factory icons sharing a suburb) — the two are related (both about marker
legibility on the map) but independent: this one is "factories have no icon
at all," that one is "icons that do exist get hidden by units drawn on top."
A new factory icon added here will immediately inherit ANU-050's occlusion
problem too, since `#map-factories` is painted before `#map-units` in
`server/public/index.html`'s layer order — not this issue's problem to fix,
but worth having both landed before judging whether factories are legible.

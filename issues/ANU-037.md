## Why

Follow-up to [[ANU-035]], which grouped the Territory tab's per-suburb
occupant list by (owner, unit type). The user asked for two more display
changes to the same unit-roster surfaces:

1. The **Units tab** (`sidebar.js`'s `renderUnitList`, sourced from
   `panel-units`/`#unit-list`) still renders one `<li>` per individual unit
   ("Drone @ 80063 (3 hp)" repeated once per unit) — the same
   wall-of-identical-rows problem ANU-035 already fixed for the Territory
   tab's suburb-detail list, just not yet applied here. The user wants it
   grouped by suburb (as a subheading) then by unit type with a count,
   e.g.:
   ```
   Mawson
   Drone x32
   Robot x1

   Curtin
   Drone x13
   ```
   No owner name needed here (the Units tab is always "my units" already).
2. The **Territory tab**'s per-suburb occupant list (ANU-035's
   `occupantGroups`, rendered as "Drone — Beno ×32") should swap the order
   of type and owner: owner name first, then unit type, then count —
   "Beno — Drone ×32" instead of "Drone — Beno ×32".

## Done when

- A new pure grouping function (or an extension of
  `suburb-detail-view.js`'s pattern) groups the viewing player's own
  `OccupantUnit[]` by `(sal_code, unitTypeKey)` with a count, for the Units
  tab. Likely lives in `suburb-detail-view.js` alongside
  `suburbDetailViewModel`/`occupantGroups`, or a small sibling pure
  function — no DOM access, testable directly, matching the existing
  convention.
- `sidebar.js`'s `renderUnitList` renders one subheading per suburb
  (`sal_code`) the player has units in, with one row per unit type under it
  showing `"<Type> x<count>"` — no owner name (redundant on this tab).
- `sidebar.js`'s `renderSuburbDetail` occupant-group rows swap to
  `"<owner> — <Type> ×<count>"` ordering (owner first).
- `spec/sidebar-view.test.ts` (and/or a new spec file for the Units-tab
  grouping function) covers both changes.
- `pnpm check` green.

## Resolution

Added `unitsByZone({occupancy, myPlayerId})` to `suburb-detail-view.js`
(pure, no DOM access, same convention as `suburbDetailViewModel`): groups
the viewing player's own units — from every suburb, not just the selected
one — by `(sal_code, unitTypeKey)` with a `count`. `sidebar.js`'s
`renderUnitList` now builds one `<li class="roster-list__zone-heading">`
subheading per suburb (sorted by `sal_code`), followed by one row per unit
type at that suburb (`"<Type> x<count>"`, sorted by type) — no owner name,
since the Units tab is always "my units." A new `.roster-list__zone-heading`
rule in `style.css` renders the subheading as a plain bold label rather than
another bordered `.roster-list li` row. Map-click unit highlighting
(`selectFromMap`'s `{type: "unit", unitId}`) now resolves the clicked unit
to its `(sal_code, unitTypeKey)` group and highlights that whole row, since
a group no longer maps 1:1 to one list item.

`sidebar.js`'s `renderSuburbDetail` occupant-group rows (ANU-035's
`occupantGroups`) swapped from `"<Type> — <owner> ×<count>"` to `"<owner> —
<Type> ×<count>"` — a one-line template-string reorder, no data-shape
change (`occupantGroups` itself is unchanged).

Four new `spec/sidebar-view.test.ts` cases: `unitsByZone` grouping across
multiple suburbs/types for the viewing player only, and the empty case.
`pnpm check` green (208/208 tests, typecheck clean).

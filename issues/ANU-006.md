## Why

PLAN.md's "Players & spawn balance" section originally committed to a
specific, checkable claim (equal shortest-hop distance from every home base
to every data center, baked once offline) but left two open decisions
—faction count and number of data centers— explicitly dependent on running
the real search against the real ACT road graph rather than picking numbers
by feel. This issue is that spike: build the real suburb-adjacency graph
once (ABS SAL tiles + OSM road adjacency, per PLAN.md's "Map data" section)
and run the balance search against it.

Mid-spike, the user redirected the game design itself (see Resolution):
lobby-based games of 4-12 players rather than a small fixed faction roster,
30+ tiered data centers rather than a couple of equal ones, and "no spawn
way better than others" rather than exact equidistance. The scope below is
rewritten to match what actually shipped, not the original ask.

## Done when

- A script builds the real ACT suburb adjacency graph: ABS SAL suburb
  polygons as nodes, edges where two suburbs share a road connection (not
  just a touching border), per PLAN.md's adjacency definition.
- Data centers are placed in tiers (mega/major/standard) on real Canberra
  locations, per the user's explicit request that key real-world locations
  should host stronger data centers.
- Spawns are computed per lobby size (4-12 players), not baked as a fixed
  faction roster, since the game no longer has a fixed player count.
- A written verdict on the chosen configuration is added to PLAN.md's
  "Players & spawn balance" and "Data centers" sections, with the actual
  numbers behind the call, confirmed acceptable with the user via
  AskUserQuestion (both the ring-based spawn-fan substitution for the
  originally-requested literal compass-angle fan, and the ~2.7x worst-case
  balance tolerance).
- The chosen configuration (adjacency graph + data center tiers/placement +
  per-lobby-size spawn table) is baked into a committed derived-data file
  (`scripts/map/data/map.json`), with source attribution (ABS SAL CC BY 4.0,
  OSM ODbL) recorded alongside it.
- A `spec/*.test.ts` check loads that baked file and recomputes BFS hop
  distances and soft-access scores from the adjacency list directly (not
  from stored precomputed numbers), asserting the agreed balance bound for
  every lobby size — this is the enforceable claim PLAN.md flags as exactly
  the kind of thing worth pointing at directly rather than just asserting.

## Resolution

Built in three stages, each hitting a real design or implementation
problem:

**1. Adjacency graph (several false starts).** Fetched ABS SAL suburb
polygons (ArcGIS REST, state_code=8, 136 ACT suburbs/localities) and OSM
roads (Overpass API, highway whitelist) and built road-adjacency by
locating consecutive road-segment points into suburb polygons. Tried
dropping or contracting the large rural "ACT Remainder" tiles (bushland/
buffer suburbs) on the theory that they're unownable and shouldn't be
playable tiles — this was wrong twice over: it reintroduces the gaps/
overlaps that ABS SAL was chosen specifically to avoid, and the naive
all-pairs contraction of a scattered multi-part remainder tile created
spurious long-hop edges between suburbs that only share a reserve polygon,
not an actual road (one suburb ended up with 55 fabricated "neighbours").
Fixed by keeping remainder tiles as real graph nodes (splitting multi-part
ones into one node per disconnected polygon piece) and excluding them only
from spawn/data-center *candidacy*, not from the graph itself. Separately,
an early version of the point-locator let a road dipping briefly into NSW
fabricate adjacency between two ACT suburbs not actually linked inside ACT
(27k+ road points fell outside the ACT boundary) — fixed by hard-breaking
the adjacency walk on any out-of-boundary point rather than skipping it.

**2. Objective function (redirected mid-spike).** The original search
targeted PLAN.md's literal "equal hop-distance to every data center"
metric with a small fixed faction roster. Partway through, the user
changed the actual design: no fixed player count (4-12 per lobby instead),
30+ data centers instead of a couple, tiered power (key real-world
locations — Civic, Kingston, Fyshwick — stronger than others) instead of
uniform, and an explicit "doesn't need to be 100% balanced, just no spawn
way better" tolerance instead of exact symmetry. This made the old
equidistance search's output (and its "sum of distances" proxy objective,
caught as a mismatch with PLAN.md's actual wording before it was locked in)
moot. Replaced with a soft-access-score metric (Σ tflops × 0.5^hop per
data center) and a max/min ratio bound, chosen after confirming with the
user that ~2.7x worst-case was an acceptable reading of "not way better."

**3. Spawn placement (geometric dead end).** The user's literal ask — fan
spawns at 360/N degree compass intervals around the map — doesn't work for
Canberra's shape: the urban area is roughly twice as long north-south as
east-west, so equal compass sectors leave some directions (due east is
mostly airport/NSW border) with no suburb once N passes ~8. Two earlier
spawn-eligibility/placement attempts also surfaced real bugs: data centers
drawn by naive farthest-point sampling landed on residential rim suburbs
rather than the "key real-world locations" the user asked for, and a
spawn-exclusion rule (spawns must be >=2 hops from strong data centers) was
dropped partway through a refactor, letting a spawn land directly adjacent
to a mega data center. Fixed by: (a) drawing the major data-center tier
from a curated list of real Canberra town/group centres and precincts
instead of farthest-point sampling, (b) replacing the compass-angle fan
with even spacing along a hop-distance ring (suburbs 4-6 road-hops from the
graph's computed "hop-center", the suburb minimising worst-case
hop-eccentricity — turned out to be Acton), which gives the same visual
effect without the geometric failure mode, and (c) restoring the spawn-to-
data-center separation floor as a hard constraint in the final ranking.
Disclosed the compass-angle substitution to the user explicitly (via
AskUserQuestion) rather than silently reinterpreting their spec.

Several of the intermediate search/placement scripts were reviewed and
sent back by the `advisor` tool before being accepted — each round caught a
concrete bug or a silent metric mismatch rather than a style preference
(see Notes). `scripts/map/balance_search.py` (the superseded fixed-roster
equidistance search) was kept rather than deleted, with a header noting
what replaced it, since it's legitimate process evidence of the pivot.

## Notes

- `scripts/map/fetch_suburbs.py`, `fetch_roads.py`, `build_adjacency.py`:
  raw data fetch + adjacency graph construction.
- `scripts/map/balance_search.py`: superseded fixed-faction equidistance
  search — kept as process evidence of the original approach and why it
  was dropped.
- `scripts/map/build_lobby_config.py`: the live pipeline — data center
  tiers, hop-ring spawn placement, per-lobby-size balance search. Regens
  `scripts/map/data/map.json`.
- `spec/map-balance.test.ts`: recomputes BFS + soft-access scores from the
  baked file and checks connectivity, data-center placement, spawn counts/
  separation, and the balance bound, for every lobby size 4-12.
- Lobby lifecycle backend work (queueing, capacity, bot fill) is already
  tracked in [[ANU-008]] (persistent identity + lobbies in SQLite), which
  anticipated this spike landing a player-count range rather than a fixed
  faction count — its capacity field was deliberately left as "a parameter
  for now". No separate issue needed; PLAN.md's "Players & spawn balance"
  section now has the 4-12 range and bot-fill rule for that work to read.
  The Sunday 5pm Australia/Sydney scheduled-start rule is not yet covered
  by any open issue — worth its own issue when lobby scheduling is built.

## Why

`server/units.ts`'s `canReach` lets a drone (`movement_mode === "fly"`)
reach ANY suburb on the map unconditionally — the whole "ignore
adjacency/corridor" rule from issues/ANU-014.md has no range limit at all,
so a drone sitting in spawn can be sent clear across the map in one order.
User feedback from live play: this is too strong relative to the robot's
owned-or-adjacent-to-owned restriction (effectively a 1-hop rule, every
move) — drones need *some* ceiling, just a much more generous one than
robots get, to keep "ignore terrain" meaningfully different from "teleport
anywhere."

## Done when

- A drone's `moveUnits`/`moveUnit`/`attackSuburb` order is rejected
  (`unreachable`, same reason robots already use) when its destination is
  more than 5 road-adjacency hops from the nearest suburb the ordering
  player currently owns. Still "ignore adjacency/corridor" below that
  ceiling — a drone doesn't need a clear path through owned territory the
  way a robot does, it just can't be dispatched past 5 hops' distance from
  the player's empire.
- Measured via BFS over the same `adjacency` map `buildAdjacency`/
  `groundCanReach` already build in `server/units.ts`, from the full set of
  the player's owned suburbs (not just the drone's own origin) — a drone
  near a far-flung owned outpost should get its 5-hop ceiling measured from
  there too, not just the player's main cluster.
- `server/public/map.js`'s client-side reachability courtesy check
  (`groundCanReachSuburb`, mirrored for the robot row's unreachable-greyout
  in `sidebar.js`) gets an equivalent drone-side BFS helper, so the "Move
  units" panel greys out a drone row for an out-of-range destination the
  same way it already does for robots — same UX, same "server stays
  authoritative, this is a courtesy only" precedent.
- `pnpm check` green. Per `CLAUDE.md`'s cost-discipline rule, no manual
  headless-Chrome verification required for this pass.

## Why

User request: mark each player's base with a skull icon, using the same
ownership-color system as units/factories ([[ANU-024]]'s colored-square
pattern). "Base" has no existing entity in this codebase — [[ANU-006]]'s
own Resolution explicitly dropped an earlier "home base" design in favor
of the current lobby spawn-suburb system (`spawn_table_by_lobby_size` in
`scripts/map/data/map.json`, applied at kickoff by
`server/territory.ts`'s `assignSpawnOwnership`). The closest existing
concept is **each player's originally-assigned spawn suburb**.

Confirmed with user: the skull marker should show only while the player
still owns that original spawn suburb — if it's captured by someone else,
the skull disappears (not reassigned to the new owner). This needs new
plumbing, not just a rendering change: today `assignSpawnOwnership` writes
a player's spawn suburb into the same `suburb_ownership` table as any
later capture, with nothing distinguishing "this was the original spawn"
once written — indistinguishable from a suburb captured mid-game. No
`PlayerPresence`/`LobbyState` field carries this to the client either.

## Done when

- **Schema**: a `spawn_sal_code TEXT` column added to `lobby_members`
  (migration alongside the existing `ALTER TABLE lobby_members ADD COLUMN`
  block in `server/store.ts`, ~line 436-443, following [[ANU-023]]'s
  now-fixed SQLite `ALTER TABLE` migration pattern).
- **Write path**: `territory.ts`'s `assignSpawnOwnership` (it already has
  each `memberPlayerIds[i] -> spawnSalCodes[i]` pairing in hand) also
  persists it to the new column, once, at kickoff.
- **Protocol**: `PlayerPresence` (`server/protocol.ts`) gains a
  `spawnSalCode: string | null` field, populated wherever `PlayerPresence[]`
  is built for `ServerLobbyState` broadcasts.
- **Rendering**: the skull icon (`Skillicon14_19.png` — icon 19, color 14,
  the same "glitch" white variant [[ANU-024]]'s unit icons use, confirmed
  by visual preview) draws at a player's spawn suburb's
  `label_point`, owner-colored square backdrop (same visual pattern as
  [[ANU-024]]'s unit markers / the existing factory marker), only rendered
  while `ownership[member.spawnSalCode] === member.playerId` — i.e. it
  disappears the moment that check fails, no special-case removal logic
  needed beyond the existing full-redraw-on-broadcast precedent
  `renderOwnership`/`renderUnits`/`renderFactories` already use.
- `spec/*.test.ts`: a player's base marker is present immediately at
  kickoff (spawn suburb = assigned suburb) and a test confirms it stops
  being "ownable" once that suburb changes hands (asserting against the
  new protocol field / store column directly is enough — no new e2e
  rendering test needed, consistent with the "no manual browser
  verification for now" CLAUDE.md rule).
- `pnpm check` passes (same pre-existing [[ANU-012]] map-balance failures
  excepted).

## Resolution

**Schema**: `server/store.ts`'s v7 migration adds `lobby_members.spawn_sal_code
TEXT` via plain `ALTER TABLE ... ADD COLUMN` — [[ANU-023]]'s schema-corruption
quirk only triggers on `DROP COLUMN`, so no rebuild-via-copy was needed.
Verified against both an in-memory test DB and a real persisted file DB
(`user_version` advances to 7, column present) rather than assuming the
migration block runs cleanly.

**Write path**: `territory.ts`'s `createTerritory` gained a
`setSpawnSalCode` prepared statement; `assignSpawnOwnership`'s existing loop
now calls it right after each `upsertOwner` call, writing the same
`spawnSalCodes[i]` it was already using for ownership — one extra write per
assignment, no new computation.

**Protocol**: `PlayerPresence.spawnSalCode: string | null` added to
`server/protocol.ts`; `StoredMember` in `store.ts` gained the matching
field, `selectMembers`'s SQL now selects `spawn_sal_code AS spawnSalCode`,
and `index.ts`'s `buildLobbyState` passes it through into the broadcast
`members` array `app.js` already has in hand.

**Rendering**: new dependency-free `server/public/base-icon.js` (icon path +
marker size, same convention as `data-center-visual.js`/`unit-icon.js`).
`map.js`'s new `renderBases(ownership, members)` iterates `members`,
skipping anyone with no `spawnSalCode` (lobby not started) or whose
`ownership[spawnSalCode]` no longer equals their own `playerId` (base
captured) — drawing an owner-colored `<rect>` backdrop plus the skull
`<image>` on top for everyone who clears both checks. Decorative only
(`pointer-events: none`, no `dataset`/click wiring), same precedent as
`.dc-marker`/`.spawn-marker` — a base isn't a selectable game object. New
`#map-bases` SVG group added to `index.html` between the spawn-ring and
factory layers; `app.js` calls `renderBases(lobby.ownership, lobby.members)`
alongside the existing `renderOwnership` call, since both depend on exactly
the same two broadcast fields and update together on every `lobbyState`.

Because the "disappears" check re-reads current ownership on every call
rather than caching a captured flag, no explicit removal/transfer logic was
needed — the existing full-redraw-on-broadcast precedent `renderOwnership`/
`renderUnits`/`renderFactories` already establish just works here too.

**Tests**: extended `spec/territory.test.ts`'s existing kickoff e2e test to
assert every member's broadcast `spawnSalCode` is set and matches an owned
suburb; added a new module-level test (direct `territory.ts`/`store.ts`
import, same pattern as `spec/factories.test.ts`, since there's no protocol
message for a direct ownership transfer — only a full attack flow, out of
scope here) proving `spawnSalCode` survives a simulated capture unchanged
while the ownership-match check a base marker relies on flips to false.
Also added `#map-bases` to `spec/gui.test.ts`'s layer-existence checks.

This branch was started before [[ANU-024]]'s PR merged to `main`; rebased
onto `origin/main` once it did (one trivial import-line conflict in
`map.js`, resolved by keeping both imports) so this builds on the merged
unit-icon work rather than diverging from it.

`pnpm check` run against this branch's own dev server (port 8083): same 9
pre-existing `spec/map-balance.test.ts` failures as a clean `main` checkout
([[ANU-012]], not this issue's regression) — all 20 other test files pass,
163/163 non-map-balance tests green.

## Why

Opening [[ANU-027]] (Risk-style move/attack), this session scanned
`issues/` and picked `ANU-026`, per `issues/README.md`'s "pick the next
number: `ls issues/*.md | sort | tail -1`" step. In the gap between that
scan and this session's own commit, a peer session (working the TFLOPS
skill-tree issue) opened and merged its own `ANU-026` (a bug report about a
stale `spec/economy-broadcast.test.ts` fixture) into the same shared `main`
checkout. This session's subsequent `git add`/`git commit` of its own
`issues/ANU-026.md` silently overwrote the peer's file on disk — `git
status` showed it as a normal "modified" file, not a conflict, because both
sessions share one working tree rather than each working in its own
worktree/branch.

`issues/README.md`'s existing numbering caveat ("a worktree that hasn't
pushed yet is invisible to that scan") assumes the collision risk comes
from an *unpushed worktree*. It doesn't cover this case: two interactive
sessions both committing straight to `main` in the same shared checkout,
with no worktree isolation between them at all for the issue-opening step
itself (`docs/git-workflow.md` rule 1 exempts opening an issue from the
worktree-per-branch rule, since it's meant to be a fast, low-ceremony
`main` commit).

## Done when

- The clobbered `ANU-026.md` is restored to the peer session's bug report,
  and this session's feature proposal is renumbered to the next free id
  — done in the commit immediately following this file's own.
- This file records the gap so a future session reads it before assuming
  "scan `issues/`, pick the next number" is collision-proof when multiple
  sessions are opening issues around the same moment.

## Resolution

Fixed by restoring `issues/ANU-026.md` to the peer session's bug report
(`spec/economy-broadcast.test.ts` stale fixture) and moving this session's
Risk-style move/attack feature proposal to `issues/ANU-027.md` — see that
commit. No script change made: the actual fix here is procedural
(`git pull`/re-`ls issues/` immediately before committing a newly-opened
issue, not just once at session start, when multiple sessions are active
around the same time) rather than something `check-issues.mjs` can enforce
after the fact — a collision like this produces two *valid*, differently-
numbered files once resolved, so there's nothing left for the checker to
catch by the time either session pushes.

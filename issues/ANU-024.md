## Why

[[ANU-021]] replaced the data-center markers' solid-color circles with real
icon sprites from the same free asset pack
(`Free-Skill-32x32-Icons-for-Cyberpunk-Game`, craftpix license). Unit
markers (`server/public/map.js`'s `renderUnits`, `unit-visual.js`,
`.unit-marker--drone`/`.unit-marker--robot` in `map.css`) are the next most
visible placeholder: both archetypes currently render as the *same* SVG
circle, with "robot" distinguished only by a CSS `transform: rotate(45deg)
scale(0.8)` to fake a diamond silhouette — no actual per-archetype artwork.

Chosen icons (confirmed with user by visual preview — the pack has no
literal drone/mech sprites, these are the closest semantic fits from the
general RPG skill-icon set):
- **Drone**: icon 1 (eye — aerial recon/scout), color 14 (white with a
  red/cyan "glitch" fringe effect, matches the cyberpunk theme)
- **Robot**: icon 26 (rifle — ground combat), color 14 (same glitch-white,
  for a consistent look between the two unit types)

Ownership is currently conveyed by the marker's fill color (owner's player
color) — a fixed-color icon can't be recolored per-owner the way a plain
circle fill could. Resolved (user's call): icon drawn on top of a colored
square backdrop in the owner's color, same visual pattern
`factory-visual.js`/`.factory-marker` already uses (owner-colored square +
glyph), rather than losing at-a-glance ownership readability.

## Done when

- The two icons (`Skillicon14_01.png` for drone, `Skillicon14_26.png` for
  robot, from color folder 14) are copied into `server/public/icons/`
  under clear names, same 32x32 native size.
- `renderUnits` in `map.js` draws each unit as an owner-colored square (same
  sizing precedent as `.factory-marker`) with the archetype icon layered on
  top via a second SVG `<image>`, replacing the current single
  `<circle class="unit-marker--...">` element. `drone-mk2`/`robot-mk2`
  (ANU-016's skill-tree-gated variants) keep rendering with their base
  archetype's icon, same as today (`ARCHETYPE_BY_UNIT_TYPE_KEY` already
  collapses mk2 -> base archetype in `unit-visual.js` — no change needed
  there).
- The "in-transit" (drone mid-flight) visual distinction survives the
  change — today it's `.unit-marker--in-transit { opacity: 0.6 }`; keep an
  equivalent (e.g. apply the same opacity rule to the new marker group).
- `map.css` updated: remove the now-unused circle fill/rotate-diamond rules
  for `.unit-marker--drone`/`.unit-marker--robot` once the icon rendering
  replaces them.
- `pnpm check` passes (same pre-existing [[ANU-012]] map-balance failures
  excepted, per that issue's note).

## Resolution

Copied the two icons (`Skillicon14_01.png` -> `unit-drone.png`,
`Skillicon14_26.png` -> `unit-robot.png`) into `server/public/icons/` at
native 32x32 size. Added a dependency-free `server/public/unit-icon.js`
(same convention as `data-center-visual.js`) holding the archetype-icon
path map and marker size, so `map.js`'s `renderUnits` imports it rather
than inlining.

`renderUnits` now builds an SVG `<g class="unit-marker unit-marker--...">`
per unit containing two children: a `<rect class="unit-marker__backdrop">`
(owner-colored, same stroke treatment the old circle had) and an
`<image class="unit-marker__icon">` (the archetype glyph, `pixelated`
rendering) layered on top at the same size/position. Both children carry
the unit's `dataset.unitId`/`dataset.salCode` — the existing click handler
hit-tests via `elementFromPoint`, which resolves to whichever element is
topmost at the clicked pixel, so without duplicating the dataset onto both
elements a tap landing on the icon (painted last) would have missed the
unit id. `drone-mk2`/`robot-mk2` needed no changes — `unit-visual.js`'s
`ARCHETYPE_BY_UNIT_TYPE_KEY` already collapses them to their base
archetype's icon.

`map.css`: removed `.unit-marker--robot`'s rotate/scale transform (no
longer rendering a plain circle to fake a diamond) and the old
circle-specific stroke rule, moving stroke onto the new
`.unit-marker__backdrop` class; `.unit-marker--in-transit`'s opacity rule
is unchanged and still applies to the whole `<g>`.

`pnpm check` run against this branch's own dev server (port 8082): same 9
pre-existing `spec/map-balance.test.ts` failures as a clean `main`
checkout ([[ANU-012]], not this issue's regression) — all 20 other test
files pass. No test file needed updating: `spec/unit-visual.test.ts` only
exercises the pure `unitVisual()` data function (untouched by this issue),
and `spec/gui.test.ts`'s `#map-units` check is unaffected by what's
rendered inside that group.

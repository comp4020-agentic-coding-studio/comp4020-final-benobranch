## Why

The user's own words: "I do not want [units] to be created using scrap. I
want them to be automatically made based on a timer. This timer can be
improved in the skill tree. The scrap should only be for building more
factories." This inverts [[ANU-015]]'s production model (player picks a
unit type, pays scrap, waits `build_time_ms`) and narrows scrap's role from
PLAN.md's "funds factory/unit production" to factories only.

Confirmed with the user via `AskUserQuestion` before starting:
- No player choice of what a factory builds (fully automatic, no manual
  queue/build button for units).
- Every factory auto-produces **every** unit type simultaneously, each on
  its own independent timer (not one-at-a-time, not a single fixed type) —
  built modular so a future unit type added to `unit_types` slots in with
  no factories.ts code change.
- Timer duration keeps using each unit type's own `build_time_ms`
  (drone 1500ms, robot 3000ms), scaled by the existing
  `factoryBuildSpeedMultiplier` skill-tree perk (unchanged mechanic from
  [[ANU-015]], just no scrap gate and no player-picked single queue slot).
- [[ANU-016]]'s `lean-production` node (`factoryBuildCostMultiplier`) is
  repointed from "cheaper to build a unit" (now meaningless — units are
  free) to "cheaper to build a NEW factory" (`FACTORY_BUILD_COST_SCRAP`),
  so the node stays meaningful under the new economy without adding a new
  perk-hook key.

## Done when

- `unit_types.build_cost_scrap` and the perk-hook key it fed
  (`factoryBuildCostMultiplier` as "unit cost" multiplier) are removed from
  the unit-build path entirely — `queueUnit`/the scrap-queue concept is
  gone. `buildFactory` is the only scrap-spending action left, and
  `factoryBuildCostMultiplier` now scales `FACTORY_BUILD_COST_SCRAP`
  instead.
- Each factory tracks, per unlocked/buildable unit type, its own
  stored-timestamp production cycle (ADR 0001's rule — no armed timer):
  when a cycle completes, one unit of that type is placed via
  [[ANU-014]]'s `placeUnit` at the factory's suburb for the factory's
  current owner, and that type's cycle restarts immediately. Modular means
  adding a new `unit_types` row (gated or not) makes every factory start
  auto-producing it too, with no `factories.ts` edit — iterate
  `unit_types` (filtered by `requires_skill_node` unlocked-or-null) rather
  than hardcoding "drone" and "robot".
- `server/protocol.ts`: `ClientQueueUnit`/`"queueUnit"` removed;
  `FactoryState` drops `queuedUnitTypeKey`/`queueProgressFraction` (single
  queue slot) in favour of something like
  `production: { unitTypeKey: string; progressFraction: number }[]`
  reporting every type's current cycle progress.
- GUI (`server/public/sidebar.js`, `suburb-detail-view.js`,
  `factory-visual.js`): remove the "Build <type>" buttons and scrap-cost
  display for units; show each factory's per-type progress bars instead
  (read-only, matching [[ANU-015]]'s "map/panel-drawable, not yet
  player-controllable" convention this reverts unit-building to). Keep
  `buildFactory`'s scrap-cost button as the one remaining spend action.
- A migration (next `PRAGMA user_version` bump) replaces the single
  `queued_unit_type_key`/`queue_started_at` columns on `factories` with
  whatever per-type-cycle storage the implementation needs (e.g. a
  `factory_production` table keyed `(factory_id, unit_type_key)` with its
  own `cycle_started_at`), seeded for every existing factory x unit type
  row on upgrade so an in-progress game doesn't lose factories.
- `spec/factories.test.ts`/`spec/factories-restart.test.ts`/
  `spec/economy-broadcast.test.ts`/`spec/factory-visual.test.ts`/
  `spec/sidebar-view.test.ts`: rewritten for the new model — no scrap
  deduction on unit completion, a factory with no scrap at all still
  produces units over time, multiple unit types progress independently and
  concurrently at one factory, `factoryBuildSpeedMultiplier` still scales
  cycle duration, a restart mid-cycle resumes correct elapsed progress (not
  reset), `requires_skill_node`-gated types don't auto-produce until
  unlocked. `spec/skill-tree.test.ts`'s `lean-production` assertion is
  updated to check `FACTORY_BUILD_COST_SCRAP` scaling instead of a unit's
  `build_cost_scrap`.
- No regressions: full `pnpm check` green except the pre-existing,
  unrelated [[ANU-012]] map-balance failures.

## Why

Every `moveUnits` order (server/units.ts) resolves and relocates its units
the instant the message is handled — `OccupantUnit.destinationSalCode`/
`moveStartedAt` (server/protocol.ts) and `units`' matching DB columns
(`server/store.ts`) exist for exactly this future issue (issues/ANU-014.md's
Notes: "a future issue adding travel time is what populates those fields for
real"), and `unitVisual`'s `"in-transit"` branch (server/public/unit-visual.js)
has been dead code since ANU-014 for the same reason. The user wants units
to actually take time to travel — constant speed, but different per unit
type — and to see that movement on the map: a dotted arrow from origin to
destination, a mark on the arrow showing how far through the trip the unit
is, and the moving unit's own archetype icon on it, not just an abstract
line.

## Done when

**Server — travel is real, not just a client-side animation:**

- Each `unit_types` row gains a constant `speed` (map-units/ms or an
  equivalent constant, server's choice) — drone and robot get genuinely
  different values (drones faster, matching their "ignore terrain" fluff;
  exact numbers are this issue's call, same "a value had to be chosen, write
  down why" precedent as `CAPTURE_DURATION_MS`/`seedBaseUnitTypes`). A new
  migration (`server/store.ts`, v10) adds the column; seeded via the same
  idempotent upsert `seedBaseUnitTypes`/`seedSkillGatedUnitTypes` already use
  (mk2 variants may keep their base archetype's speed or get their own —
  pick one and say why, same as their movement_mode/stat-ratio precedent).
- Travel time between two suburbs is derived from real distance — the two
  suburbs' `label_point`s in `scripts/map/data/map-geometry.json` (loaded
  server-side the way `map-data.ts` already loads `map.json`) divided by the
  moving unit's `speed` — not a flat per-hop duration, so a long flight
  takes longer than a short one.
- Per this session's AskUserQuestion-confirmed decision (see Notes below):
  combat resolves **on arrival**, not at dispatch. A `moveUnits` order no longer
  decides outcomes synchronously — each selected unit is marked in-transit
  (`destination_sal_code`, `move_started_at` stored-timestamp columns, same
  ADR 0001 pattern as capture/factory timers, never an armed `setTimeout`)
  and resolves later, against whatever actually occupies the destination at
  the moment its travel time elapses (which may differ from what was there
  when the order was sent — a defender can reinforce or retreat mid-flight).
  This means:
  - `MoveUnitsResult`'s `outcomes` can no longer be "every outcome, decided
    now" — rework its shape (or add a new settle-driven result path) so the
    protocol/tests reflect "N units dispatched, in transit" immediately and
    "N units arrived, here's what happened to each" later, once resolved.
  - A new `settleArrivals(lobbyId)` (server/units.ts, same shape as
    `territory.ts`'s `settleCaptures`/`factories.ts`'s `settle`) runs the
    stored per-unit combat resolution once `elapsedMs(moveStartedAt) >=
    travelTimeMs`, called from index.ts's existing ~1s ticker pattern
    (`factoryTicker`/`captureTicker`) plus before every occupancy-driven
    broadcast, so a unit that finishes travelling with nobody connected to
    trigger it is still settled correctly on the next read (ADR 0001).
  - A unit's `sal_code` only changes to the destination once resolved
    (moved/kill outcome) or never (an attacker that dies first never
    "arrives" — Notes below covers the interesting edge case: two units
    crossing paths/racing for the same contested suburb).
  - `spec/units.test.ts`/`spec/combat.test.ts`/`spec/move-units-protocol.test.ts`
    update for the new async-resolution shape; `GAME_TIME_SCALE` (already
    used by capture/factory tests) lets these assert a real elapsed-time
    arrival without a multi-second sleep.
- `OccupantUnit.destinationSalCode`/`moveStartedAt` (already-existing fields)
  get populated for real for both archetypes while in transit (robots
  included — this session confirmed via AskUserQuestion that travel time
  applies to both drones and robots, not drones only; a robot's single
  adjacency hop now takes real time and shows the same in-transit state a
  drone would, so `unit-visual.js`'s current "only a drone ever reports
  in-transit" branch and its three `spec/unit-visual.test.ts` cases asserting
  that a robot never does need to change).

**Client — the dotted travel arrow:**

- A new map layer (own `<g id="map-transit">`, same static-markup-in-
  index.html-plus-render-function-in-map.js convention as the other seven
  layers) draws one dashed/dotted `<line>` or `<path>` per in-transit unit
  group, from its origin suburb's `label_point` to its destination's —
  grouping multiple units of the same (origin, destination, owner,
  archetype) traveling together into a single arrow with a count, same
  spirit as [[ANU-034]]'s `layoutUnitMarkers` fan-out/grouping (a pure,
  jsdom-free module, e.g. `transit-visual.js`, is the natural place for the
  "which units are in transit, grouped how" logic, tested the same way
  `unit-marker-layout.js` is).
- A progress mark (a small shape, not just color) sits on the line at the
  fraction-complete point, computed from `elapsedMs(moveStartedAt) /
  travelTimeMs` — the same derived-at-render-time pattern
  `capture-visual.js`'s progress bar and `factories.ts`'s
  `progressFraction` already use, not a value trusted from a stale
  broadcast. Needs to visibly move between broadcasts without a new message
  for every frame — reuse the existing ~1s occupancy broadcast cadence (or
  add a lightweight client-side `requestAnimationFrame`/`setInterval` tween
  between broadcasts using the stored `moveStartedAt`, server's/client's
  call which, document the choice).
- The traveling unit's own archetype icon (`UNIT_ARCHETYPE_ICONS`,
  `unit-icon.js` — same icons already used for grounded markers, per the
  request) renders at the progress mark's position, not just a generic dot.
- Owner color still conveyed somehow (the arrow, the icon backdrop, or
  both) so a travelling enemy fleet reads as hostile the same way a
  grounded one does.
- New `map.css` rules for the dashed line (`stroke-dasharray`) and any new
  `@keyframes` follow the existing JS-toggles-class / CSS-owns-animation
  split ([[ANU-034]]'s `.unit-marker__count--lost` precedent).

**Both:**

- `pnpm check` green (typecheck + `spec/*.test.ts` against the running
  app). Per `CLAUDE.md`'s current cost-discipline rule, no manual
  headless-Chrome verification required for this pass.

## Resolution

**Schema/seed**: `server/store.ts` v10 adds `unit_types.speed REAL NOT NULL
DEFAULT 1` (plain `ADD COLUMN`, no rebuild-via-new-table dance — this is an
addition, not a drop, so issues/ANU-023.md's `DROP COLUMN` quirk doesn't
apply). `server/units.ts` seeds `DRONE_SPEED = 0.5` / `ROBOT_SPEED = 0.2`
(map-units of `map-geometry.json`'s `label_point` space per game-ms —
drone 2.5x robot's speed, chosen wide enough to read as genuinely different
paces while keeping travel times in the same rough order of magnitude as
the file's other design durations; see the code comment for the worked
examples). `server/skill-tree.ts`'s mk2 variants keep their base
archetype's speed, same "upgraded chassis, not a faster engine" precedent
`movement_mode` already set. `server/map-data.ts` gained
`distanceBetweenSalCodes()`, loading `map-geometry.json` server-side (same
pattern as its existing `map.json` load) purely for this straight-line
distance.

**Resolve-on-arrival**: `moveUnits` now only dispatches — it stamps
`destination_sal_code`/`move_started_at` on each selected unit (`units`'
`startTransit`) and returns `{ dispatchedUnitIds }` instead of resolved
`outcomes`; nothing about combat is decided at dispatch time. A new
`settleArrivals(lobbyId)` resolves every in-transit unit whose travel time
(`distanceBetweenSalCodes / speed`) has elapsed since `move_started_at`,
in lobby-wide `move_started_at`-then-`id` order (not scoped per-order) so
two units racing for the same contested suburb from separate `moveUnits`
calls resolve in actual-arrival order, each seeing the real effect of
whichever resolved just before it. The combat-resolution core was split
out of the old `attackSuburbImpl` into `resolveCombatAt` (ownership/
reachability-agnostic) so `settleArrivals` can resolve a unit without
re-checking reachability — a unit reachable and owned at dispatch stays
committed to its trip even if the destination's ownership shifts mid-flight;
only the defender's live PRESENCE, not reachability, can change the
outcome. `attackSuburbImpl`/`moveUnit` (the old single-unit synchronous
primitives, unreachable from the live protocol since ANU-027) are
unaffected and still resolve instantly — they back `spec/units.test.ts`'s
seeded-rng assertions and `spec/capture.test.ts`'s capture-state fixtures.
`server/index.ts` calls `settleArrivals` from a new `arrivalTicker` (same
~1s pattern as `factoryTicker`/`captureTicker`) and before every
occupancy-driven action (`placeUnit`/`moveUnits`) and on `hello`, so a
unit that finishes travelling with nobody connected is still settled
correctly on the next read (ADR 0001's stored-timestamp rule). A completed
arrival's side effects (occupancy broadcast, kill-scrap economy update,
captures settle) are relayed the same way a synchronous `moveUnits`
outcome's always were.

Both archetypes travel for real now (confirmed via AskUserQuestion) — a
robot's single adjacency hop takes real time and shows the same in-transit
state a drone's flight does; `unit-visual.js`'s `state` is now
`unit.destinationSalCode ? "in-transit" : "grounded"` with no archetype
check, and `spec/unit-visual.test.ts`'s old "a robot never reports
in-transit" case now asserts the opposite.

`OccupantUnit` gained `travelProgressFraction` (0 to 1, computed
server-side in `toOccupant` from live `elapsedMs(moveStartedAt) /
travelTimeMs`, same derived-at-broadcast-time pattern
`SuburbCaptureState`/`FactoryProductionCycle`'s `progressFraction` already
use) so the client never needs `GAME_TIME_SCALE` to compute it itself.

**Client — the dotted travel arrow**: a new pure module
`server/public/transit-visual.js` (`layoutTransitArrows`, tested in
`spec/transit-visual.test.ts`, no DOM — same convention as
`unit-marker-layout.js`) groups in-transit units by `(origin, destination,
ownerPlayerId, archetype)`, with the group's progress mark position taken
from its LEAST-advanced member's `travelProgressFraction` (so a trailing
straggler is never drawn ahead of where it really is). A new `renderTransit`
(`map.js`) draws into a new `#map-transit` SVG layer (between `#map-units`
and `#map-factories` in `index.html`) — one dashed `<line>` per group from
the origin's `label_point` to the destination's (CSS `stroke-dasharray` plus
a `transit-line-march` `@keyframes` that shifts the dash offset so the line
visibly "marches"), an owner-colored backdrop with the travelling unit's own
archetype icon (`UNIT_ARCHETYPE_ICONS`) riding the line at the progress
fraction, and an `"xN"` count label when more than one unit shares the exact
trip. `renderUnits` now excludes in-transit units entirely (they no longer
"occupy" their origin suburb server-side either) so a unit is drawn either
grounded (map-units layer) or travelling (map-transit layer), never both.
The arrow's progress mark carries the same `dataset.unitId` click-selection
convention as a grounded marker, resolving to the Units tab's existing
zone-grouped list (no sidebar changes needed — `selectedUnit` is already
resolved against the full occupancy list, including in-transit units).

**Tests**: `spec/units.test.ts` replaced the old synchronous `moveUnits`
assertions with dispatch/settle pairs (`forceArrival` backdates
`move_started_at` so `settleArrivals` treats travel as complete without a
real sleep), plus new cases for "an in-transit unit can't be dispatched
again," "settleArrivals leaves an un-elapsed unit untouched," and the
cross-order arrival-race scenario from the issue's Notes.
`spec/combat.test.ts`/`spec/economy-broadcast.test.ts`/
`spec/move-units-protocol.test.ts`/`spec/occupancy.test.ts`'s WebSocket-level
tests that need a unit to actually arrive now spawn their own
`GAME_TIME_SCALE`-elevated server (`spec/lib/spawn-server.ts`, same pattern
`spec/capture.test.ts`/`spec/factories-restart.test.ts` already use) rather
than the shared unscaled `APP_URL` server, since a real drone/robot flight
at the seeded speeds is seconds to minutes. 14 new tests across
`spec/units.test.ts`/`spec/transit-visual.test.ts`; `pnpm check` green (220
tests across 28 files). Per `CLAUDE.md`'s cost-discipline rule, not
re-verified by driving a browser.

## Notes

Two units racing for the same contested suburb — one travelling there to
reinforce, one travelling there to attack, each dispatched before either
could see the other's order — is the interesting new edge case
instant-resolution never had to handle: `settleArrivals` must resolve
whichever one's travel time elapses first against the ACTUAL occupancy at
that moment (not a snapshot taken at dispatch time), and the second
arrival's own resolution then sees the result of the first. This is a
natural consequence of "resolve on arrival" rather than a special case to
hand-code, but is worth a dedicated `spec/units.test.ts` case since it's the
scenario most likely to reveal an ordering bug in `settleArrivals`.

Confirmed with the user via AskUserQuestion before implementation started
(this session): (1) combat resolves on arrival, against the destination's
occupants at that later moment, not at dispatch against occupants at
send-time; (2) travel time applies to both drones and robots, not drones
only.

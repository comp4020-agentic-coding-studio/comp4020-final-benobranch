## Why

While building [[ANU-013]]'s schema migration, the original `INSERT OR
REPLACE` membership upsert was replaced with a one-time `insertMembership`
(first join) + `touchMembership` (reconnect to the same lobby) to fix a
real bug (the REPLACE reset every economy/perk/color column on every
reconnect). But the replacement's first-join path used a plain `INSERT`,
which doesn't account for `player_id` still being `lobby_members`' primary
key: an existing member of lobby A creating or joining lobby B — the
ordinary Server Browse flow, not an edge case — threw an uncaught `UNIQUE
constraint failed` error inside the WebSocket message handler. `pnpm check`
stayed green through two full runs while this was in the code, because no
existing spec file ever exercised a player switching lobbies; every spec
either stays in one lobby or uses a fresh identity per lobby.

The bug was caught by `advisor`'s review of the diff before the PR merged,
not by `pnpm check` — the agent confidently shipped a crash on a normal
user action, and the first-pass "no regressions" check gave false
confidence because its own coverage had a hole shaped exactly like the bug.

## Done when

- `INSERT ... ON CONFLICT(player_id) DO UPDATE` replaces the plain
  `INSERT` for first-join/lobby-switch (commit 813dd48, in
  [[ANU-013]]'s branch).
- `spec/lobby-membership.test.ts` added: store-level tests for
  switch-resets-economy and reconnect-preserves-economy, plus a real
  WebSocket-level test that creating a second lobby while already in a
  first doesn't crash the connection or the process.
- `pnpm check` green (except [[ANU-012]]'s pre-existing, unrelated
  failures) with the new spec in place.

## Resolution

Fixed in [[ANU-013]]'s branch, commit `813dd48` ("ANU-013: fix lobby-switch
crash, unit_types seeding, spawn player-count, false palette claim"). The
fix itself: `server/store.ts`'s `insertMembership` statement changed from a
plain `INSERT` to `INSERT ... ON CONFLICT(player_id) DO UPDATE SET
lobby_id = excluded.lobby_id, ...` with economy/perk columns explicitly
reset to their defaults in the conflict branch (a lobby switch is a new
game, not a continuation).

`spec/lobby-membership.test.ts` is the check that now catches this
specifically — it would have failed on the broken code and passes on the
fix (verified by reverting the fix locally and re-running the new spec
before committing it).

No `CLAUDE.md` rule change proposed yet — this is a single caught-and-fixed
instance, not (yet) a pattern repeated across issues. If a similar "spec
coverage has a hole exactly where a refactor touches" gap recurs on a later
issue, that's the point to propose a standing rule (e.g. "a protocol/store
change touching existing write paths needs at least one spec exercising
each write path it didn't just add") to the user for `CLAUDE.md`, rather
than inventing one unilaterally now.

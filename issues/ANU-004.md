id: ANU-004
title: issue-finish.mjs used git branch -d, which gives a false negative right after a local merge
status: done
type: harness
opened: 2026-11-02
---

## Why

Writing `scripts/issue-finish.mjs` to automate the end of
[`docs/git-workflow.md`](../docs/git-workflow.md) rule 1 (one issue, one
branch, one worktree) and rule 10 (the `ANU-XXX-name_of_the_issue` branch
convention): once a branch is merged into `main`, the script should remove
its worktree and delete the branch.

## Done when

`issue-finish.mjs` deletes a branch it has just merged into local `main`,
without a false "not fully merged" refusal.

## Resolution

The first version called `git branch -d <branch>` after the merge. Testing
in an isolated sandbox repo (not the real one) hit exactly the failure
`docs/git-workflow.md` rule 9 already warns about: `git branch -d`'s own
safe-delete check compares the branch against its **upstream**
(`origin/main`), not local `HEAD`. Right after a local `--no-ff` merge that
hasn't been pushed yet, `-d` refuses with "not fully merged" even though the
branch demonstrably is an ancestor of `HEAD` — the exact false negative rule
9 describes, now reproduced by a script rather than by hand.

The script already ran `git merge-base --is-ancestor <branch> HEAD` first as
the "independent confirmation" rule 9 calls for, but then still called the
conservative `-d` afterwards, defeating the point of checking independently.
Fixed by switching to `git branch -D` *only after* the `merge-base` check
passes — not a bypass of a safety check, but doing the thing rule 9 already
prescribes: trust the explicit ancestor check over `-d`'s own heuristic.

Caught by running the full start→work→finish lifecycle in a throwaway
sandbox repo (`/tmp/issue-sandbox`, with a bare remote to mimic `origin`)
before running either script against this repo, specifically because a
script doing real `git worktree`/`merge`/`branch -d` surgery is exactly the
kind of thing worth proving against a disposable repo first. Also exercised:
idempotent re-run of `issue-start` on an already-started issue, a real merge
conflict (left for manual resolution, not auto-aborted), `--no-delete`, and
the guard rails (must run from `main`, must be clean, ambiguous/missing
branch refs rejected with a specific error).

## Notes

This is the same class of problem as [[ANU-001]]: a RefWhistle-derived git
rule existed in prose (rule 9) before the automation did, and writing the
automation was what actually exercised the edge case the prose rule had
already anticipated but nothing had yet tested in this repo. See
`scripts/issue-finish.mjs`'s comment at the `merge-base`/`-D` call site for
where the fix lives in code.

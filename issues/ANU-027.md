## Why

[[ANU-020]]'s suburb-detail panel sends exactly one unit per action: pick a
single unit from a dropdown, click "Send unit here". That's tedious once a
player has stacked more than a couple of units in one suburb, and it doesn't
match how the user wants to play this — like Risk: click the territory
you're moving from, declare how many of each unit type to send, then click
the destination territory on the map itself (not a second dropdown).

Confirmed with the user via `AskUserQuestion`:
- This flow **replaces** the old per-unit dropdown + "Send unit here"
  button entirely — not an addition alongside it.
- Quantities are chosen with a numeric input plus `+5`/`+10`/`-5`/`-10`
  stepper buttons, per unit type, capped at however many of that type
  currently sit in the source suburb.
- Robots are greyed out (quantity forced to 0, disabled) for a destination
  the player doesn't border — exactly [[ANU-014]]'s existing `ground`
  reachability rule (owned, or road-adjacent to a suburb they own). This
  is evaluated **after the destination is clicked**, not live per
  map-hover: the quantity panel opens with every type enabled (we don't
  know the destination yet), and clicking a destination suburb then greys
  the robot control if that specific suburb is unreachable for a ground
  unit — the player can still send drones there.
- If the clicked destination isn't owned by the player, a confirmation
  popup ("Confirm attack?") appears before the order is sent — guards
  against a misclick landing an order on the wrong territory. A
  player-owned destination sends immediately, no popup.

## Done when

**Protocol** (`server/protocol.ts`):
- A new `ClientMoveUnits` message: `{ type: "moveUnits", fromSalCode,
  toSalCode, counts: Record<string, number> }` (`counts` keyed by
  `unit_types.key`, e.g. `{ drone: 5, robot: 2 }`) — replaces exposing
  `moveUnit`/`attackSuburb` to the client one-unit-at-a-time.
  `parseClientMessage` validates `fromSalCode`/`toSalCode` as non-empty
  strings (reuse `MAX_SAL_CODE_LENGTH`) and `counts` as a plain object of
  non-negative integers keyed by a bounded-length string
  (`MAX_UNIT_TYPE_KEY_LENGTH`), rejecting anything else the same way every
  other handler does (closes the connection with code 1008 on a malformed
  payload, per the existing convention every `spec/*-protocol.test.ts`
  file checks).
- `server/units.ts` gains a `moveUnits(lobbyId, ownerPlayerId, fromSalCode,
  toSalCode, counts)` method on the `Units` interface. For each unit type
  with a requested count > 0, it selects that many of the owner's own
  units of that type currently at `fromSalCode` (stable order, oldest
  first — same `spawned_at, id` tie-break `selectOccupantsAt` already
  uses) and, for each selected unit, calls the *existing*
  `attackSuburb`-equivalent reachability + combat resolution logic
  (reuse — don't fork — `canReach`/the combat branch already in
  `attackSuburb`) to send it toward `toSalCode`. Movement-mode reachability
  is still enforced server-side per unit, same as today: a bulk order
  requesting more robots than can reach is rejected for the whole order
  (`{ ok: false, reason: "unreachable" }`) rather than silently moving the
  drones and dropping the robots — the client-side grey-out is a courtesy,
  the server is still authoritative, same pattern [[ANU-013]]'s Notes
  established for `attackSuburb` already. Requesting more of a type than
  currently sit at `fromSalCode`, or a `fromSalCode` with none of the
  player's own units at all, is also rejected (reason `"insufficient-units"`).
  Combat against a defended target resolves **unit by unit, in the order
  selected**, each one only advancing/surviving per the existing per-unit
  `attackSuburb` rules (a hit may kill an attacker's unit before later
  units in the same order get their turn; see server/units.ts's existing
  combat resolution) — no new bulk-combat formula.
- `server/index.ts`'s `moveUnits` handler follows the existing
  `attackSuburb` handler's shape (`started`-lobby guard, broadcast
  `occupancy` on success, send `economy` to the acting player if any kill
  occurred during the order).
- The old `moveUnit`/`attackSuburb` client message types and their
  `server/index.ts` handlers are **removed** (the GUI is the only caller
  of either — [[ANU-020]]'s Resolution confirms the sidebar was the one
  place that sent them, and [[ANU-020]]'s Why explicitly scoped
  `placeUnit` as never getting a control, implying `moveUnit`/
  `attackSuburb` were always meant to be GUI-fronted, not a stable public
  API surface) — `server/units.ts`'s underlying `moveUnit`/`attackSuburb`
  functions stay as the internal primitives `moveUnits` composes, just no
  longer reachable as their own wire messages. Cutting them, rather than
  leaving them live alongside the new message, avoids two parallel ways to
  move a unit that could drift apart.

**GUI** (`server/public/map.js`, `server/public/sidebar.js`,
`server/public/suburb-detail-view.js`):
- Clicking a suburb that has at least one of the player's own units
  offers a "Move units" button in the Territory tab's suburb-detail panel
  (alongside the existing `buildFactory` button, which is unaffected).
- Clicking "Move units" opens a quantity panel: one row per unit type the
  player has at least one of in that suburb, a numeric input (defaulting
  to 0), and `-10`/`-5`/`+5`/`+10` stepper buttons, each clamped to
  `[0, countOfThatTypeInSuburb]`. This is new pure-function view-model
  work in `suburb-detail-view.js` (testable without jsdom, same pattern as
  the existing `sendableUnits`/`occupants` fields) plus new DOM wiring in
  `sidebar.js`.
- While the quantity panel is open, the map enters a "pick a destination"
  mode: the next suburb tap is captured as the destination rather than
  reselecting the Territory detail panel. `map.js`'s `onSelect` callback
  shape doesn't need to change; `sidebar.js` just branches on whether a
  move is pending when a `{ type: "suburb" }` selection arrives.
- On destination pick: if that destination is unreachable for `ground`
  units (reuse the same adjacency data the server enforces — exposed
  client-side via a comparably-scoped helper, or accept evaluating this
  fully server-side and just disabling the robot input once the server's
  `unreachable` rejection comes back for a robot-only order; either is
  acceptable, pick whichever doesn't duplicate `server/units.ts`'s
  adjacency table in two places), the robot quantity row greys out
  (input disabled, forced to 0) and the panel stays open for the player to
  confirm drone-only counts or cancel.
- On destination pick, if the destination suburb is NOT owned by the
  acting player, show a confirmation prompt ("Confirm attack on
  <suburb>?") before sending `moveUnits`; if it is player-owned, send
  immediately. A plain `window.confirm` is acceptable here — this repo has
  no existing modal/dialog component, and introducing one is out of scope
  for this issue.
- The old unit-picker `<select>` + "Send unit here" button in
  `suburb-detail-view.js`/`sidebar.js` (`sendableUnits`,
  `attackSuburb`-calling button) are removed.

**`spec/` coverage:**
- `spec/units.test.ts`: `moveUnits` happy path (splits counts across
  multiple types, moves the requested number, leaves the rest at the
  source); rejects a count exceeding what's present
  (`insufficient-units`); rejects when any requested unit type can't reach
  the destination (`unreachable`) without partially applying the order;
  a defended destination resolves combat per unit in order.
- A new `spec/*-protocol.test.ts` (or an addition to an existing one)
  exercising `moveUnits` over the real WebSocket connection, same
  connect/send/waitFor pattern as `spec/skill-tree-protocol.test.ts`:
  malformed payload closes the socket (1008); a valid order broadcasts
  `occupancy`; a kill inside the order sends `economy` to the attacker.
- `spec/sidebar-view.test.ts`: the new view-model output for "units
  available to move, grouped by type, from the selected suburb."
- Any `spec/*.test.ts` asserting the old `moveUnit`/`attackSuburb` wire
  messages are updated or removed to match the new single entry point —
  not left asserting dead protocol surface.

**No regressions**: full `pnpm check` green except the pre-existing,
unrelated [[ANU-012]] map-balance failures.

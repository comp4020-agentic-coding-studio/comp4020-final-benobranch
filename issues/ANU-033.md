id: ANU-033
title: Spawn suburbs render unowned on first paint - mountMap's async fetch raced renderOwnership
status: done
type: bug
opened: 2026-11-05
---

## Why

The user reported that at kickoff, a player's own spawn suburb doesn't show
up filled in their color on the map — only the cyan spawn-ring preview
circle is visible, as if the player has to attack their own spawn to take
it (screenshot: a green player marker inside the ring, but the tile under
it unfilled).

The server-side ownership logic was already correct:
`territory.assignSpawnOwnership` (`server/territory.ts`) writes each
player's spawn suburb into `suburb_ownership` directly in `startLobby`
(`server/index.ts`), before any unit exists to attack with —
`spec/territory.test.ts`'s "spawn-ownership at kickoff" describe block
already asserts this and was (and still is) green.

The actual bug was client-side, in `server/public/app.js`'s
`renderLobbyScreen`: `mountMap(...)` is `async` (it fetches
`/map/map.json`/`/map/map-geometry.json` and only then builds the `<path>`
element per suburb that `renderOwnership` colors — see `map.js`'s
`initOnce`), but the call site invoked it without `await` and immediately
called `renderOwnership(lobby.ownership, lobby.members)` on the same tick.
On the very first mount of a lobby's map, `#map-suburbs` is still empty at
that point, so `renderOwnership`'s `suburbsLayer.querySelectorAll("path")`
matched nothing and colored nothing — permanently, since `mountMap` never
re-ran the render calls itself once its own fetch resolved. Everything else
on the map (the spawn-ring preview, drawn from inside `mountMap` after its
await) appeared fine, which is exactly why only the fill color looked
missing.

## Done when

The first `lobbyState` broadcast after a lobby starts results in every
player's spawn suburb already filled in their color, with no attack
required and no dependency on a later broadcast re-triggering the render.

## Resolution

`server/public/app.js`'s `renderLobbyScreen` now chains
`renderOwnership`/`renderBases`/`renderUnits`/`renderFactories`/
`renderCapture` onto `mountMap(...).then(...)` instead of calling them
synchronously right after an un-awaited `mountMap` call, so they always run
once `map.js`'s suburb `<path>` elements actually exist — on first mount
and on every later re-render alike. `pnpm check` (typecheck + the full
`vitest run` suite, including the existing kickoff-ownership test) stays
green; per `CLAUDE.md`'s temporary cost-discipline rule this was not
re-verified by driving a browser.

## Notes

No spec file asserts the *client's* render-after-fetch ordering (`spec/`
checks the server's broadcast contract and static shell, not map.js's
internal async sequencing) — this class of bug could recur in another
`mountMap`-dependent render path without a test catching it. Left as a
follow-up rather than added here, since retrofitting a DOM-level client
test is a bigger change than this one-line race fix warranted.

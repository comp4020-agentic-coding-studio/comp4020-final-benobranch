## Why

[[ANU-013]] (suburb ownership), [[ANU-014]] (units/drones/robots) and
[[ANU-015]] (factories) all landed with real server logic, a broadcast
protocol, and — for units/factories — a pure map-drawable visual function
(`unit-visual.js`/`factory-visual.js`). None of the three has any client
wiring: `app.js` never even listens for the `occupancy`/`factories`
messages the server already sends, `map.js` has no `renderUnits`/
`renderFactories`/`renderOwnership`, and the reserved `#map-units`/
`#map-ownership` SVG layers in `index.html` have sat empty since ANU-011.
This issue is that wiring, plus a layout change the user asked for
alongside it: once a lobby is `started`, the map should fill the viewport
and every HUD/game panel should live in an overlay sidebar rather than
stacked `<section class="panel">` blocks below a short map box.

**Controls are actionable now, confirmed with the user via
`AskUserQuestion`.** [[ANU-013]]'s Notes deferred actionable (player-
triggered) GUI controls until the skill tree ([[ANU-016]]) and zone
capture ([[ANU-017]]) also existed, reasoning that a GUI built against an
incomplete rule set would need rework. The user explicitly overrode that
for *units and factories specifically*, since ANU-014/ANU-015 are both
`done` — there's nothing left for a units/factories GUI to wait on. Skill
tree and zone capture remain **out of scope**: [[ANU-016]] has real
purchase/protocol logic in an unmerged branch (`origin/ANU-016-...`, PR
#11 draft) as of this issue opening, and [[ANU-017]] hasn't started. No
GUI for either lands here, and this issue must not touch
`server/skill-tree.ts` or anything [[ANU-016]] owns. Because [[ANU-016]]'s
branch also touches `server/protocol.ts`/`server/index.ts`/
`server/public/unit-visual.js` (unmerged at the time this issue opened),
expect a merge conflict on those files when either branch lands after the
other — resolve by union, not by discarding either side's additions.

**The reserved `#map-ownership` SVG layer stays [[ANU-017]]'s.** Its
comment in `index.html` ("ANU-017's renderOwnership/renderCapture layer")
means the diagonal-stripe contest visuals specifically — not basic
ownership-fill rendering, which this issue DOES add (a player's territory
rendered in their color, no stripes, no capture/pause/contest state, since
none of that machinery exists yet). This issue renders ownership by
coloring the existing `.suburb` paths directly (already present per
suburb, already carrying `data-sal-code`), leaving `#map-ownership` itself
untouched and still empty for [[ANU-017]] to fill in.

## Done when

**Protocol (two small, additive, backward-compatible messages — no schema
migration):**
- A new `ServerUnitCatalog` broadcast (`type: "unitCatalog"`) carrying
  every `unit_types` row (`key`, `health`, `damage`, `buildCostScrap`,
  `buildTimeMs`, `movementMode`, `requiresSkillNode`), sent once per
  connection right after `welcome` (global reference data, not
  lobby-scoped). `server/units.ts` gains an exported `listUnitTypes(db)`
  (plain export, same convention as the existing `seedBaseUnitTypes`, not
  added to the `Units` interface).
- A new `ServerEconomy` message (`type: "economy"`, `scrap`, `tflops`) —
  **sent to the player it belongs to, never broadcast** (unlike
  `LobbyState`, which is identical for every socket in a lobby today, a
  scrap balance is private). Sent on `hello` (if the resuming player has a
  lobby), on `startLobby` (to every member), and after `attackSuburb` (a
  kill credits scrap), `buildFactory`, and `queueUnit` (both deduct scrap)
  — to the acting player's own socket(s) only.
- **Deliberately excluded: no GUI control for `placeUnit`.** It's a
  leftover ANU-013 primitive (places a unit in any suburb, no scrap cost,
  no factory) that predates the factory economy — exposing it as a button
  would let a player spawn free units and bypass ANU-015's entire
  scrap/factory system. `moveUnit`/`attackSuburb`/`buildFactory`/
  `queueUnit` get GUI controls; `placeUnit` does not.
- **One "Send unit here" action, not separate Move/Attack buttons**: it
  always calls `attackSuburb` — a strict superset of `moveUnit`'s
  behavior (identical reachability rule; handles both the undefended and
  defended cases), so one button covers both.

**Full-screen layout** (`server/public/index.html`,
`server/public/style.css`, `server/public/map.css`):
- A new `.lobby-screen--fullscreen` class, toggled on `#lobby-screen`
  exactly when `.screen--wide` is today (i.e. `lobby.started`), makes
  `#lobby-screen` `position: fixed` over the full viewport (below the
  existing `.status` bar's `z-index: 10`), `#map-panel` fill it entirely
  (`position: absolute; inset: 0`), and a new `#sidebar` render as a fixed
  overlay panel on top of the map rather than a block below it.
- Every OTHER screen (home/browse/options/name-prompt) and the
  **non-started** lobby screen are pixel-identical to today.
- `#sidebar` is **always present in the DOM**, never `[hidden]` —
  pre-start it renders as a normal in-flow panel holding just the
  existing player list; only its tab nav (`#sidebar-tabs`) and economy
  readout (`#sidebar-economy`) are hidden pre-start, matching
  `#map-panel`'s existing `hidden` toggle. `#player-list` keeps its id
  and stays written by the same `app.js` code, now inside `#sidebar`
  instead of its own standalone section.
- Phone-width: `#sidebar` becomes a collapsible bottom drawer (a visible
  handle toggles `.sidebar--expanded`). Doesn't resolve PLAN.md's
  still-open "list/HUD view vs. full pan-zoom map" question.
- Every new `[hidden]`-toggled element that also gets its own `display`
  override restates `[hidden] { display: none }` — same
  cascade-specificity trap `style.css`/`map.css` already document for
  `.screen[hidden]`/`.map-panel[hidden]`.

**Sidebar structure** (new `server/public/sidebar.js`):
- Three tabs — Territory (player roster + the selected suburb's detail),
  Units (roster of the player's own units), Factories (roster of the
  player's own factories).
- Clicking a suburb on the map opens/updates the Territory tab's suburb
  detail section: owner, occupant units, factory (if any), and action
  buttons (`buildFactory` if owned with no factory, `queueUnit` controls
  if owned with a factory, a unit-picker + "Send unit here" button that
  calls `attackSuburb`).
- Clicking a unit or factory icon on the map switches to the matching tab
  and highlights that row.
- `unitCatalog` supplies real build costs/stats for every build button
  (never hardcoded); a unit type with a non-null `requiresSkillNode` is
  not offered yet (no skill-tree-unlock check exists client-side — both
  seeded base types have it null today).
- `economy.scrap` greys out/disables a build button whose `buildCostScrap`
  exceeds the player's current balance.

**Map rendering** (`server/public/map.js` gains composed layer functions,
per ANU-013's file-layout convention):
- `renderOwnership(ownership, members)` — colors each existing `.suburb`
  path by its owner's `PLAYER_COLORS` entry (semi-opaque fill), full
  redraw on every call (same `replaceChildren`-then-rebuild precedent as
  `renderSpawns`). Does not touch `#map-ownership`.
- `renderUnits(units, members)` — populates `#map-units` with one icon
  per `OccupantUnit`, built via the already-tested `unitVisual()`, colored
  by owner, clickable (`data-unit-id`, `pointer-events: auto`).
- `renderFactories(factories, members)` — populates a new
  `#map-factories` layer (added to `index.html` between `#map-spawns` and
  `#map-units`) with one icon per factory via the already-tested
  `factoryVisual()`, clickable (`data-factory-id`).
- `mountMap`'s exported surface grows an `onSelect` callback parameter:
  fired with `{ type: "suburb", sal_code }`, `{ type: "unit", unitId }`,
  `{ type: "factory", factoryId }`, or `null` (deselected) — `app.js`
  forwards the event into `sidebar.js`.

**`spec/` coverage:**
- `spec/gui.test.ts`: `#sidebar` exists and is never `[hidden]`;
  `#sidebar-tabs`/`#sidebar-economy` hidden by default; `#panel-territory`
  visible by default, `#panel-units`/`#panel-factories` hidden by
  default; `#player-list` exists inside `#panel-territory`, not as a
  standalone top-level section; `#suburb-detail`/`#unit-list`/
  `#factory-list` exist; `#map-factories` exists inside `#map-svg`.
- New `spec/sidebar-view.test.ts` (pure function, matching
  `spec/unit-visual.test.ts`'s pattern): a `suburbDetailViewModel`
  function's output for owned-no-factory, owned-with-factory,
  unowned-empty, and `sendableUnits` filtered to the viewing player.
- New protocol-level assertions (WebSocket, matching
  `spec/occupancy.test.ts`'s helpers): `hello` yields a `unitCatalog`
  with the real seeded drone/robot stats (not placeholders); a kill via
  `attackSuburb` sends `economy` to the attacker only, not to a bystander
  in the same lobby; `queueUnit`/`buildFactory` each trigger an `economy`
  update reflecting the deduction.

**No regressions**: full `pnpm check` green except the pre-existing,
unrelated [[ANU-012]] map-balance failures.

## Resolution

Built largely as scoped. Opened as **ANU-020** rather than ANU-019 — that
number was independently claimed (TFLOPS-accrual bug) by another parallel
session between planning this issue and opening it, and ANU-016 (skill
tree) also landed real purchase/protocol logic in an unmerged branch in the
same window; both were just names/context to work around, not blockers,
since this issue's branch point predates ANU-016 merging.

**Protocol**: `UnitTypeCatalogEntry`/`ServerUnitCatalog`/`ServerEconomy`
added to `server/protocol.ts` exactly as scoped. `server/units.ts` gained
`listUnitTypes(db)`. `server/index.ts`'s `hello` handler sends the catalog
unconditionally (global data) and the caller's own economy when they have a
lobby; `startLobby` primes every member's economy; `attackSuburb` sends it
only on a `"kill"` outcome (not `"hit"`/`"moved"`, which don't change
scrap); `buildFactory`/`queueUnit` send it on every success. No schema
migration — both messages read `unit_types`/`lobby_members` columns ANU-013
already created.

**Full-screen layout**: `.lobby-screen--fullscreen` toggled in `app.js`'s
`renderLobbyScreen` alongside the existing `.screen--wide`, scoped so no
other screen or the non-started lobby screen changes. `#sidebar` is always
in the DOM, never `[hidden]` itself — only `#sidebar-tabs`/
`#sidebar-economy` are hidden pre-start, matching `#map-panel`'s existing
toggle. `#player-list` kept its id, now nested in `#panel-territory`.
Found and fixed, before it shipped, the same cascade-specificity trap
`style.css`/`map.css` already document for `.screen[hidden]`/
`.map-panel[hidden]`: `.sidebar-tabs`/`.sidebar-economy`/`.sidebar-panel`
each set their own `display`, so each needed its `[hidden]` rule restated
explicitly — without it, a pre-start lobby would have rendered the tabs/
economy readout despite the `hidden` attribute being present. Phone width
(≤640px) collapses the sidebar into a bottom drawer toggled by a handle
button, per plan — doesn't resolve PLAN.md's open list/HUD-vs-map question.

**Map rendering**: `renderOwnership`/`renderUnits`/`renderFactories` added
to `map.js`, all following the existing `renderSpawns` full-redraw
precedent (no diffing — nothing here touches the viewBox). `renderOwnership`
colors the existing `.suburb` paths via an inline `style` attribute rather
than a class, so it doesn't fight the existing `.suburb:hover`/
`.suburb.selected` class-based rules on specificity. `mountMap` gained an
`onSelect` callback; the existing tap/click handler now checks
`dataset.unitId`/`dataset.factoryId` (icons painted on top of the suburb
layer) before falling back to `dataset.salCode`, so a tap always resolves
to the topmost thing actually under the pointer.

**Sidebar**: `server/public/sidebar.js` (DOM-writing, tabs/actions) plus
`server/public/suburb-detail-view.js` (the pure `suburbDetailViewModel`
function, split into its own dependency-free file specifically so it's
importable/testable without jsdom — `sidebar.js` itself does
`document.getElementById` at module top level, same as `map.js`/`app.js`,
which would throw on a plain Node import). Territory/Units/Factories tabs,
contextual suburb-detail actions (`buildFactory`/`queueUnit`/a unit-picker
"Send unit here" calling `attackSuburb`), all gated client-side only as a
courtesy (affordability, no-factory-yet) — the server's existing
accept/reject logic remains authoritative.

**Scope boundaries held**: no control added for `placeUnit`; "Send unit
here" always calls `attackSuburb` (one button, not two); no skill-tree or
zone-capture GUI; `#map-ownership` left untouched for ANU-017.

**Verification**: `pnpm check` — typecheck clean, `check:issues` clean,
131/140 tests pass. The 9 failures are exactly ANU-012's pre-existing,
already-open `spec/map-balance.test.ts` failures (same failures present on
`main` before this branch, confirmed by the stock-`main` baseline run this
issue's own run was diffed against during development). New coverage: 7
`spec/sidebar-view.test.ts` pure-function cases (owned/unowned, with/without
factory, busy-factory, sendableUnits/occupants filtering); 2 new
`spec/gui.test.ts` cases (sidebar/tabs/economy visibility, Territory/Units/
Factories panel markup, `#map-factories` layer) plus 1 extending the
existing map-panel-markup test; 3 `spec/economy-broadcast.test.ts` cases
(real seeded catalog stats, kill-credits-economy-to-attacker-only privacy
check against a bystander in the same lobby, queueUnit's deduction) —
each kill-dependent test needed a *second* connected player to own the
defending unit, since `attackSuburb` against a target with no other
player's unit present just resolves as an undefended "moved" (no scrap
credited) rather than a kill; the first draft of these tests had both the
attacker and defender owned by the same connection and consequently never
exercised a real kill, caught by running the tests and seeing them time out
rather than assumed to be correct.

Per `CLAUDE.md`'s current cost-discipline rule, no headless-Chrome/manual
e2e verification was performed or is required — `pnpm check` against a
locally-started instance (port 8120, a scratch `DATA_DIR`, per
docs/git-workflow.md rule 6) is the bar this issue was verified against.
